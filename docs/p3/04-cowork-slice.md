# P3.04 Cowork 纵向切片：录入工作台

日期：2026-09-17。站点：`cowork-a.localhost`。

## 切片范围

对应旧系统界面上的「录入工作台 → 识别记录 → 推送日志」这条线。

| 产出 | 说明 |
|---|---|
| DocType `Intake Record` | 识别记录：方向（进项/销项）、来源（上传/LINE/邮件/手工）、单据号与日期、对方名称与税号、金额、类别、附件、推送渠道与状态、识别留证、去重键与影像指纹 |
| 服务层 `pearnly_cowork/intake.py` | 建单、人工确认、排队推送、列表、汇总；五个给前端用的接口 |

## 状态机是这条链路的骨架

```
draft ──识别完成──> recognized ──人工确认──> confirmed ──排队──> queued ──> pushed
                                                            └──> failed / rejected
```

写在 DocType 层，**不允许跳步**：

- 新记录只能从 `draft` 或 `recognized` 开始；
- 状态**不能回退**；
- **没确认过的单据不能推送**（这条被实测拦截过，见下）。

## 小助手（Companion）在切片里的位置

`push_channel` 有两个值：

- `companion` —— 由**小助手在商家本机出站拉取**后落库（云端不主动连入）；
- `cloud` —— 云端直接推送。

切片里已把这个分支建出来并实测走通（`channel: companion`）。完整的配对、心跳、
套账上报、本机落库属于 P6 的集成范围，本轮只保证"这条链路在数据模型上存在且
可被选中"。

## 实测结果（全部通过）

脚本 `scripts/sample-cowork-slice.sh`：

| 步骤 | 结果 |
|---|---|
| OIDC 登录 | 身份 `tenant-admin@sample.local` |
| 录一张进项票（识别完成，未确认） | 生成 `IN-2026-00006` |
| **未确认就排队推送** | **被拒**：`只有已确认的单据才能排队推送` |
| 人工确认（并改对方名称为全称、补类别） | `status: confirmed`，价税合计 `1070.00` |
| 排队走小助手通道 | `status: queued`，`channel: companion` |
| 列表 | 状态、对方名称、金额、渠道都对 |
| 汇总 | 按状态计数；进项已确认金额 `1070.00` |
| 同一张票再录一次 | **被去重拦下**：`这张票已经录过：IN-2026-00006` |

金额核对：不含税 1000 + 增值税 70 = 1070.00，与返回一致。

## 本轮修掉的两个真问题

### 1. 改密页的 CSRF 令牌渲染成了字符串 "None"

`pearnly-password.html` 里原先写 `{{ frappe.session.csrf_token }}`，实际渲染出的是
**字符串 `"None"`**（该字段在会话数据里可能还没生成）。前端拿这个值去调接口必然失败。

改为在页面控制器里显式取：`from frappe.sessions import get_csrf_token; context.csrf_token = get_csrf_token()`。

这个 bug 在做上一个功能时没被发现——当时的验证脚本正好没走页面取令牌那条路。

### 2. 测试脚本的请求体靠 shell 转义拼字符串，极易出错

表现是服务端只回一句 `Invalid request body`，看不出任何细节；排查了很久才发现请求体
末尾多了一个 `}`。

处理：请求体改成 **heredoc 直接写**（不再经 shell 转义），并在发出前**本地校验一次 JSON**，
不合法就把原文打出来。这类"看不见的失败"以后会当场暴露。

**说明**：这两条都属于"验证工具与页面自身"的问题，不是业务逻辑缺陷；但它们会让
验证结果不可信，所以必须修。
