# 按影响面验证

一份结果只证明它实际覆盖的代码、环境和场景。没有新修改、失败或新证据，不扩大或重复验证。既有有效强制检查仍需完成；本规范不把未接入的工具称作自动闸门。

## 选择矩阵

| 改动 | 最低需要的验证 | 何时扩大 |
| --- | --- | --- |
| 文档、AGENTS、模板 | diff、链接、命令/路径存在性、规范冲突 | 增加了脚本或执行配置时，验证其真实调用 |
| Python 纯逻辑 | 适用配置的语法/静态检查，受影响成功与失败用例 | 引入 Site、数据库、缓存或外部 I/O 时进入对应层 |
| Frappe 接口、权限、共享 core | 隔离 Site 内行为；未登录、无权、跨租户拒绝；受影响调用方 | 共享身份/会话改变时覆盖相关产品入口，至少包含已跑通 DMS 链路 |
| DocType、fixtures、patches、安装 hooks | 新 Site 安装、已有测试 Site 升级、重复 migrate、数据/用户设置保留 | 有数据风险时做新鲜备份及独立 Site 恢复验证 |
| Vue 页面、交互、接口字段 | 前端 build、翻译检查、受影响入口的浏览器操作和服务端回读 | 手机布局、语言或 LINE 行为改变时增加相应设备/语言验证 |
| LINE / DMS 状态流转、队列、提交 | 定向链路、重复事件、nonce、并发/幂等、权限、失败与重试状态 | 需要外部效果时在已有明确授权下真连并回读结果 |
| 任何旧功能迁移 | 开工与交付前旧生产版本回读、源码映射、行为及依赖增量核对 | 线上相关行为变化时同步增量并复验；见 [线上基准](migration-baseline.md) |
| Compose、镜像、底座依赖 | 配置解析、锁定版本/架构核对；受影响启动与持久化 | 底座升级加入安装、迁移、恢复及 DMS 关键回归 |
| 检查脚本、CI | 语法、正常路径和关键拒绝路径，核实作用范围 | 不为每行配置写一份镜像测试，不触发业务全量作为默认 |
| 界面文案（术语表、CC 网页 `i18n.ts` / TSX、CC 桌面版 `i18n.py`、Keycloak 主题、页面与邮件模板） | `python3 scripts/check-copy.py`（相对 merge-base 的新增 / 改动文案与新代码里的写死、拼接；改已有文案先给用户看并登记），交付时附 `--report` 清单给用户和测试窗口；见 [界面文案](interface-copy.md) | 改了闸门本身或词表时跑 `python3 tests/test_check_copy.py`；整改存量用 `--audit` 出报告 |
| 发票识别读法（模型版本、提示词、读法、识别后确定性规则） | 两批金标同口径评测四项指标不退、测试租户并发压测（3 租户 × 10 人）速度不退；见 [识别改动上线闸门](#识别改动上线闸门) | 一次只改一个变量；成本变化先报告再上线 |
| 改到登记的共用件（`scripts/impact/shared-parts.toml`：扫码 / 相机、上传、LINE 共用流程与三个点、公司切换 / 选择框、页面注册与侧栏、权限钩子、CC 设置页与心跳、`cc_desktop` 通道、写账规则、按码找商品、下载等） | `python3 scripts/check-impact.py` 出影响清单，清单里**每个入口**按「通过 / 不通过 / 没测到（原因）」记进任务记录；见 [共用件连带回归闸门](#共用件连带回归闸门) | 上线后对线上测试租户跑只读冒烟子集 |
| 需要在真实环境确认的改动 | 在 [Windows 测试环境](test-environment.md) 用**同一镜像 digest** 起环境，并用测试租户走一遍受影响路径 | 涉及电话/手机、真实 LINE 消息、第三方落单时，要在切换状态下做真机验收并单独记录 |

格式按各 App 的 `pyproject.toml` 和已有配置；不要跨仓复制 Ruff 版本后批量改写全部文件。存量问题记清基线和影响，新增回归必须处理，不能假借存量问题忽略本次失败。

## 现有入口

### 静态与前端

在工作树根目录运行：

```bash
git diff --check
git diff --cached --check
python3 scripts/i18n-build.py --check
python3 scripts/check-i18n.py --strict
python3 scripts/check-frontend-i18n.py --strict
python3 scripts/check-copy.py
npm --prefix frontend run build
```

CC 对话页（`frontend/assistant`）改界面时另跑 `python3 scripts/check-frontend-tokens.py`（组件里不许写死颜色、圆角、阴影，只引用 `globals.css` 的变量，见 [ccs](ccs.md)）。

按矩阵选择命令；上面的翻译检查不会改语言包。首次安装或锁文件变化时用 `npm --prefix frontend ci`。`build` 自带 `vue-tsc --noEmit`，只查类型可单独用 `npm --prefix frontend run typecheck`。

构建输出在 `apps/pearnly_core/pearnly_core/public/pearnly-app/`，是被忽略的生成目录。正式构建需确保镜像包含对应版本的产物；不能把旧仓的 `static/dist` 提交规则搬过来。前端开发入口见 [前端说明](../../frontend/README.md)。

App 下虽然有 `.pre-commit-config.yaml`，但它们不是根级统一检查；根级只有 `.githooks` 的共享钩子（提交时跑架构检查与界面文案闸门并禁止在 `main` 上提交，推送 `main` 时要求快进且 CI 已通过）。整合后的主线已有手动镜像构建/投递工作流，这与统一 PR 检查不同。不能认为进入 App 目录就会自动检查整个单仓，也不要未经核对运行带 `--fix` 的全仓钩子。

### Frappe 与 DMS

新增框架集成测试优先放在所属 App 的 `test_*.py` 中，使用锁定版本的 Frappe 测试机制；在已配置开发依赖的隔离 bench 内用 `bench --site <测试站点> run-tests --module <真实测试模块>` 选择范围。占位符不是现成模块，不能记录成已执行。[官方测试文档](https://docs.frappe.io/framework/user/en/testing)

迁移中的既有 sample 脚本继续保留，不为统一目录一次性重写。以下是选用索引，不是自动执行列表：

| 影响范围 | 本仓入口 | 执行前提 / 证据边界 |
| --- | --- | --- |
| DMS 客户端纯逻辑 | `scripts/sample-verify-dms-client.sh <组>` | 假 transport、不连外部；包装器仍使用指定容器及其中安装的代码 |
| 订车提交登记 | `scripts/sample-verify-dms-booking-attempt.sh <组> <测试Site>` | 真实 Site 会话和 Redis；会改本地测试状态 |
| LINE 入口路由 | `scripts/sample-verify-dms-entry-e2e.sh <组> <测试Site>` | 出口和两处入队均替换，真实本地会话；不是 LINE 真机 E2E |
| 网页编辑器 API/票据 | `scripts/sample-verify-dms-edit-browser.sh <组> <测试Site> <端口>` | 本地 Site 与 HTTP 断言；已有脚本假定该测试站点未配置 LIFF |
| 编辑器页面 | `scripts/sample-verify-dms-edit-page.sh <组> <测试Site> <端口>` | 先读脚本，核对真实 DMS 主档读取、测试草稿及消息出口；不默认离线 |
| 查询/其他 DMS 模块 | `scripts/sample-verify-dms-*.sh` 中对应单项 | 先读选中脚本和被调用代码，逐项确认副作用；禁止 glob 批量运行 |

测试前必须确认容器运行或挂载的是本次工作树的代码；脚本从本树送进容器，不代表容器中的 App 也来自本树。记录镜像 ID、挂载来源及 Site。多个脚本共用 `/tmp/dmscheck`，未经隔离不要并行覆盖同名脚本或争用同一测试账号。

新建或修改验证脚本时明确标出：使用的环境、数据修改、外部调用、退出条件、清理范围。异常、缺依赖、未跑到断言都应失败；不能只打印 `PASS`，也不能只见 `RESULT` 就忽略后续错误。

### 运行配置

`bash scripts/stack.sh config --quiet` 用于配置解析，`bash scripts/stack.sh ps` 查看样板服务。完整 `config` 和容器环境可能包含凭据，不作为未脱敏的提交或聊天证据。

`scripts/dev-reload.sh <组> --sites <测试Site>` 会清缓存并重启运行组；即使指定 Site，同组服务重启仍影响其他 Site。结构变化才用 `--migrate`，先准备数据保护；默认不执行 `all --migrate`。

## 识别改动上线闸门

用户 2026-10-02 定：生产上的识别**模型版本、提示词、读法冻结**。任何改动（换模型、改提示词、改读法、加识别后的确定性规则）
都要先过下面两道闸才能上线，**一次只改一个变量**；没过的不合入、不部署。

**闸 ①：两批金标同口径评测**（约 660 张票，扫描件、照片、电子 PDF 都有，采购与销售都有）

- 金标与样本只在生产机：`/root/pearnly-corpus/06-录入推送/金标.tsv`（287 份）、`金标扩充.tsv`（646 份），对应样本
  `样本-发票300.tsv`、`样本-金标扩充.tsv`。语料不出生产机、不进仓库；结果放 `/tmp/pearnly-eval/<轮次>/`。
- 工具 `scripts/eval-invoices.py`，在生产机一次性容器里跑（用法见文件头）：
  - 改模型 / 提示词 / 读法：识别窗口出一个 0% 流量的带标签修订版，测试租户临时指向它，`run` 按真实入口提交两批里受影响的形态，
    跑完无论成败改回主地址并回读。会真实识别、按页计费，费用先报。
  - 识别后的确定性规则：不新增调用，在已存结果上零费用重放；需要 Vision 原文的用 `l1` 从检查点桶取回（7 天内）。
  - 打分：`python3 eval-invoices.py gold --count-missed --gold <金标> --runs <生产基线同批文件> <候选>`。
    `--count-missed` 把整份漏掉的真票和没对上的票按「全部字段错」计入分母，候选与基线同口径。
- 四项指标，和**同一批文件**的生产基线比，两批分别看、合并报：

| 指标 | 阈值 |
| --- | --- |
| 印了的读错或漏读（票面印了的字段读错或没读出） | 不升 |
| 字段总错误率（含没印却填了；漏掉的真票按全错计） | 不升 |
| 真票被拒（整份判成不是发票） | 为 0（不多于基线） |
| 非票据入账（不是票据却建了记录） | 不增 |

评测噪声约每 2000 格 ±4 处（同一读法连跑两轮也会有新错与改对互抵）。按批次是否改了读法分开跑、分开判（用户 2026-10-02 定，省测试费）：

- **改了读法的批次**（模型、提示词、读法逻辑、识别后改值的后处理）：照旧两批金标**全量**，四项照表严格判。
- **没改读法的批次**（提速、稳定性、派发、存储、基础设施，读法代码与提示词未动）：只跑**固定小样本**，再加零费用重放：
  - 小样本清单固定为生产机 `/root/pearnly-corpus/06-录入推送/样本-闸1小样本.tsv`（79 份、97 页），由
    `eval-invoices.py subset` 按 方向 × 形态 × 是否票据 分层、层内按编号 sha1 排序取出，每轮都用同一份，不重新抽。
    分层页数：采购 扫描 18 / 照片 18 / 电子 12，销售 扫描 8 / 照片 8 / 电子 13，非票据 扫描 8 / 照片 8 / 电子 4。
  - 跑（生产机 `/tmp/pearnly-eval/`）：`SUBSET=<清单> bash evalpair.sh <标签地址> <轮次> 扫描PDF,照片,电子PDF`（只提交清单里的文件）；
    打分：`eval-invoices.py gold --count-missed --subset <清单> --gold <金标> --runs <上一轮> <本轮>`（上一轮全量结果按同一清单截取，零费用）。
  - 零费用重放：本批若动了站点侧识别后的代码路径，用本批代码在上一轮存的结果与 Vision 原文（`l1`）上重放，字段应逐格相同。
  - 小样本噪声比全量大（约 620 格；batch2 → batch3 同读法两轮：印了的读错 +2、字段总错 +6）。**超出下面任一条才补跑全量**，否则按过关：
    印了的读错多于 +3 格；字段总错多于 +8 格；漏掉的真票或整份漏掉增加；真票被拒（打不开以外的整份判非票据）增加；
    非票据入账多于 +2 份；降级 / 换入口等兜底路径明显增多。阈值随后续同读法轮次的实测再校准。
  - 全量判法（同读法批次）：「字段总错误率」允许在噪声带内（每 2000 格 ±4，按格数等比放大），要写明逐格新错 / 改对数与分布；
    「印了的读错或漏读」不升、「真票被拒」为 0 照旧严格。2026-10-02 首次按此判（`docs/work/2026-10-02-release-batch-next.md`）。
- 压测同样省费用：发票识别用回放（`scripts/ocr-replay.py` 开 `pearnly_ocr_replay`，交回以前的真结果、不调谷歌、识别费 0；
  只认 `testcowork` / `testerp` / `testdms` 系列站点，`check-architecture.py` 拦误开；原件池与回放库留在生产机），对账从 15 套减到 5 套。

**闸 ②：测试租户并发压测（3 租户 × 10 人同时上传）**：速度不退（排队、单页耗时、整份完成时间），在测试租户上跑。
现阶段目标是 3 个租户各 10 人同时用不排队（用户 2026-10-07：「100 人压测不要做了，太大了」）；扩容验收另按 [生产容量](production-capacity.md)。

## 共用件连带回归闸门

起因：改了盘点用的安卓扫码，其它入口扫码全部黑屏，没有窗口发现（2026-10）。凡改动命中登记的共用件，**先出影响清单，清单里每个入口实测通过才能合入**。

1. 登记表 `scripts/impact/shared-parts.toml`：每个共用件的路径、识别调用方的特征串、全部入口（产品、页面、怎么点、预期、自动 / 人工）。
2. `python3 scripts/check-impact.py`（CI 同名步骤）读相对 merge-base 的 diff：
   - 列出命中的共用件和要测的入口（`--markdown` 输出贴进 `docs/work/` 任务记录）；
   - 按特征串反查全仓调用方，**有调用方没登记就失败**——新加调用方、新页面要同一提交里补登记；
   - 登记表本身的格式、入口引用、路径存在性不对也失败。
3. 实测：自动的入口用 `scripts/smoke/`（实验栈对候选源码：每页打开无 JS 报错、扫码入口有画面且读出测试码、上传走通、LINE 模拟 webhook、Express 写 C 盘读回）；
   标「人工」的入口由验收窗口按清单逐个点。扫码、相机、上传**逐入口**，不抽样。
4. 记录：每个入口一行「通过 / 不通过 / 没测到（原因）」，**不能用推断或「同一组件已测过」代替**；没测到的不能写成通过。
5. 上线后：对线上**测试租户**跑只读冒烟子集（`scripts/smoke/` 的 `--readonly`），不碰真实客户站点。
6. 开发窗口与验收窗口**各自独立**出清单（一个跑脚本、一个按代码与登记表自己核），对比后互相补漏；补出来的入口同一批补进登记表。

## 四类副作用

1. **离线**：静态检查、假 transport、无网络单测，可在本任务环境直接执行。
2. **本地数据写入**：Site 测试、草稿、队列、fixture，须确认隔离数据与恢复方式；不借测试清空共享数据库。
3. **外部读取**：登录、查主档也可能挤掉共享账号会话或消耗配额。确认任务范围和账号占用，按读请求安排。
4. **外部写入或付费调用**：DMS 建单、推送 LINE、真实 OCR、账号/渠道配置等只在明确授权下执行；记录目标、操作和回读方式。

已发现 `sample-verify-dms-booking-real.sh` 会真实建订车单并挂附件。`*-real*` 通常需要额外核对，但没有 real 后缀也不能判定安全。预览卡、日志或 HTTP 成功不代替外部系统记录。

## 每次怎样留证据

记录：时间、源码 SHA（未提交变更另记差异）、环境/数据归属、命令或操作、预期、实际、退出码及未覆盖项。日志/截图存受控位置并脱敏，索引写工作包。

分别标记实现、本地验证、CI、部署、外部结果、用户验收为“通过 / 失败 / 未执行 / 不适用 / 阻塞”，并给依据。只有用户确认才记录用户验收；一个层级通过不自动推进下一个层级。历史通过保留原日期，不改写成当前版本通过。

## 架构与开户边界

所有代码工作包先运行 `python3 scripts/check-architecture.py`；DMS 改动运行 `python3 scripts/check-dms-offline.py`（207 条离线业务断言，无网络）。不要批量执行未审过的 sample 脚本。
