# 标准开发流程

适用范围：本仓代码、开发工具和开发文档。原则是一个工作包解决一个可验收的问题，证据与代码同批交付。不是新增产品功能的审批流程。

## 1. 定义任务和基线

- 用户当前请求决定范围，来源仓库、旧交接和历史 TODO 只提供证据。
- 记录目标、完成条件、涉及目录、是否涉及数据或外部写入。普通实现选择自行决定；只有关键歧义或缺少必要授权才询问。
- 查看 `git status --short --branch`、`git diff --cached --name-only`、`git worktree list` 和 `git rev-parse HEAD`。不替其他任务提交、stash、reset 或清理。
- 确认集成目标分支和基线 SHA，再创建 `codex/<主题>` 工作树。续接未合并的迁移工作时可从对应提交开始，须写明依赖；不要把 DMS 分支固定成所有未来任务的主线。
- 需要了解远端时只读查询；刷新本地 refs 后记录新基线，不顺手改写他人分支。尚未整合远端不宣称已经满足合并条件。
- 确认远端默认分支与集成主线。当前远端默认是 `main`；任务分支只承担临时开发。完成时记录提交、目标主线、合并和远端回读结果；未合并说明具体缺口，不把分支推送当作收口。

多步骤、跨模块迁移或跨会话任务使用 [工作包模板](templates/work-package.md)。一行文案、小修可以只写提交或 PR；不为了格式建立多份内容相同的记录。

## 2. 为迁移建立可核对的映射

**先按 [迁移线上基准](migration-baseline.md) 读回旧项目当前生产身份，再开始移植；交付前再次读回。** 本地旧仓与远端最新源码都必须和线上进行核对。每批迁移先列最小合同：

| 生产证据 / 核验时间 | 来源仓库 / SHA / 路径 | 本仓落点 | 保持的行为 | 有意变化与依据 | 验证场景 |
| --- | --- | --- | --- | --- | --- |
| revision、digest、流量与源码映射 | 填实际值，不写“旧系统最新版” | App、接口或页面 | 输入、输出、权限、状态、副作用 | 当前需求或 ADR 链接 | 正常、拒绝、失败恢复 |

查看来源代码时核对它是不是已证实的生产 SHA；有脏文件的日常目录不能自动充当上线版本。可以通过 `git show <sha>:<path>` 读取固定版本，不必切换或清理来源工作树。线上证据不足时可继续只读调查，但不能猜一个 SHA 开始移植。

逐项区分：直接复用、适配框架、重新实现、明确不迁移。记录真实差异，不以函数同名、代码行数或测试数量证明等价。现有 DMS 链路是迁移回归基线；共享层变化也要回归受影响的 DMS 入口。

## 3. 选择实现和环境

- 自有功能放自有 Frappe App；参考 ERPNext 的组织、权限、迁移和测试方法，不因此增加 ERPNext 业务模块。
- DocType JSON、控制器、hooks、fixtures 和 patches 随 Git 管理。新旧数据的迁移逻辑明确区分，升级不能重跑 seed 覆盖用户设置。
- 涉及底座、存储边界、协议或不可兼容行为的决定写 ADR；普通局部实现记工作包即可。
- 按 [兼容矩阵](../p1/01-version-matrix.md)、镜像 digest 和锁文件安装依赖。上游源码快照、镜像版本、Site 安装 App 是三个不同的事实。
- 本地运行前核对 Docker context、Compose project、端口、卷、Site、镜像及源码挂载。现有 Compose 固定了 `pearnly-sample` 名称，换工作树后直接 `up` 可能改掉共享服务的挂载。
- 需要独立运行环境时必须确认 project、端口、卷和凭据均隔离；未隔离前不接管共享样板。只读诊断和纯静态检查可以继续。
- 快速迭代优先复用已有环境；重载仍会影响同组其他 Site。文档变更不启动容器；依赖或正式候选构建才需要重建镜像。

## 4. 实现与验证

先确定什么结果算通过，再改代码。验证范围由 [检查矩阵](verification.md) 决定：低风险文档只做静态检查；业务修改覆盖成功、失败和权限；数据库与框架迁移用隔离真实 Site。

Bug 修复在适合自动化时保留能复现旧错误的回归检查。检查应证明行为，不只检查函数被调用、代码中存在某串字符，或复制实现再计算一次。已有测试足够就复用。

失败时区分代码失败、环境阻塞和存量问题。修复失败项及相关影响，不通过删断言、放宽基线或吞掉错误过关。记录跳过原因；“没环境”是未执行，不能算通过。

## 5. 审查与合并准备

审查最终差异：

- 触发条件、变化后的行为、上下游调用方是否一致；API、队列消费者、UI 和状态回读是否同步。
- 服务端权限、租户边界、重复事件、并发、超时与重试是否保持；外部写入结果不确定时，先查结果再重试。
- 依赖、迁移、翻译和构建产物是否完整；日志和截图是否泄露凭据或个人信息。
- 验证是否覆盖受影响场景，工作包和文档是否反映最终实现。

默认实现者自审；需要独立审查时由用户或已授权的审查 Agent 执行，不能把自审写成独立审查。严重缺陷未解决或关键检查未执行，不标“可合并”。

提交格式为 `<type>(可选范围): 简要说明`，使用真实作者，不加工具署名。使用明确路径 `git add <本任务文件...>`，提交前检查暂存差异。提交、推送、建 PR 和合并按当前任务授权执行；已有明确授权不重复问。

PR 使用 [模板](../../.github/PULL_REQUEST_TEMPLATE.md)。只改文档时允许压缩成问题、结果、检查三项。合并前确认候选包含目标分支的新改动；新冲突或新增差异只触发相关复验。不要仅靠一张历史绿色截图判断当前候选通过。

多个工作树收口时：列各分支独有提交 → 在隔离环境合并候选 → 核对组合后的入口和版本 → 按授权合回集成主线并推送 → 回读远端 SHA。Git 无文本冲突只说明可以自动拼合，不能代替组合验证。未合并的独有提交不清理；原工作树更新前确认其任务和运行挂载已不再占用。合并代码与部署服务器分别处理，不顺带切生产。

## 6. 发布与收尾

任务包含发布时才进行：确认候选 SHA、构建内容与镜像 digest，完成本地相关验收，准备受影响 Site 的备份和恢复方案，再按已授权目标执行。数据升级使用原生 migrate；失败不得用 `--skip-failing` 标成成功。

发布后回读运行身份、受影响入口、队列和必要业务结果；真机或外部系统尚未验的部分单独保留。含 schema/data 迁移的恢复需要配套数据库、文件、配置和原镜像，不能假设降级镜像即可恢复。使用 [发布记录模板](templates/release.md)，不从此规范推导任何生产写入授权。

未包含发布时，交付源码或文档就是本次范围内完成。更新任务记录，列明下一步；不为了“收工”重跑全套。只清理明确属于本任务的临时进程、文件和工作树；业务数据、共享依赖、未知归属资源保留。
