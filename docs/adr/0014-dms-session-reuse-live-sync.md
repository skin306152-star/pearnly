# ADR-014：DMS 会话复用、白天增量同步与账号并发

- 状态：用户采纳，2026-09-27（"一起做，按你说的顺序来""4 的接口也留出来"）。
- 修订 [ADR-011](0011-dms-manual-read-snapshots.md) 的三点：订车提交前的主档复核改读本地快照；不再"每次操作都登录、结束即登出"；DMS bench 的 scheduler 检查间隔改为 60 秒。ADR-011 其余决定（交互读本地、提交实时复核、四组手动/绑定建底座、夜间全量兜底）不变。

## 背景（2026-09-27 在 DMS-TEST 只读实测）

- 登录是最贵的一步：测试站 2–4 秒，生产实测 6–16 秒（新连接 TLS 握手）；业务请求每个 0.07–0.5 秒。
- 会话只靠一个 `PHPSESSID` cookie。把它放回新的浏览器上下文、甚至普通 HTTP 请求，仍是登录态；闲置多档仍有效（结果见[工作记录](../work/2026-09-27-dms-session-reuse.md)）。
- 使用记录（`eventlog`）按模块查条数每次约 0.07 秒，改动当秒可见。
- 本站所有操作员连接配的是同一个"管理员"账号（绑定时就是老板本人的 DMS 账号，ris 为 `dms001`），而改动前每次操作都同时锁销售与管理员两把账号锁：全体操作员实际在一把锁上排队。

## 决策

1. **会话复用**（`adapter/session_cache`）：操作结束不登出，把本 DMS 站点的 cookie 加密存进 Redis（键名为账号哈希）；下一次同账号操作先放回 cookie，用客户列表计数请求确认仍是登录态，是就跳过登录，否则清缓存照原流程登录。仍在账号锁内使用。技术故障、被顶下线时照旧登出并丢缓存。保留时长：管理员/系统账号 `pearnly_dms_session_idle_seconds`（默认 600），销售账号 `pearnly_dms_sales_session_idle_seconds`（默认 180，不超过前者）；前者为 0 即完全关闭复用，回到改动前行为。
2. **管理员锁用到才拿**：进入时只锁销售账号；真要管理员会话（`ensure_admin_session`）时才锁管理员。只用管理员的权威后台读取（`skip_sales_session`）只锁管理员。加锁顺序固定"先销售后管理员"，不形成环。
3. **建单不再为主档借管理员**：用户 2026-09-27 定"主档信息一般不会经常变来变去"。订车提交前的主档与收款银行复核改为对照**本地完整快照**（`booking_preflight.local_preflight`，由第 6 点的白天增量与凌晨全量保持新鲜），不访问 DMS、不占任何账号；选中车型已不在快照里仍按"主档已变"退回重选，颜色目录缺失明确报 `ERR_DMS_MASTER_UNAVAILABLE`。建单整段不再包在管理员会话里：客户资料卡、顾问组织先用销售会话实时读，销售读不到才借管理员（各自原有的回退）；需要改写客户档时的写入仍走管理员。查重本来就只读本地。
4. **本系统专用账号**（`adapter/admin_pool`，DocType `DMS System Account` 的 `purpose`；用户 2026-09-27 定）：
   - **读档账号**（一个）：**就是本站连 DMS 用的账号**（连接页上不再另有"连接账号"，`set_read_account` 同时写进公司连接，保存前按读档真试）。登记后所有后台读取只用它——每分钟同步、整组重读、首次读全档、凌晨回读（`operations.background_read_account` → `adapter.use_account`）。没登记读档账号的老连接不做白天同步，首次读全档也先不做，由凌晨全量用公司连接的账号读。
   - **改写账号**（若干）：需要管理员会话时（客户档建/改、权威读取）按轮转顺序试锁，谁空用谁；登记了就只用它们。一个都没有时，用公司连接复制到操作员连接上的那组（即读档账号）。读档账号不进这个池。
   - 连接页右上角只有两个按钮：「添加改写权限账号」（主，一行一个账号密码，「添加」加一行、每行可删）与「添加 / 修改读档账号」（次；没连上时是唯一按钮）；页面只列地址、读档账号、改写权限账号。LINE「进入 DMS」「修改账号密码」拒绝解析到公司连接（读档账号不能被人拿去登录网页或改密码）。
   - 登记前按用途真试（`adapter/account_probe`，强制真登、不复用缓存会话）：读档要能看使用记录、客户列表与客户资料，改写要能打开新建客户表单；缺哪项回哪项。操作员的销售账号、已登记的其他系统账号不能登记；改写账号也不能是读档账号。
5. **排队可见、超时可重试**：等账号锁期间每 20 秒续一次 LINE"正在输入"（免费）；等满仍拿不到报 `ERR_DMS_BUSY`（尚未提交任何内容，给重试按钮，订车同样允许重试），不再落成"服务器内部错误"。
6. **白天增量同步**（`adapter/live_sync`）：每分钟（`pearnly_dms_live_sync_seconds`，默认 60，0 关闭；会话复用关闭时也不跑）在白天窗口（`pearnly_dms_live_sync_hours`，默认 `6-22`，站点时区）用**读档账号**的复用会话跑一轮 `change_sync.catch_up`，走 `dms_sync` 队列、只读批次、去重。开着时，操作员那一笔不再在等待路径里顺手翻日志。
7. **白天不做大组整组重读**：日志点不出具体记录时，客户/地址只标记待重读，由凌晨全量读完后对账；车辆/公司等小组照常立即重读。
8. **被顶下线就退让**：缓存会话在期限内却已失效，视为有人正在网页上用同一账号，记 15 分钟；读档账号被顶掉时，这期间白天同步不为自己去登录，免得每分钟把那个人踢下线一次。
9. DMS bench 的 `scheduler_tick_interval` 由 `configure-dms-runtime.py` 设为 60 秒（其他产品 bench 不变），否则"每分钟"实际是每 240 秒。
10. **首次读全档不再干等**（用户 2026-09-27；ris 客户详情一次约 69 分钟、车辆约 10 分钟、公司约 8 分钟、地址 11 秒）：
   - 顺序：地址 → 客户 → 车辆 → 公司（各组分步、轮流推进）。
   - 客户组列表阶段读完（ris 约 150 页）就先发布**客户索引** `customer_index`（编号/客户码/姓名/证号 + 称谓），查重立刻可用；`Directory` 在完整客户组发布前用"索引 + 已核实写回"作答：查无此人直接答，查到但详情未读 → `CustomerDetailPending`，由 `snapshot_writeback.with_customer_detail` 单独读这一条（权威会话，约 1–2 秒）写回后重答。完整客户组发布后照旧优先用完整的。
   - 读取进度带 `usable`：连接页的遮罩在各组可用时就放开，客户详情在后台读完。
   - 触发：绑定（`save_connection`）与登记读档账号（`set_read_account`）都调用 `bootstrap`，**缺哪组读哪组**；没登记读档账号返回 `awaiting_read_account`，页面提示先添加。
11. **缓存键不含密码**（`store.scope_identity`）：同一账号只改密码不重读；换账号才是另一份资料。上线时一次性补丁 `snapshots/scope_rekey` 把现有资料按旧键（含密码）改挂到新键，不让所有租户重读；密码改对后由 `store.clear_authorization` 清掉旧的"认证被拒"记号。

## 边界与风险

- 复用期间账号保持登录。人如果同时在网页上用同一个账号会看到重复登录提示，并顶掉系统会话（系统下次自动重登，又会顶掉他）。2026-09-27 测试机写入实验确认：DMS 的页面/表单流程会把同账号重复登录踢下线。所以系统专用账号只给系统用；有人在网页上用的连接账号，靠登记读档与改写账号让系统白天不再占用它。
- 登记时的按用途试读只覆盖关键几项；整组重读涉及的全部主档（员工、收款银行等）读不到时，会在连接页的读取状态里失败显示。
- DMS 服务端会话超时长于实测上限前，缓存期限应保守；存活检查兜住过期，最多白花一个请求。
- 建单另有按 DMS 地址的全局锁（防单号撞号），多人同时建单仍会排队；本 ADR 只缩短每人占锁的时间。
- 没有 API/变更推送时，白天同步把延迟压到约一分钟，不是实时；提交前实时复核仍是最终保障。
