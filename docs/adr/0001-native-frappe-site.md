# ADR-001 采用 Frappe 原生 Site 承载产品租户

状态：已选定（用户确认 2026-09-17）。实施细节待 P1 记录。

## 背景

现有系统是 FastAPI + 原生 JS/Vite + 外部 Postgres 的单体应用，身份、路由、数据库连接与后台开户都在同一进程里，缺产品级隔离。需要让"新增客户、新增产品、新增功能"有固定流程。

## 决策

采用 **Frappe 原生 Site** 作为产品租户载体：

1. 公司 × 已开通产品 = 一个独立 Site，各带独立域名、会话、数据库与文件。
2. 三产品分 Bench 运行组（Cowork / ERP / DMS），组内多租户共享进程，但库与凭据独立。
3. 统一后台 `pearnly_control` 只装控制 Site，且**只在本机运行**（见 ADR-004）。
4. 用户已明确接受因此产生的底层改造。

## 被否的方案

在现有 FastAPI 上做多数据库 + 固定 DSN 部署。曾被评估为"最小改动"，但它把隔离压在应用层，无法解决每租户独立数据库、独立文件与框架级权限；只作为比较过的备选。

## 后果

- 必须把 psycopg2 与全局连接池改为 Site 内数据访问；Postgres 的 JSONB、FILTER、数组、UUID、UPSERT、锁与事务语法要逐项处理，**不能只换 DATABASE_URL**。
- 必须建薄公共 App 复用框架的 Session、User/Role、DocType、迁移与后台任务。
- 现有前端、纯业务计算与映射函数保留，用适配层包住身份与基础设施。
- 迁移期不得同时存在旧 FastAPI 与新 Frappe 两套权威。
