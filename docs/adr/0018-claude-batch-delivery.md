# ADR-018 Claude 批处理识别：预填检查点，识别仍走实时同一条路

- 状态：已采纳（2026-10-07）。用户：「cowork 这边的另一个新窗口的功能要走批量，你只管建好 claude 这边，谷歌那边先暂时不管」。
- 依据：[ADR-017](0017-ocr-engine-claude.md)「扩展点」（批处理复用同一份请求体与解析，执行方式由入口在受理时冻结）；
  Anthropic Message Batches：同价减半，多数一小时内、最长 24 小时出结果，支持看图与提示词缓存。
- 关联工作包：[Claude 识别引擎](../work/2026-10-07-claude-ocr-engine.md)

## 问题与约束

- 文件夹自动录入这类入口不急，可以等几十分钟换半价；网页上传仍要实时。
- 不能另起一套识别：检查闸、入库、复核、推送、扣费必须与实时同一份代码，结果不能因交付方式不同而不同。
- 不能动 Core 的排队与过期规则：识别工作单进了队列就占租户在途名额（50），排队超过时限会过期；批处理要等几小时。
- 付费防重照旧：同一页不付两次；结果不明不重交。

## 决定

1. **入口**：`ocr.execution.service.submit(..., delivery="batch")`。只有冻结的引擎是 Claude、原件是图片 / PDF 才真走批处理，
   其余（谷歌引擎、Word / Excel 表格）照旧实时，调用方不用先判断。冻结配置照常写在识别单上；阶段 `batch_waiting`；
   **先不建工作单**。识别单新增字段 `delivery`（不可改）与 `provider_batch`（批号、请求键、进度）。
2. **收集**（`ocr.execution.batch.collect`，后台任务）：用识别单上冻结的配置在本机跑一遍引擎（`workflow.run_local`，与实时
   同一段），Claude 请求只收集不发出：`AnthropicClient.batch_entry` 给出与实时调用**完全相同的检查点键**和请求体；
   要调谷歌（读字 / 模型）的直接退回实时。以检查点键作 `custom_id` 交一批（`providers.anthropic_batch`，纯协议层）。
3. **推进**（`batch.tick`，每 5 分钟，hooks `scheduler_events`）：批次结束后把成功的结果按键写进这份识别（尚未建的）工作单的
   检查点（Core `work.checkpoint`，与实时写检查点同一个入口），再建工作单（`service.enqueue_work`）。
4. **识别**：工作单照常跑；批处理交付固定在本机执行（检查点在本站，不交 Cloud Run、不回放），每页发同一个请求时直接从
   检查点取回、不付费。没拿到结果的页（出错 / 过期 / 取消）在这一遍里照常实时调用，按原价。
5. **退回实时**（直接建工作单）：不能出批、收集失败、提交被拒、提交结果不明且过了 30 分钟（不重交，免得交两批）、
   超过 26 小时还没结束。建工作单时队列满就留在等待里，下一轮再建。
6. **计量**：批处理结果的用量带 `service_tier=batch`，`engine.cost` 按半价算。

## 选项

- 让 Core 的工作单支持「挂起几小时」：要改共享排队、过期与名额，影响三个产品，不采用。
- 在 Cloud Run 上收集与完成：检查点在谷歌存储桶，预填要跨两边；批处理不急，本机最后一遍不调模型，压力很小，不采用。
- 自己存请求体、结果回来自己拼结果：等于另写一条识别路线，结果可能与实时不同，不采用。

## 后果

- 调用方（文件夹自动录入）只多一个参数；进度看识别单状态：先 `batch_waiting`，之后与实时相同。
- 收集与完成各在本机渲染一遍页面（不调模型）；生产服务器多一点 CPU，换来模型费减半。
- 代码在两次之间升级、请求体变了：键对不上，那几页改走实时（多花钱、结果照样对），不会读错。
- 谷歌引擎没有批处理（用户 2026-10-07：先不管）。
