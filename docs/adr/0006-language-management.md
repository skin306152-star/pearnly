# ADR-006 语言管理：跟着账号走，缺译错译要纠正

状态：已选定（用户 2026-09-18 定："新租户默认泰语"、"缺的错的要纠正"、
"新功能以后再说，做新功能就补"）。

## 背景

三个产品 + 控制面要给中文与泰语用户用，登录页也要多语言。旧系统确实已经有一套词典，
但它解决不了新架构的问题。核过的现状：

| 现象 | 证据 |
|---|---|
| 各模块各管一套词典 | `static/{landing,dms,ai,daily,admin}/…-i18n*.js` 各一份，另有 `landing-tour-i18n.js` |
| 默认语言不一致 | 主站 `landing-i18n.js:368` 与 DMS 都硬编码回落 `'th'`，而 DMS 页面本身是中文 |
| 语言靠浏览器共享 | 都读写同一个 localStorage 键 `mrpilot_lang` |

**第三条在新架构上直接不成立**：Cowork / ERP / DMS 各是一个子域名，
而 `localStorage` 按域隔离、不跨子域共享。旧系统能用是因为当时同域。
所以"语言选择"必须跟着账号走，浏览器只能当本地缓存。

## 决策

### 1. 默认语言：租户默认泰语

| 位置 | 默认 | 说明 |
|---|---|---|
| 租户登录页（`pearnly-business`） | **泰语** | 租户可在登录页自己切，切换结果记在账号上 |
| 控制面登录页（`pearnly-platform`） | 中文 | 只有本人用（ADR-004） |
| 租户站点（前台与后台） | **泰语** | 开通参数 `pearnly_default_language` 可按租户覆盖 |

### 2. 取值顺序：照两个框架的既有规则，不自己造一套

登录页（身份服务）：**账号已选语言 → 浏览器能匹配上的语言 → 租户默认（泰语）**。
实测：泰语/中文/日语/英语浏览器各看各的，法语这种匹配不上的才回落到泰语。

租户站点（Frappe）：`_lang` → cookie → `Accept-Language` → 用户 → 系统
（顺序取自框架自己的文档字符串，`frappe/translate.py:33`）。

两边共同的实质是：**登录之后一律跟账号走**。所以账号上必须存得住语言偏好
（身份服务用用户 locale，Frappe 用 `User.language`），不能只存在浏览器里。

**补充（2026-10-13，对话页 CC）**：界面默认跟这台设备的语言。泰文 Windows 的新电脑，登录页按系统语言显示泰文，
登录后整页却是账号里以前存的中文，用户要的是泰文。对话页的语言因此按一条规则定（`pearnly_core/account/ui_language.py`）：
在这台设备上自己选的（对话页「语言」、登录页上点的）→ 这台设备第一次登录时登录页显示的语言 → 这台设备记住的 →
账号语言 → 系统语言 → 英文。前两种记在本站的 `pearnly_locale`（这台设备）并照旧存成账号语言，
所以后台发的提醒、简报、LINE 仍按账号语言，与这台设备一致；对话页的请求带着页面当前的语言（请求头 `X-Pearnly-Lang`）。
后台（Desk）页面不变，仍跟账号。

### 3. 每一层的文案放在哪

| 界面 | 方式 |
|---|---|
| 业务页面（Vue，见 ADR-005） | Vue I18n，按产品、模块划分语言资源 |
| Frappe 原生页面 | 用框架自带的翻译机制；v16 新增翻译优先 PO |
| 登录 / 忘记密码 / 改密（身份服务） | 主题的 `messages_*.properties`，四语各一份 |
| LINE 消息、邮件、报表 | 服务端语言模板，发送时明确"这份要哪种语言"；不沿用管理员语言 |
| ~~WeKan~~ | 已不再迁移（2026-09-21 用户决定，后期自行开发），无语言包事项 |

统一的不是文件格式，而是**术语**与规则：同一个概念（账套、过账、提交）在四个界面里
用同一个词。各框架用自己的标准格式（Vue I18n 用 js，Frappe 用 PO，Keycloak 用
properties），不强行统一成一个文件。

### 4. 缺译与错译：不许静默

用户要求"缺的错的要纠正"，落成三条硬规则：

1. **缺译不许静默降级**：不能让中文用户看到英文，更不能把键名（`pearnlyLoginBtn`）
   当文案显示出来。缺了就补，补不了就报出来。
2. **复用的键必须四语都准确**：要是某个语言下是空的或译得不对，就得自己写，
   不能"借来用"。
3. **新功能在开发时补齐四语**，不留到"以后统一补"。

### 5. 能复用框架标准键就复用，译得不准才自建

判定规则：Keycloak 标准键在该语言下**有译文且语义准确** → 直接用；
**缺失、空白、或语义不准** → 自建。

本轮实际判定（都有出处，不是凭感觉）：

| 键 | 判定 | 依据 |
|---|---|---|
| `passwordNew`、`passwordConfirm`、`logoutOtherSessions` | **复用标准键** | 四语译文都准确（少维护 12 条） |
| `updatePasswordTitle` | 自建 | 泰语译成 "ปรับปรุงรหัสผ่าน"，语义是"改进密码"，不准 |
| `doSubmit` | 自建 | 泰语是 "ส่ง"（发送），而这个页面是"保存" |
| `showPassword` | 自建 | 泰语译文是**空的** |
| `traceIdSupportMessage` | 自建 | 只有英文，中文/泰语/日语都是空的 |

## 本轮实际做了什么

### 默认泰语

| 改动 | 文件 |
|---|---|
| 租户 realm 默认语言改泰语、控制面保持中文，并写成可重复执行的脚本（原来是敲 API 设的，仓库里没记录） | `scripts/sample-configure-login-theme.sh` |
| 开通收尾把站点语言设成租户默认语言 | `apps/pearnly_core/pearnly_core/provisioning.py` |
| 新建账号带上租户默认语言 | 同上（`ensure_local_user`） |

只在**新建账号**时设语言：已有账号不覆盖，否则重跑开通会把用户自己在界面上改过的
语言顶回去。控制面刻意不受影响（靠 `pearnly_product` 区分，实测控制面语言仍为空）。

### 纠正缺译与错译

| 问题 | 处理 |
|---|---|
| 日语"重置密码"页两处是我抄写时改写的，与旧页原文不一致 | 改回原文（`登録メールを入力してください。再設定リンクを送信します。` / `送信`） |
| 自建了 3 个标准键已有的条目 | 改用标准键，删掉自建的 |
| 泰语缺 `showPassword`、三国语言缺 `traceId` 提示 | 自建补齐 |
| **语言切换的"当前选中"高亮从来没生效过** | 修好（见下） |

### 顺带修掉的一个静默 bug

语言切换的"当前选中"高亮**一直是失效的**：原写法拿字符串去比 Keycloak 的 Locale
对象，两边类型不同恒为 false，四个标签永远都是空 class —— 页面上完全看不出来。
中途我改成 `l.active` 又把页面打成 500，因为这个版本的 `LocaleBean$Locale`
（`org.keycloak.theme.beans`）只有 `languageTag / label / url` 三个 getter，没有 `active`。
正确写法是 `locale.currentLanguageTag`（`LocaleBean` 上确实有这个 getter）。
现在验证脚本里有专门一条盯着它，包括五种浏览器语言下的表现。

## 验证

`scripts/sample-verify-login-theme.mjs` 共 **36 项，全部通过**。与语言相关的：

| 项 | 验到了什么 |
|---|---|
| 语言标签顺序 | 「中 / TH / EN / 日」四个短标签，悬停显示完整名字 |
| 切换语言 | 切英文/泰文，标题真的变，切回中文正常 |
| **默认语言** | 泰/中/日/英浏览器各看各的，匹配不上的回落到泰语 |
| **当前语言高亮** | 五种浏览器语言下，高亮项与页面语言一致 |
| 忘记密码页 | 与登录页同一套外壳，且按当前语言渲染 |
| 租户站点语言 | 开通收尾后 `System Settings.language = 'th'`（回读确认） |
| 新账号语言 | 新建账号 `User.language = 'th'`（回读确认，探针账号已删） |

## 被否的方案

**把语言只存在浏览器里**（旧系统的做法）。子域名架构下不成立：三个产品各自一个域名，
`localStorage` 不共享，用户在 Cowork 选了泰语，进 ERP 又变回默认。

**缺译时用英文兜底。** 中文与泰语租户会突然看到一句英文，用户已经把这条定为"要纠正"的
问题。缺译必须补，不能靠兜底掩盖。

**另起一套统一翻译平台 / 每次打开页面调 AI 翻译。** 不需要：初期语言资源随代码走即可，
不增服务器、不依赖外部服务，也避免每次打开页面都产生一次外部调用。

## 后果与约束

- **语言偏好是账号数据**，不是浏览器数据。身份服务与 Frappe 侧各存一份，
  登录时以账号为准。
- **前端 i18n 框架还没建。** ADR-005 的 Vue 工程还没起，所以"业务页面用 Vue I18n"
  目前只是一条方向；现在真正齐的只有登录主题这一层。
- **术语表还没建。** 跨四个界面的统一用词（账套、过账、提交…）需要一份对照表，
  这是下一步的事，本轮没有编。
- **翻译完整性检查还没接进发布闸门。** 现在只有登录主题能靠验证脚本兜住；
  Frappe 侧的 PO/CSV 与业务页面的词典还没有检查手段。
- **日期、时区、泰国佛历是另一件事**，不在本决策内。
- 切换语言**不改业务数据**：客户名称、发票原文、账套币种不随界面语言变化。

## 边界（明确没做）

- 没做按租户逐个指定语言的开通界面：现在只有默认值 + 站点配置可覆盖。
- 没做"发送 LINE 消息时用收件人的语言"：那属于消息模板，随对应功能一起做。
- 没做手机号登录（身份服务原生不支持，不另造）。
