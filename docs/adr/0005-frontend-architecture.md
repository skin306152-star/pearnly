# ADR-005 前端架构：Frappe 原生后台打底 + 新建业务页面用 Vue 3

状态：已选定（用户确认 2026-09-18）。具体依赖版本在样板验证后锁定。

## 背景

后端已按 ADR-001 落在 Frappe 原生 Site 上：公司 × 产品 = 一个 Site，
各有独立域名、会话、数据库与文件。但**产品自己的界面还没建**——
三个产品 App 里前端文件是 0，租户登录后看到的是框架 Desk 加一个过渡工作区。

同时旧系统有一套成熟业务界面（`pearnly-app` 的 `src/home/` 253 个文件、
`static/` 90 个），是**TypeScript + Vite**（不是原生 JS），调的是旧 FastAPI 接口。

需要定的是：新业务界面用什么技术、放哪里、怎么访问、和框架自带界面什么关系。

## 决策

### 1. 技术栈

| 部分 | 选择 |
|---|---|
| 新业务页面 | **Vue 3 + TypeScript** |
| 构建 | **Vite**（打包成静态文件，不做常驻 Node 服务） |
| 基础组件 | **Frappe UI**（官方组件库，本身就是 Vue 3 + Tailwind，与后端同源） |
| 导航与公共状态 | Vue Router；必要时 Pinia |
| 多语言 | 统一翻译机制，中/泰等文案集中维护 |
| ERPNext 原生表单与报表 | **保留 Frappe Desk 原生组件** |
| WeKan 看板 | **保留 WeKan 自身前端**，作为 Cowork 内部功能接入，不重写 |

选 Vue 的理由是与 Frappe 生态贴合：Frappe UI 是 Vue 3 组件库，不用自研一套。

**Frappe UI 与 ERPNext 原生 Desk 是两套界面体系**：可以统一品牌、语言与使用习惯，
但**不把两边的 CSS 混在一起**（混了以后两边升级都受制）。

### 2. 四个独立入口

| 地址示例 | 用户看到的 | 进入哪里 |
|---|---|---|
| `a-cowork.pearnly.com` | Cowork 工作台、看板入口 | A 公司的 Cowork Site |
| `a-erp.pearnly.com` | ERP 经营页面 | A 公司的 ERP Site |
| `a-dms.pearnly.com` | DMS 页面 | A 公司的 DMS Site |
| 控制面 | 平台开户、功能与租户管理 | 独立控制 Site，**只在本机运行** |

⚠️ **控制面没有公网域名**。这是 ADR-004 的硬约束：控制面只在本机跑、只做开户与授权、
仅本人使用；云上只跑三产品 Site、Keycloak 与 WeKan 实例。控制面里存着开户凭据，
不能暴露到公网。

同一个产品的不同租户**复用同一份前端程序**；新增公司只增加 Site 与开通配置。

### 3. 代码组织

仍在本仓库内：

- 每个产品维护自己的页面、业务组件与接口调用；
- 按钮、弹窗、翻译、错误处理放**公共库**；
- 公共库**不保存全平台账号会话，也不直接访问其他产品的数据**。

### 4. 必须统一的几条规则（不只是外观）

1. **登录统一、会话分别建立。** 同一个业务账号可进入已开通产品；管理后台身份独立；
   浏览器不保存一个能通行所有产品的万能令牌。
2. **页面与接口同域名。** 页面用相对地址请求本站接口；由服务器确认域名对应哪个 Site，
   前端**不能**自己指定租户。
3. **功能与权限由后端决定。** 前端按后端返回的授权渲染菜单；直接调接口、下载附件、
   导出数据同样要检查权限（P4.04 已把功能门禁做在后端）。
4. **账套切换必须完整。** 切换时取消旧请求、清空旧账套缓存；提交时后端再次核对账套。
5. **文件、消息与缓存同样隔离。** 上传、预览、实时通知、LINE 打开的页面，
   都带正确的产品与租户边界。

### 5. 登录页：统一用现有的"猫"那套设计

三个产品入口共用同一个登录页，视觉用旧系统那套设计（用户 2026-09-18 确认）。

**做法：给身份服务（Keycloak）做自定义主题**，不是搬一个独立页面。

为什么不能把旧页面原样搬过来自己收密码：登录只走**授权码 + PKCE**（P2 合同），
密码必须在身份服务那里收。自己收密码就得走"密码直传"那条我们特意避开的路径。

代价与边界：

- Keycloak 登录页是服务端渲染，搬的是**视觉与结构**；页面里原有 JS 逻辑
  （语言切换、弹窗）要按其方式重做。
- 旧的"通过邮箱链接登录"按钮**不要**（已按用户要求关掉）。
- 旧背景图偏大（桌面 5.5MB、手机 4.1MB），搬迁时压缩。

### 6. 施工顺序

1. **列页面清单与对应接口**：含手机页面、LINE 入口、文件预览、导出与管理员页面，
   明确每页归属。
2. **先做一条完整样板**：发号 → 登录 → 选账套 → 一笔真实业务操作 → 退出 → 权限拒绝，
   验证前后端合同。
3. **现有页面先接新后端**：保留有效交互，替换身份、接口与账套上下文；
   已可用的原生 Frappe 页面继续保留。
4. **新功能与需整理的页面统一用 Vue**：按业务模块逐批替换，验收一批迁一批，
   **避免长期维护两份相同页面**。

## 被否的方案

**让租户直接用 Frappe Desk 当产品界面。** 省事，但把框架后台暴露给租户
（DocType 列表、字段表、系统设置不是客户该看到的东西），而且旧系统那套专门为业务
做的界面（录入工作台、识别记录、对账中心）重建一遍纯属浪费。
Desk 现在只是**过渡落点**，不是终态。

**重写全部页面。** 与计划"保留业务功能和界面"冲突，且返工量最大。

## 后果与约束

- **不新增服务器**：Vue 在本地或 CI 打包成静态文件，由现有服务器的 Nginx 提供；
  不为四个前端各常驻一套 Node 服务。
- **"现有页面先接新后端"是实打实的工作量**，等于计划里的 P3.05（前端兼容 API）：
  旧页面调的是旧 FastAPI 接口，接新后端要么做兼容适配层，要么逐页改接口。
  这部分不能按"顺手改改"估。
- **前端不能作为权限边界**：所有检查以服务端为准（P4.04 已建立）。
- **范围不含 POS**：收银台 POS、AI 管家、Daily、会计、工单、报税、工资、
  邮件接入、Excel 对账内测均已明确不迁移；本决策不涉及它们的页面。
