# ADR-022：Claude 识别路线（按租户选择，与谷歌路线互不牵扯）

- 状态：已采纳（用户 2026-10-17：「可以上线，这个项目只是 Claude，不要和谷歌牵扯；后台管理有自由调配模型识别 Google 或者 Claude 的选项，
  每个租户可以自定义，开户也可以自定义选择，选 Claude 后就走今天这套规则逻辑，要适用于三个产品」）。
- 取代：ADR-017（Claude 识别引擎）/ ADR-018（Claude 批处理交付）保持已废止，不恢复它们的做法。

## 背景

10-07 Claude 输给谷歌（字段读错 5.7% 对 2.1%），主因是照搬给谷歌调的提示词、录不录口径没写、读不准不复核。10-17 在甲骨文重测
（记录：`docs/work/2026-10-17-claude-ocr-route.md`）：Claude 专用提示词 + 只按硬性自检升级的 Haiku→Opus 分级，三组真实单据合计
字段读错 1.62%（不计册号口径约 1.32%），每页 ฿0.09–0.19，识别段中位约 5 秒；非票据几乎不会被录。

## 决定

1. **两条路线互不调用。** 站点配置 `pearnly_ocr_engine` = `google`（站点上未设时）或 `claude`；控制面租户与开户单的默认值 2026-10-18 起是 Claude（用户：新开户默认走 Claude），所以新开的站点都写 `claude`。选 `claude` 的租户，识别全程只调 Anthropic：
   不调 Vertex / Vision / Document AI，失败也不转谷歌；谷歌路线代码一行不改。
2. **一套引擎、三个产品的全部识别入口。** 选 Claude 的站点：Cowork 录入（图片 / PDF、Excel / Word 表格按逻辑页文字）、销项税核查的发票、
   对账三类文档（银行账单 / 总账 / 销项税报告，扫描件与照片逐页读，结果按原企业档格式拼页，下游对账不动）；ERP 采购 / 销售（含 LINE）；
   DMS 身份证。**硬闸**：付费谷歌调用的两个出口（共用层 `provider.post`、Cowork 交 Cloud Run 的 `forward`）对选了 Claude 的站点一律拒绝
   （`GoogleRefused`），漏接的入口当场报错、不会悄悄走谷歌；源码守卫（`tests/test_claude_ocr_rules.py`）要求每个调谷歌识别的入口都先看路线。
   识别前与谷歌路线同一个本地转正（`ocr_models.orient`）。文件存储与浏览器直传（原件桶、Cloud Run 读页数 / 出预览）不是识别，不在此列。
3. **一套引擎、三个产品共用。** `pearnly_core.claude_ocr` 是纯计算包（不导入 Frappe、不读站点配置）：Claude 专用提示词与结果格式
   （发票类 `voucher`、身份证 `id_card`、对账的银行账单 `bank` / 总账 `gl` / 销项税报告 `vat_report`）、硬性自检、Haiku→Opus 分级。产品各加一个分支：当前站点选了 `claude` 就调
   `pearnly_core.claude_ocr.client`，再把结果转成自己原来的格式；扣费、存档、推送、复核下游不动。
4. **分级规则（改动须过金标闸门）。** Haiku 5.5（effort low）先读；以下任一条成立交 Opus 5.5（effort low）重读，并告诉它哪些字段
   可疑：泰国税号校验位不对；未税额 + 税额 ≠ 合计（含税小票未税额 = 合计算正常）；录入的票缺单号 / 日期 / 合计；3 页及以上的单据读出的
   票数少于页数。读出的税号与本公司税号只差 1–2 位时改成本公司的。不按模型自标的「不确定」升级。身份证：身份证号校验位不对、缺号码
   / 姓名 / 生日时交 Opus。对账文档一页一读：银行账单余额链（新的在前、旧的在前都认）、总账余额走向、税报每行未税 + 税额 = 合计与税号
   校验位，不过交 Opus；页上没印期末行时取最后一行印的余额，总账第 1 页漏读期初时按第一笔印的余额与借贷倒推（只用印出来的数）。
5. **运行位置。** 甲骨文 free-arm 常驻 `claude-ocr` 服务（无冷启动、到 Anthropic 3 毫秒、与 Anthropic 保持长连接），生产经 HTTPS 直连
   （只放行生产 IP、钉死证书指纹、带令牌；不走 Cloudflare：免费版把生产送到东京 / 巴黎边缘，见 2026-10-17 服务器改造记录）。甲骨文
   连不上时生产本机用同一份引擎直接调 Anthropic（每次调用多约 0.25 秒），仍是 Claude 路线。Anthropic 故障按工作单现有重试排队。
6. **选择入口。** 控制面租户页面与开户表单各一个「识别引擎」选项，保存后经现有队列写入租户站点的 `pearnly_ocr_engine`；下一份单据起生效。
   这是识别通道的运行配置（登记在 `architecture-policy.json` 的站点配置表），不是功能开关；售卖与扣费不变（按页）。
7. **缓存与成本。** 系统提示词走 Anthropic 提示缓存；每次调用的用量与估算成本记进识别结果，`engine.cost` 登记 Haiku / Opus 5.5 价目（只用于估算）。

## 上线闸门

1. **走产品正式代码**重跑语料（`scripts/claude-ocr/run-gate.sh`：原件 → 上传检查 → 产品入口 → 存档前最后一步 / 对账配对，读法经甲骨文
   服务，与生产同一条路）：金标、SM 热敏小票、Express 账按原打分口径，与谷歌**生产记录**同口径比；对账按账单 + 总账配对出的结果比；
2. DMS：从生产取真实身份证件小批量测；
3. 测试环境实测从上传到出结果的速度；
4. 一个内部租户试用，再按批次部署。

## 不做

- Claude 路线内转谷歌兜底；按页混用两家；批处理半价接口（实时受理用不上）。
- 把各产品现有的谷歌提示词直接交给 Claude（10-07 失败原因之一）。
