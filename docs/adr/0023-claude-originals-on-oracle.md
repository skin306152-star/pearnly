# ADR-023：选了 Claude 识别的租户，Cowork 原件存甲骨文

- 状态：已采纳（用户 2026-10-18：「原件直接放甲骨文，数页数和预览也在甲骨文做」；「当初就是生产服务器满足不了并发才发谷歌的，
  所以不要再给生产服务器增加或者退回什么东西了」）。
- 关联：ADR-016（原件直传谷歌存储，谷歌租户照旧）、ADR-022（Claude 识别路线）。

## 决定

1. **范围**：站点选了 Claude 识别（`pearnly_ocr_engine = claude`）时，Cowork 录入台直传的原件（PDF / 图片）存甲骨文 free-arm，
   上传后核对（类型、页数、sha256，与服务器收原件同一份 `ocr.originals.inspect`）、预览渲染（同一份 `render_page`）、下载都在那台。
   不在范围（与 ADR-016 相同，照旧在服务器）：表格 / Word 原件、LINE 收到的原件、对账中心的临时文件。谷歌租户行为不变。
2. **生产不经手原件字节**：浏览器经 `originals.pearnly.com`（Cloudflare 隧道，泰国落曼谷节点约 10 毫秒；甲骨文不对外开端口）
   直接 PUT / 取预览 / 下载；生产只做权限、幂等、记录、访问日志、签地址（HMAC-SHA256，生产与甲骨文同一把密钥，签进方法、对象名、
   过期时间与大小 / sha256 / 文件名 / 页码；上传 15 分钟、下载与预览 5 分钟）。识别交对象名与 sha256，甲骨文自己读文件、转正、
   渲染、交 Claude（`claude_ocr.client.read_original`）。生产到甲骨文的内部调用（核对、删除、取回、识别）走 8443（只放行生产 IP、
   钉死证书指纹、带令牌）。
3. **甲骨文连不上**：上传确认回 `retry` 让页面过几秒再来，识别按工作单重试；**不退回生产存**。（没配甲骨文原件存储的 Claude 站点
   照旧经服务器上传，这只是没配置时的样子。）
4. **记录**：`storage_url` = `oracle://<站点>/originals/<原件名><扩展名>#<sha256>`；同一对象只写一次（写过回 412）；预览按
   `<站点>/previews/<原件名>/v<画法版本>-<sha 前 16 位>-p<页码>` 存下，下次直接给。删票后原件与预览一起删（后台任务）。
5. **部署**：`scripts/claude-ocr/deploy.sh`（同一个容器：识别 + 原件服务，`infrastructure/claude-ocr/serve.py` 把共用层与 Cowork 的
   纯计算模块拼起来，内存 4g，原件目录 `/opt/pearnly-originals`）、`scripts/claude-ocr/tunnel.sh`（隧道）；生产 runtime.env 加
   `PEARNLY_ORIGINALS_PUBLIC_URL`、`PEARNLY_ORIGINALS_SIGNING_KEY`。

## 代价与风险

- **单点**：原件只在甲骨文一块盘上（谷歌存储有多副本与 7 天软删除）。那台按「可能失联」设计，磁盘坏了原件就没了 —— 需要另做备份
  （待定：甲骨文免费的卷备份，或定时复制到别处）。
- 容量：那台 193G 盘剩约 177G；全平台现有直传原件 308 MB（大多是测试租户）。4 核 24G，核对约 0.01–0.2 秒、预览首画约 1 秒
  （之后 0.002 秒），同时渲染 / 核对限 3 份。
