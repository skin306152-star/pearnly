# ADR-013 识别读法：便宜模型读、代码兜底、按需复核，默认不用 3.8

- 状态：已采纳（2026-09-27，用户：「按这个方案施工，先做 ERP，3.8 开关保留默认关」）
- 范围：ERP 采购 / 销售识别（`pearnly_erp_portal.recognition.policy`、`purchasing.recognition`）；共用层新增
  `pearnly_core.ocr.text_from_image`、`ocr.labels`、`ocr.orient`。
  Cowork 发票识别（`pearnly_cowork.ocr.engine.runner`，含对账中心的发票核对）2026-09-27 起按同一套先后执行，见下文「Cowork」
  （用户：「cowork 那边只改读票和转正，对账不动」「由你来改造 cowork」）
- 依据：[OCR 语料实测](../work/2026-09-27-ocr-corpus-eval.md) 第 8 节；评测脚本 `scripts/ocr-policy-bench.py`、`ocr-vision-bench.py`、`ocr-policy-report.py`
- 关联：[ADR-012 票种决策表](0012-shared-tax-document-rules.md)

## 问题

旧线上的读法：`gemini-3.1-flash-lite` 读一次，过不了硬闸整张升 `gemini-3.8-flash` 重读。
用户实测觉得 3.8 又贵又慢：3.8 的输出单价是 3.1 的 5 倍，思考 token 也算输出，一次要 7–20 秒。

## 实测（194 张金标，每种读法都真调一次，离线组合）

语料：真实小票 32 张、同批退化照片 64 张、Sister Makeup 真实采购税票 9 张（MR.ERP 答案）、拍照级合成压力集 89 张。

| 读法 | 金额 + VAT + 进项全对 | 错了没标红 | 每张原价 | 平均 / P95 |
| --- | --- | --- | --- | --- |
| 旧：3.1 → 整张升 3.8 | 170 | 8 | ฿0.176 | 7.4 / 15.3 秒 |
| 3.1 只读一次 | 165 | 4 | ฿0.053 | 4.2 / 6.3 秒 |
| 3.1 → 3.1 带提示复核 | 169 | 4 | ฿0.068 | 5.1 / 8.2 秒 |
| 3.1 双读投票 | 166 | 1 | ฿0.094 | 4.3 / 6.3 秒 |
| **新：3.1 + 代码修复 + 按需复核 / OCR 核对** | **171** | **5** | **฿0.089** | **5.7 / 9.4 秒** |

- 3.8 只在两张真实采购税票上胜过 3.1，这两张用代码也能修好：
  - 反推漏读的整单折扣。
  - 用 OCR 原文确认买方是本公司。
- 在退化照片和压力集上，3.8 没有提升；「错了没标红」反而更多（它的错误读数更容易蒙混过检查）。
- 剩下的错主要是严重退化的照片，所有读法都一样错。

## 决定

1. **首读**：`gemini-3.1-flash-lite`，思考 MINIMAL。PDF 自带文字层时只传文字。
2. **代码修复**（确定性、免费），在各产品的 `structured` 里做：
   - 数量为空按 1 件。
   - 折扣行并入整单折扣。
   - 预扣税、不可抵扣 VAT。
   - 票种按决策表。
   - 反推漏读的整单折扣：只在票面 VAT 能独立印证折后金额时才采用。
3. **只在金额 / 结构对不上时重读**（`checks.reread`）：
   - 用同一个便宜模型，带上第一次的读数和没过的检查，思考调高一档（LOW），看原件核对一次。
   - 复核没有改善就保留第一次的读数。
   - 税号校验位、贷项通知单、票种 / 进项原因、日期软标注都**不重读**，只标红。
4. **按需 OCR 核对**（采购）：只在「税票没写买方」或「税号校验位不过」时调一次 Vision 取原文。
   - 本公司税号出现在原文里 → 确认买方是本公司。买卖读反时，把本公司税号挪到买方。
   - 按校验位找回读错的税号；找回只差一位的票面金额。
   - **每一处改动都要让检查问题变少才采用**。
   - 单号、日期无法用检查验证，不改：实测「原文里只差一位就替换」会改坏。
4b. **复核后仍对不上，按 OCR 原文再读**（2026-09-27 补强）：单张图片时调一次 Vision 原文，「原图 + 原文」一起给 3.1 再读。
   同一次识别里 Vision 原文只取一次（`ocr.text_from_image` 有缓存），核对阶段复用。
   依据是与 Cowork 现方案的 18 张对比：明细密集的税票（NBC 逐行折扣）看图读不对，Cowork 靠原文读对了；
   单独试验时，「原图 + 原文」对 NBC 和 Giffarine 两张都读对、检查全过，只给原文仍有对不上的。
4c. **识别前本地转正**（`ocr.orient`）：先按 EXIF 转正；再用 PaddleOCR 方向分类模型（Apache-2.0，6.8 MB ONNX，onnxruntime 跑在 CPU 上，约 15 毫秒一张），
   沿长边取三块，三块判断一致、且平均概率 ≥ 0.9 才转。
   离线实测（37 张 × 4 个方向）：正常照片误转 0；歪的小票转对 67/96、转错 0；A4 整页照片多半不动。
   Pillow 投影法与按长宽比过滤实测都不可行（手机照片几乎都是 4:3）。
5. **3.8 只作站点开关**：`pearnly_erp_ocr_escalation = {"model": "gemini-3.8-flash", "min_total": 50000}`。只对仍需重读、且票面合计不低于下限的单据升级。**默认没有这项，不升级。**
6. 还不过就标红交人工，不再花钱硬读。
7. Vertex 请求带账单标签（tenant / product / task / stage），结算报告可以按租户、产品、步骤分组。

## Cowork

识别结果的格式、对账、VAT 核对、历史、计费、断点续跑都不变；变的只有「怎么读」。

- 每页图片：3.1 直读（**精简看图提示词** `IMAGE_SYSTEM`，MINIMAL）→ 没过原直读闸（缺合计、金额对不上、合理性）就同一模型
  带提示复核（`RC`，不开思考；复核里空着、第一次读到了的字段沿用第一次）→ 仍不过调 Vision，「原图 + 原文」一起给 3.1 再读
  （`ocr_read`，LOW，输出上限 8,192）→ 还有触发项标红。
- 精简看图提示词：原 L2 提示词约 1.2 万字符，还要求每个金额 / 税号 / 日期写 `source_refs`（来源栏位，只对表格有用），
  看图时换成约 3,600 字符、同一套输出字段、空字段可不写。表格与 PDF 文字层仍用原提示词。
- 共用会计规则（`pearnly_core.tax_documents.amounts`，与 ERP 同一套，Cowork 侧在 `ocr/validation/accounting.py`）：
  金额写法规范、合计为扣预扣税后的实付额时核对算平并补税率 / 税额、有 Vision 原文时按校验位找回税号与读错一位的金额。
  「本公司是买方」对调不搬：Cowork 同一批可能是采购也可能是销售。
- 直读页数上限从 20 提到 50（原来是整份回落时代的限制）。
- **只处理没过的那一页**。旧线上一页没过就整份文件改走 Vision + 纯文字 L2。
- 直读、复核、带原文再读写满输出上限时不再原样重试，直接进下一步。
- 3.8 视觉复核（L3 与金额补读）改为站点开关 `OCR_LAYER3_ENABLED`（在 `pearnly_cowork_ocr_environment` 里），**默认关**。
  关着时，原本要升级的触发项直接标红。表格路线原本就不升级，照旧。
- 转正：`PageSource(orient=ocr.orient)`，图片与 PDF 渲染页都转；Vision 用转正后再缩小的图。
- PDF 文字层路线（text fast path）仍走原来的 Vision / 文字 + L2。
- 同一批 18 张实测（旧线上 ฿0.220 / 张、9.1 秒、16/18）：精简后 ฿0.065 / 张、4.2 秒、15/18，与 ERP（15/18、฿0.093）持平；
  少对的一张是人为退化的照片（旧线上靠 3.8 读对）。
- 多页限流（全平台共用，`pearnly_core.execution`）：后台识别任务里短的等待（≤ 20 秒一次、每个调用累计 60 秒）原地等并
  保住公平队列位置，不整份让出；检查点每次运行只读一次。压测 50 页由卡死变为 16 分钟读完（`scripts/ocr-multipage-stress.py`）。
- 对照测试：`test_cowork_engine_source_parity.py` 对旧线上源码 `ec2e5c957e6b` 仍通过（600 直读判定、64 Vision 判定），
  只登记「没过闸改为复核同一页」这一处有意改动。

## 未采用（有数据）

- **首读加思考（LOW）**：准确率与 MINIMAL 相同，P95 更短（4.8 秒），每张多约 ฿0.003。可作为后续调优候选，本次不改首读。
- **双读投票**：「错了没标红」最少，但每张 ฿0.094、标红率更高，不作为默认。
- **OCR 全量校对**（每张都调 Vision）：准确率不升，成本多 ฿0.05 / 张。
- **按产品拆 GCP 项目来解决 429**：Vertex 按量付费是整个组织共用的动态池（Usage Tier 按组织历史花费定），拆项目额度不会变多。
  不加预算时能做的：少调用（本方案）、按模型调我们自己的限流阀门、被 429 时换一个模型的池子（待测）。
- **Pillow 投影法矫正歪图**：真实手持照片上不可靠（正常照片 6/37 被误判成侧拍），改用上面第 4c 条的方向分类模型。

## 后果

- 每张原价从约 ฿0.18 降到约 ฿0.09，P95 从 15 秒降到约 9 秒。
- 旧线上「硬闸不过换 3.8」的对照关系改变。ERP 这条不受旧线上逐字对照约束；Cowork 已在对照测试里登记（见上文「Cowork」）。
- 评测脚本保留在 `scripts/`，以后换模型、改规则，都先用同一批语料跑一遍再上线。
