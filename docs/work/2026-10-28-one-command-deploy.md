# 生产部署一条命令（2026-10-28）

用户觉得每次生产部署慢。主会话定的范围：把「构建 → 放镜像 → 服务器激活 → 回读」从人工逐步改成一条命令，**每一道检查和顺序都不变**，
只消除步骤之间的人工等待；不砍候选检查、不跳过激活前备份、不并行激活、不加固定月费、不循环频繁 SSH 生产。

## 结论

- 新命令：`scripts/production/deploy.sh`（本机跑）。真实部署前先 `--dry-run`。
- **机器耗时省不了多少**：前三次发布里，步骤之间的空档合计只有 1–2 分钟（见「时间对比」）；构建约 7 分钟、激活约 9–10 分钟是机器真实在干活，
  不砍检查就降不下来。省下的是人：不用盯着构建、复制 digest、手写服务器脚本、隔一阵 SSH 看日志、逐条回读。
- 用 `workflow_run` 让放镜像在构建成功后自动跑：**不改**（理由见下），一条命令已经把这个空档吃掉了。

## 三个脚本

| 文件 | 在哪跑 | 做什么 |
|---|---|---|
| `scripts/production/deploy.sh` | 本机 | 触发构建 → 等完成、核候选检查、从构建产物取 digest → 触发放镜像 → 等完成 → 一次 SSH 后台启动服务器端 → 一条长连接看进度 → 打印结果和各段用时 |
| `scripts/production/deploy-run.sh` | 生产机 | 核镜像 revision → 同步部署工具、核对 → ERP / Cowork / DMS 依次激活 → 基础层 → 回读；每一段之前等可用内存 ≥ 8 GB，全程每 10 秒记内存 |
| `scripts/production/deploy-readback.sh` | 生产机，只读 | 新镜像、active-image 记录、NOFORK、全部站点维护模式与部署后 Error Log、四个域名、mariadb 内存（docker stats） |

用法：

```bash
scripts/production/deploy.sh --dry-run
```

```bash
scripts/production/deploy.sh
```

断点续跑：`--digest sha256:<64位>`（这个 main 已构建过，跳过构建）、再加 `--skip-stage`（镜像已在生产机上）；本机断线后 `--attach` 重新接上。

| 人工步骤（production-deploy-steps） | 现在 |

新增（只加检查、不减）：revision 硬核对、服务器端脚本与镜像副本一致、生产机同一时间只允许一次部署（锁目录记 pid 与 SHA，进程已不在的残留锁会接管）。

回读的一处判定：进维护那一分钟定时任务被拒的 `Scheduled jobs can't run in maintenance mode` 单独列出、不算问题，
这和 10-25（08bfb419）人工回读的判定一致（mrerp 当时就有 4 条）；其他任何新报错都算问题、打印前 3 条。

批次特有的表、字段、补丁回读和线上冒烟不在通用回读里，照旧按发布记录另做。

## SSH 次数

任务书写「低频（不短于 60 秒一次）读回日志」。记忆里明确不许写「每 60 秒 SSH 一次」的等待循环（09-27 办公室 IP 被挡），
所以改成服务器那头 `tail -F --pid`：一次部署只有 **2 次 SSH**（启动 1 次、看进度 1 条长连接，部署结束自己断开）。
长连接断了等 120 秒再接，最多 5 次；接上后从已看到的行之后继续，不重复。旧流程一般是启动 1 次 + 看日志若干次 + 回读 1–2 次。

## 失败时停在哪

| 停在 | 生产 | 下一步（脚本会打印） |
|---|---|---|
| 构建失败 / 候选检查不是 success / 取不到 digest | 没动 | `gh run view <id> --log-failed`；修好推 main 再跑 |
| 放镜像失败 | 服务没动 | `deploy.sh --digest <d>` 重跑 |
| SSH 启动失败、已有部署在跑 | 没动 | 网络好了 `--digest <d> --skip-stage`；有部署在跑就等它 |
| revision / 部署工具核对没过 | 没动 | 看日志 FAILED 行 |
| 某个产品激活失败 | 该产品可能停在维护，后面的产品没动 | 不自动回滚；看 `activate-<产品>-<短SHA>.log`，备份在各站点 `private/backups/`，回退照上一次发布记录 |
| 回读有问题 | 激活已完成 | 逐项看 PROBLEM 行；可单独重跑 `deploy-readback.sh` |

## 放镜像要不要用 workflow_run 自动触发：不改

- 放镜像会在生产机上 `docker pull`（`receive-image.py`），不启动，但占生产磁盘和带宽，接收端不清理旧镜像。
  自动触发后，**每一次**构建都会把镜像拉上生产，包括之后作废的构建（10-27 就作废过 6c8860b9、5afc3755 两个）。
- `workflow_run` 用默认分支上的工作流定义、带生产密钥运行；digest 只能经产物传递（保留 1 天），多一层耦合。
- 收益只有构建结束到放镜像开始之间的空档；一条命令里这个空档已经是几秒（脚本每 15 秒查一次状态）。
- 所以不满足「100% 确定零影响」，不改。

## 限制

- 真实部署的端到端（服务器上 `tail -F --pid`、nohup 后 SSH 立即返回）还没在生产上跑过，第一次用时盯一下；任何一步不对脚本会停，不会自动回滚。
- 远端 main 上的提交必须已经含 `deploy-run.sh`（本次合入之后的提交都含），否则脚本让你按旧的人工步骤走。
