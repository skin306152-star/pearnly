# 需求影响评估：CC 引导式 · 收银日汇总（POS 导出，P3 C1 第 4 类）

> 总表 CW-D-POS-L / C / M 三格。基线 `pearnly/cc-guided-recon`（含引擎 N1–N10）。

## 0. 需求原文与理解

- 原话：用户 11-14「每个功能都要有引导式」；主会话 11-16 定 C1 顺序：增值税 → 收银日汇总 → 预扣税。
- 理解：Cowork 版 CC 里点「收银日汇总」：交 POS 导出（Excel / CSV）→ 走库存还是记费用（导出带商品明细时才问）→ 认列题（第一次见这种版式才问：哪列是日期 / 票号 / 金额…、日月顺序、金额含不含税、状态值是销售 / 作废 / 退货；按公司记住）→ 复核卡（每天一行：日期、首末票号、金额、税额）→ 确定 → 建好每天一张日汇总票 → 结果卡。认列答案从卡上点，不再由模型填 `answers`（P3 盘点 #31）。
- 不在范围：认列规则、按天汇总、推送载荷不动；推送（写进 Express）见第 12 节第 1 条。

## 1. 现有同类与复用

- 网页、LINE 没有 POS 入口；服务端已全有：`pos_import/service.preview`（认列 / 回答认列题，回 `layout_needed` 的表头、样例、问题，或 `ready` 的逐日汇总）、`admit`（按天建票，按原件 + 请求号幂等）；版式按公司记住（`pos_import.layouts`）；定时任务里停着等认列的那份同一组函数。CC 工具 `cowork_pos_import / cowork_pos_layout` 调的就是它们。
- 结论：全部复用，新增 `pearnly_cowork/assistant/guided/pos.py`。认列题用引擎 N1a（子题由 `preview` 的 `questions` 算出：`column.<字段>` 从表头选、`date_order`、`amount_basis`、每个没见过的状态值一题），提交时拼回 `preview(answers=…)` 要的形状。

## 2–3. Frappe 原生 · 按类通用

- 不涉及 Desk。「交文件 → 服务端出动态题 → 复核每行 → 确定」的写法与预扣税同类。

## 4. 上下游数据

- 只接 Express（`cowork_pos_import` 说明：POS 推送只接 Express）；MR.ERP 格仍等 MR.ERP 线（总表不变）。账套 = 本对话账套（写入闸）。
- 建票不写账本、不扣费；同一份导出再交一次照服务现状会再建一遍（工具说明「Importing the same export again enters it again」），引导里同一次确定只办一次（引擎保证）。
- 推送后收款科目（每种付款方式一次，判定卡 kind receipt）走采购 / 销售同一张判定卡。

## 5. 隔离与权限

- 菜单：有录入功能的人（`scope.require("intake")`，同工具）；文件只认本对话附件。

## 6–9

- CC 菜单「收银日汇总」+ 说一句；网页 / LINE 不动。新模块 + hooks 追加 + 术语表追加；不改 `pos_import/*`。无新增存储与费用。建出的票照录入工作台规则删除（不在本引导）。

## 10. 文案

- 认列题的标题、选项尽量沿用 `pos.*` 已有词条与 POS 字段名；没有的四语新增。菜单字「收银日汇总」、开场一句新增。不加说明。

## 11. 测试与验收

- 离线：版式认得出不出认列题、认不出出子题（列从表头选、日月顺序、含税、状态值）、答了记住下次不问；没有商品明细不问走库存；复核卡每天一行合计对；确定建票一次（双击不两次）；认列答案不全确定时退回认列那一步；MR.ERP 账套给事实不给确定。
- 流程（接线后）一条；真模型：说「把这份收银导出录进去」→ 只打开引导。
