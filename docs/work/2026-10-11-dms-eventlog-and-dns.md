# DMS 白天同步跟上对方使用记录改版 + 容器 DNS 与 LINE 发送重试（2026-10-11）

分支 `pearnly/dms-eventlog-dns`，基线 `0fce2a49`。用户 2026-10-11 21:00：两个都修，测试机没问题就上线（次日演示）。

## 1. 外部 DMS 改了"使用记录"，白天同步停住

- 现象：曼谷 11:54:59 起 `live_sync` 每轮在第一个模块（客户）停住，两个租户同时（正式与测试 DMS 同在 `www.mrerp4sme.com/dms`）。
- 证据（只读实测）：`eventlog/component/js/view.js` Last-Modified 10-11 03:43:46 GMT（曼谷 10:43），新加"按日期删除使用记录"；
  不带 `sdtamt` 的请求不再回 `dt::<总数>`，回最新一行；行从"一个 `<p>` 里 7 个 `<span>`"变成"每项一个 `<p>`"，
  顺序 账号 / IP / 日期 / 时间 / 模块 / 动作 / 标识，标识 `<流水号>||`；分页多给一行、页与页重叠一行
  （`sdtamt=3`：第 1 页 991–988，第 2 页 988–985）。客户 / 车辆 / 银行 / 用户 / 订车列表总数照常，脚本日期都是旧的。
- 影响：只影响"DMS 网页上的改动白天补进缓存"；LINE 查询、建单、凌晨全量不走使用记录。新登记读档账号的权限试探
  （`account_probe._can_read_events`）用的也是总数，同样会失败。
- 修法：`eventlog_reader` 两种行形状都认、行外有字或 `dt::` 无行判失败、要求严格从新到旧；`count` 换成 `head`
  （最新一行的流水号）。`change_sync` 改按流水号判断：最新流水号大于水位才往回翻、翻到不大于水位的那一行为止、
  按流水号去重；最新流水号小于水位或翻到底没碰到水位（记录被删）按"未知"交整组重读。读不到时日志写明原因。

## 2. 偶发解析不到域名

- 链路：容器 → Docker 内置 DNS → 宿主 systemd-resolved（127.0.0.53，上游谷歌，当时用 IPv6 那台）。dockerd 日志
  10-01 起约 210 次"问 127.0.0.53 超时"：10-01 Cloud Run 识别域名 162 次（压测），之后外部 DMS 域名 AAAA 28 次、
  `api.line.me` 13 次（A 6 次 = 3 起菜单同步报错）、`auth.pearnly.com` 3 次。实测直接问 4 个上游与 127.0.0.53 各 80 次，
  只有 IPv6 上游丢 1 个。
- 风险：LINE 回复撞上就改推送，推送同一瞬间也失败，消息丢（只留警告）。
- 修法：compose `x-runtime` 与 keycloak 加 `dns`（8.8.8.8 / 1.1.1.1 / 8.8.4.4，可用 `PEARNLY_DNS_1/2/3` 换），
  绕开宿主那一跳；`pearnly_core.line` 在"还没连上就失败"（`NewConnectionError`，含解析失败、连接被拒）时
  隔 0.5 / 1.5 秒重试，读超时、对方断开等可能已送达的情况不重试。
