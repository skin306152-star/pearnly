# 发票每份的服务器 CPU（2026-10-01）

分支 `codex/invoice-cpu`，基线 `origin/main` 4091731d。来源：压测窗口转交的产品问题（用户同意做零成本的服务器优化，服务器先不升级）。
原则：结果、保护、审计都不变，只减少重复工作；每一项写清省了多少。

## 压测窗口的生产实测

每份发票在我们服务器上约 3.2 CPU 秒（cProfile 按 CPU 计 + cgroup 累计），8 核每分钟只能完整处理 60–70 份；每份约 200 条 SQL。
其中转发给 Cloud Run 时每次重建 TLS（约 0.17 秒）归 LINE 窗口（forward.py）。

## 测量方法（测试机，不付费）

`scripts/testenv-invoice-cpu.py`：在测试栈 testcowork 上走真代码的上传 → 提交 → 识别任务 → 存结果 → 扣费，只把 Cloud Run 的回答
换成一份已有识别结果、扣费直接回成功（不碰账本）、不投递识别队列；识别进程先停。前 5 份预热不计入，每轮 30 份，新旧代码交替各跑
3 轮（同一测试栈、同一数据）。测试机比生产快约 5 倍，比的是同条件下的相对变化。

| | 每份 CPU（3 轮） | 「识别 + 存结果」 | 每份 SQL |
| --- | --- | --- | --- |
| main（旧） | 0.368 / 0.378 / 0.369 秒 | 0.247–0.252 秒 | 199 |
| 本分支 | 0.305 / 0.303 / 0.305 秒 | 0.190–0.192 秒 | 188 |

合计约 -18%（「识别 + 存结果」约 -23%）。

## 改动与各自的效果

1. **查重复发票走索引**（`history/duplicates.py`、`Cowork OCR History` DocType）
   - 原来三道查重（发票号 / 日期 + 卖方 / 日期 + 对方税号）对字段套 `LOWER()`、表上也没有这几列的索引，只能沿创建时间把本公司记录
     逐行过一遍：没有重复时每存一张票扫一遍全表（生产 testcowork 已 2925 行），记录越多越慢，压在数据库 CPU 上。
   - 改：`invoice_no`、`invoice_date` 加 `search_index`（DocType 原生声明，部署迁移时建）；`LOWER(x)=%s` 改 `x=%s`——两列都是
     `utf8mb4_unicode_ci`（测试机实查），本就不分大小写，取出的候选完全相同，最终仍由 Python 逐字核对。
   - 效果：EXPLAIN 由沿 creation 索引逐行过滤变为走发票号索引（估 1 行）/ 日期索引（估 9 行）。测试机只有 479 行，产品侧 CPU
     看不出差别；省的是数据库那边、并随记录增长。
2. **权限判断去重**（`access/scope.py`、`files/access.py` 及 5 处「几项里有一项能用」的调用方）
   - `granted` / `allowed_any`：几项一起判时账号是否启用只查一次；`contains`、`references` 改参数化查询（不经查询构建器）；
     `full_allowed` 每种（归属，客户）只核一次。判据、时机都不变：`tests/test_cowork_scope_queries.py` 穷举
     账号 × 站点 × 买的功能 × 启用 × 角色的组合，结论与原来逐项 `allowed` 完全相同，账号只查一次。
   - 效果：「识别 + 存结果」约 -0.04 秒（测试机），SQL 条数基本不变（省的是拼 SQL 的 CPU）。
3. **识别任务单更新时不再逐个回库核对关联字段**（`ocr/execution/store.py`）
   - 一次识别存 4 次任务单，每次 Frappe 把 4 个关联字段（原件 / 归属 / 客户 / 提交人）各查一遍。这 4 个都是不可改字段（`validate`
     拒绝任何改动）、建单时已核对；被引用的记录删不掉；归属 / 客户是否停用由授权复核判断；任务单没有 `fetch_from` 字段。新建照旧核对。
   - 效果：每份 -10 条 SQL、约 -0.015 秒。`tests/test_cowork_ocr_store_save.py` 守住上述前提。
