## 0. 结论（先说结果）

1. **dsh 的前端不能单独搬过来用。** 它的网页是「插件树」，启动时从 dsh 自己的 Node 后台（Host）拉插件、走 dsh 自己的 WebSocket 协议；登录方式是进程启动时打印的一次性令牌换 cookie，只有一个「主人」身份，没有多用户、没有租户。我们的 CC 是每个租户一个 Frappe 站点、Keycloak 登录、后端在 Managed Agents。要用它的前端，要么每个租户再跑一个 dsh 的 Node 后台（推翻 ADR-019「不加常驻 Node 服务」和整个智能体后端），要么在 Frappe 里重写一份 dsh 后台协议（约 2.3 万行的协议层要对上）。两条路之后，**公司分组、右侧栏、代录、预选卡、附件识别、定时任务、桌面版桥接这些业务组件照样要全部按 dsh 插件重写**。
2. **dsh ≠ Claude。** 搬过去以后界面会像 dsh，不会因此变得像 Claude。dsh 的侧栏按「工作区＝本机文件夹」分组，设置页是模型、插件、终端这些开发者选项，都是给本机写代码用的。
3. **dsh 还很不稳定。** 官方写着「开发者预览」「未来将出现破坏兼容性的变更」「尚未接受安全审计，不得视为安全或可用于生产环境」；所有版本都是预发布版，近一个月约 4,200 次提交，2–3 天出一个版本，rc.1 还把最低 Node 版本提高到了 24.9。
4. **我们在「对话标题」上用的机制本来就和 dsh 默认做法同类**：都是先拿第一句话当临时标题，再让模型总结第一句话。差别在**什么时候换成总结**（dsh 第一轮进行中就开始总结，我们要等第一轮结束）和**长度**（dsh 中文约 10 个字，我们按显示宽度 26 卡，中文约 13 个字）。详见第 4 节。
5. **建议选 C**：不换框架，用户指出的每处不像，先拿到 Claude 的实测依据（截图或录屏），再在现有前端里逐项补齐。dsh 有公开文档、写得清楚的交互细节（比如标题时机），可以当参考（B 的做法），但它不是 Claude 的依据。A 估算写代码约 115–175 小时、机器跑 15–25 小时，另加多轮真机；而且会推翻已上线的智能体后端和桌面版接法，风险最大。

## 1. dsh 本身（有出处）

| 项 | 事实 | 出处 |
|---|---|---|
| 是什么 | DeepSeek 开发的开源 agent harness，「一切皆插件」，由 Cordis 运行时驱动 | `README.zh.md` |
| 智能体跑在哪 | 本机 `dsh` 进程里跑智能体循环和工具；默认把启动目录当文件位置；模型走外部 API（DeepSeek，也支持 `anthropic`、`openai` 等提供方和自定义网关） | `docs/user/guide/index.md`、`docs/user/guide/providers.md`、`packages/llm/llm-pi-ai` |
| 会话存哪 | 追加写的会话日志 `session.vN.jsonl[.zstd]`，放在 `$DSH_HOME`；密钥在 `$DSH_HOME/.credentials.yaml` | `docs/architecture.md`、`providers.md` |
| 网页怎么起 | `npx @deepseek-ai/dsh web`，默认 `http://127.0.0.1:3080`；要求 Node ≥ 24.9 | `README.zh.md`、`package.json` 的 `engines` |

| 前端怎么加载 | 网页启动时「从 Host 提供的启动图加载客户端模块系统，再激活客户端插件」；插件由 Host 以 `/plugins/.../client.js` 提供 | `packages/client/web/README.zh.md`、`packages/client/connection/README.zh.md` |

| 公网部署 | 有反向代理指南，但「打印的 URL 携带进程凭据，只应与预期用户分享」，端口要自己限制在可信网络内 | `docs/user/guide/public-deployments.zh.md` |
| 安全声明 | 「尚未接受安全审计，不得视为安全或可用于生产环境」；沙箱「不保证隔离」 | `SAFETY.zh.md` |
| 桌面端 | 有 Electron 桌面版（Windows 安装器、macOS 更新） | `docs/architecture.md`、发布页 rc.1 |
| 手机 | 窄于 768px 时侧栏变抽屉；rc.1 写了「完善手机和平板适配」；有 PWA 清单测试 | `packages/client/ui-layout/README.zh.md`、发布页、`apps/web/tests/pwa-manifest.e2e.ts` |
| LINE 内置浏览器、QtWebEngine | **不知道**：文档没提，我们也没跑过 | — |
| 许可证 | MIT | `LICENSE` |
| 成熟度 | 「开发者预览」「未来将出现破坏兼容性的变更」；8 月 13 日公开（第三方报道 pasqualepillitteri.it 与搜索结果）；全部版本是预发布（alpha / rc），10-03 到 11-04 共 13 个版本；近一个月约 4,200 次提交 | `README.zh.md`、`git tag`、`git log` |

## 3. 三种做法比较

| | A 整体换成 dsh 前端，后端能力逐个接 | B 只借 dsh 的个别交互照着做 | C 不换，逐项按 Claude 实测补齐 |
|---|---|---|---|
| 做什么 | 先选「每租户跑 dsh Node 后台」或「Frappe 实现 dsh 协议」，再把第 2 节的业务组件全部写成 dsh 插件 | 挑 dsh 文档写清楚的交互（例如标题时机、侧栏悬停卡、归档撤销）在现有前端照做 | 用户指出一处不像 → 先拿 Claude 截图或录屏 → 现有前端改到一致 |
| 写代码（机器耗时，粗估） | 协议或后台 40–60 小时 + 业务组件重写 60–90 小时 + 测试与流程改写 15–25 小时，**合计约 115–175 小时** | 每项约 1–4 小时 | 每项约 1–4 小时；侧栏 + 标题这一批约 5–15 小时 |
| 机器跑 | 15–25 小时（全量流程、三产品、手机、桌面版） | 按受影响场景 | 按受影响场景 |
| 真机 | 多轮：三星 / LINE / iPhone / 测试机 CC 桌面版 | 一轮 | 一轮 |
| 多租户、安全 | 高风险：dsh 只有单主人身份，官方说没做安全审计 | 不变 | 不变 |
| 手机、LINE、桌面版 | 高风险：都要重测，LINE 和 QtWebEngine 能不能跑**不知道** | 低 | 低 |
| 性能 | **不知道**：浏览器侧代码约 18 万行，比我们约 3.5 万行大很多；老办公机上怎样没测过 | 不变 | 不变 |
| 跟版本 | 高：2–3 天一个预发布版，会有破坏性变更；实际只能分叉冻结，之后自己维护，dsh 后续改进也拿不到 | 无 | 无 |
| 用户看到的差别 | 整个界面变成 dsh 的样子（不是 Claude 的样子）；业务功能在重写期间会缺 | 个别交互变化 | 用户指的那处变得和 Claude 一致 |
| 会不会推翻已上线的东西 | 会：智能体后端接法（ADR-019）、桌面版桥接、代录对话、全部前端测试 | 不会 | 不会 |

ADR-019（10-10）当时已经比较过 dsh，排除的理由是「单用户本机设计，无服务器级认证，官方声明未经安全审计的预览版」。本次复核发现这几点都没有变，见第 1 节。

## 4. 用户点名的两处细节

### 4.1 对话标题 =「用户第一句话的简要」

| | dsh 默认（`packages/bundle/base/cordis.patch.yml` 第 60–77 行） | 我们现在 |
|---|---|---|
| 临时标题 | 第一条消息的前 5 个词、不超过 40 字节（`session-title` 的 `fallbackMaxWords: 5`、`fallbackMaxBytes: 40`） | 第一句原文，压空白后截到 60 字（`contracts.py:78-86`、`titles.py:38-43`）；侧栏按宽度显示 |
| 总结用什么 | 只给第一条用户消息（`packages/session/session-title-first-prompt-llm/src/index.ts`） | 第一条消息 + 第一段回复的开头 + 界面语言（`contracts.title_prompt`） |
| 什么时候总结 | 第一条消息之后、主请求路由一记下就发辅助请求，不等这一轮做完（同包 README「调度」） | **第一轮结束后**才排后台任务（`relay.py` 的 `_turn_ended` → `titles.turn_ended`） |
| 长度 | 中文约 10 个字 / 英文约 5 个词（`targetCjkCharacters: 10`、`targetWords: 5`） | 显示宽度 26（`contracts.py:21` `TITLE_WIDTH`），中文约 13 个字 |
| 模型 | 当前对话的同一路由，最低推理强度 | `claude-haiku-5-5`（`engines/__init__.py:40`） |
| 几次 | 只自动一次；改名后不覆盖；另有实验插件每条消息后重新生成 | 只自动一次；改名后不覆盖（`sessions.py:499-508`） |

**差在哪（推断，待用户截图确认）**：机制是一样的。最可能让人觉得「不是第一句的简要」的是时机：第一轮要跑工具、识别单据时，可能要几分钟才结束，这期间侧栏一直显示截断的原文；另外我们总结时带了 CC 的回复，标题可能偏向回复内容，不是第一句话。
**Claude 本身怎么做：不知道。** 本次没有实测依据。要照 Claude 改，先拿到 Claude 的截图或录屏：标题出现的时刻、长度、是否参考回复。

### 4.2 侧栏分组

- dsh：默认「按工作区」分组，可切换成「工作区树」或「平铺」。先显示置顶，再显示其他；「最近更新」按最后一次用户提问时间倒序；拖动后变成手动排序。每组默认显示 5 条，「展开其余」每次多 5 条。悬停 800ms 出悬浮卡。行高 32px。出处：`packages/client/ui-workspace/README.zh.md` 第 30–60、200、216 行。工作区就是本机文件夹（「添加工作区需要组合目录选择器」）。
- 我们：按公司分组，有置顶、排序、折叠、拖动、多设备同步（`thread-list.tsx`、`sidebar-*.ts`、`list-sync.ts`）；10-15 已按 Claude Code 网页版实测规格重构过（`docs/work/2026-10-15-claude-code-ui-study.md`）。
- **用户说的「不一致」具体指哪几处：本次不知道。** 那需要用户这次的截图，或者 Claude 当前版本的实测，才能逐条对照。dsh 的规则是 dsh 的，拿来当 Claude 的依据不对。
