## 先说结论

1. **答案是齐的，不用从 S 盘导出。** 测试机语料 `06-录入推送` 的 158 份账套答案每份都带只读复制的 Express 原表（ISINFO / APTRN /
   ARTRN / ISVAT / GLJNL / GLJNLIT / APMAS / ARMAS / GLACC / STMAS / STCRD / ISTAB），科目、对方码、RECTYP、录入日（GLJNL.CREDAT）
   都在。用户批的「S 盘只读导出」本轮没有用上，S 盘一个文件都没碰。生产机 `/root/pearnly-corpus` 本窗口无权核（任务书不碰生产），
   它是同一批语料的副本；判定层、识别闸层都在测试机跑完，没有搬数据。
2. **两层都没过达标线，离得很远。** 判定层 A 类 53.0%（95% 下限 51.8%，6130 张），B 类 93.6%（下限 93.2%，13875 张）；
   识别闸层文字层 PDF 过闸 28 张、字段 0 错但有 3 张非票据过闸（89.3%，下限 72.8%），样本远不够 381 张；合并估计约 47%。
   按设计「没达标按类修，再跑」，下面列了按类的原因与数据。
3. **能自动的占比很小**：39 家 394,499 张单里 A 1.55%、A+B 5.07%；C 类 84% 是同一个原因——永续 / 混合库存账套的商品单没声明入账类型，
   推送准备照生产规则交人。
4. **三套阈值**：建议 A 只有 3 家升到 L1（自动推 246 张、推错 53 张、降档 1 次）；B 稳 1 家（23 张、0 错）；C 快 4 家（490 张、76 错、降档 4 次）。
   在判定准确率修好之前，阈值差别不是主要矛盾。
5. **回放查出并已纠正一处设计与代码不符**（`b8fdbd0e`）：生产电子 PDF 照图片直读（文字层快路 10-02 起关着），识别链永远不以 `text`
   开头，原代码会把所有单都判成图片单（C）。改为按原件文字层字数判（同识别取文字层的门槛：每页平均 ≥200 字）。

## 按类修的候选（数据给的方向，未施工）

按「按类通用修复、不针对某家」整理，哪条做、怎么做由开发窗口与用户定：

1. **商品单的入账类型**（C 的 84%）：129/158 份账套是永续库存，商品单（有存货明细）上传时不声明入账类型就按 `posting_needs_review` 交人。
   要让这类单能自动，得先有「这家这类单按库存记」的规则来源（定时任务规则、或按公司记一次），否则档位再高也推不了。
2. **销项现 / 赊按票种定算 A 不成立**：答案里 93% 不对（会计按现销 HS 记，票面按正式税票判赊销）。识别全对的票面只知道「有税额 = 正式税票」，
   现销的税票 / 收据合一单若识别成 `receipt_tax_invoice` 结果会不同，这一层核不了；但现有口径直接当 A 风险大，宜降为 B 或按客户记一次。
3. **销项默认收入科目算 A 不成立**：44% 不对（有几个收入科目的公司）。
4. **进项账套记忆按供应商记一个科目**：记忆定的科目 7.7% 被会计记成别的科目、806 张一单多科目；A 类不能只凭「记过一次」。
   可考虑「记忆定的科目要连续 N 张一致才算 A」之类按数据的条件（不加开关）。
5. **抵进项按方向推断（B）0 错 / 13,871 张**：正式税票、印了税额、写明买方就抵（全平台共用的 `pearnly_core.tax_documents.rules.purchase_treatment` 口径），数据支持改为 A；有正确口径的写死（用户长期口径）。
6. **账套期间只认本年**：会计在同一份账套里接着记次年段的单（SINCERE 等），3,734 张被第 2 条判 C；T1 按日期选账套同样只认本年，两处口径一致，
   要不要认 `next_end` 由用户定（R1-5 当初为防跨年写错账套才不认）。
7. **录入晚于单据日期 60 天**（6,117 张）：会计常在报税前集中补录，`EARLIEST_DAYS = 60` 对补录的单一律交人，是有意的保守，数据给用户看。
8. **非票据被当票**：还款收据、内部费用单能过识别闸，属 10-07 记录里还没修的那一类。

## 模拟的假设与偏差（报表解读要带上）

- 票面单据类型按「有税额 = 正式税票、没税额 = 收据」造，现 / 赊票面写没写也不知道（不造 `payment_status`），销项现 / 赊的错率受此影响最大。
- 入账类型：答案里没有存货明细（STCRD）的单按「服务」声明（录入第一步每批的选择，不改计分项），有存货明细的不声明。
- 没有公司规则、任务默认、分类映射、供应商档案、银行流水：只模拟网页上传 / LINE 入口，定时任务入口只换 `trigger` 重算档位。
- 主档用每份账套原表（含模拟期之后才建的档，**偏乐观**）；CC 桌面版写入时找对方档按 `master_create._find_code` 同一级联在回放里模拟。
- 录入日取凭证 CREDAT（没有取单据日期后 7 天）；合格回读假定每期都有、在截止日后一天；推错的单在回读里就是「被改」。
- 账套记忆每份账套从空开始（生产同样按账套记）；新年度账套带着上一年的单，Express 历史可用，但模拟里第一张即要人选、之后记忆覆盖，
  历史「已定」本轮没有起作用。
- 判定层只比四项；单号、日期、金额、分店由识别闸层管；存货、部门不计分。

## 与设计的出入

- **数据放哪**：设计写「先核生产机答案齐不齐，不齐才搬到测试机」。答案本来就在测试机（语料只放测试机），而且齐，所以直接在测试机跑，
  没有搬任何数据、没碰生产；生产机副本没有核（任务书不碰生产）。
- **识别闸层的来源**：设计要先在测试租户重跑 `scripts/ocr-replay-corpus.py` 补回放库、离线重跑 `prepare_history_batch`。测试机 cowork lab
  正被测试窗口用、库里也没有金标批次，本轮改用测试机上已有的金标一轮记录（当前生产代码的按记录结果 + 同轮复核标记），不重跑后处理；
  工具同时留着 `prepare_history_batch` 那条路的接口位置（`gate` 读记录，`result_json` 回放库可接到同一套核对）。分档没报（结果里没存）。
- **写入层**（62 套回归核 `verify` 全为 ok）本阶段没做（任务书只要判定层与识别闸层）。
- **「62 家」**：语料有答案的是 39 家公司、158 份账套；62 是测试机 T8 / T9 测试账套份数。按公司报。
