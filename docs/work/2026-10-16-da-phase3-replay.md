## 先说结论

1. **答案是齐的，不用从 S 盘导出。** 测试机语料 `06-录入推送` 的 158 份账套答案每份都带只读复制的 Express 原表（ISINFO / APTRN /
   ARTRN / ISVAT / GLJNL / GLJNLIT / APMAS / ARMAS / GLACC / STMAS / STCRD / ISTAB），科目、对方码、RECTYP、录入日（GLJNL.CREDAT）
   都在。用户批的「S 盘只读导出」没有用上，S 盘一个文件都没碰。生产机 `/root/pearnly-corpus` 本窗口无权核（任务书不碰生产），
   它是同一批语料的副本；两层都在测试机跑完，没有搬数据。
2. **两层都没过达标线（点估计 ≥99.5% 且 95% 下限 ≥99.0%）。** 判定层（不计本层核不了的销项现 / 赊）A 类 78.55%（下限 77.25%，4,005 张；
   首轮 53.0%）、B 类 89.17%（下限 88.68%，16,008 张；首轮 93.6%）；识别闸层文字层 PDF 过闸 27 张、字段 0 错、2 张非票据过闸（92.59%，
   下限 76.63%；首轮 89.3% / 28 张），样本远不够 381 张；合并估计约 72.7%（区间 59.2% ～ 78.2%；首轮约 47%）。
   A 类剩下的错几乎都是进项费用科目：账套记忆按供应商记一个科目（7.6% 不对）与一单多科目（807 张）。
3. **能自动的占比很小**：39 家 394,499 张单里 A 1.02%、A+B 5.07%；**全部单的 84%（C 类的 89%）**是同一个原因——永续 / 混合库存账套的
   商品单没声明入账类型，推送准备照生产规则交人（首轮报告写成「C 类里 84%」，分母错了，已改）。
4. **三套阈值**：建议 A 有 2 家升到 L1（自动推 200 张、推错 53 张、降档 1 次）；B 稳 0 家；C 快 2 家（414 张、74 错、降档 4 次）。
   判定准确率修好之前，阈值差别不是主要矛盾。
5. 销项现 / 赊这一层核不了（见「模拟的假设」第一条），单列：2,126 张里 1,984 张与答案不同。按类改成「按票种判赊算 B」后，销项不再有 A 类。

## 按类修的候选（数据给的方向，未施工）

按「按类通用修复、不针对某家」整理，哪条做、怎么做由开发窗口与用户定：

1. **商品单的入账类型**（占全部单 84%、C 类的 89%）：129/158 份账套是永续库存，商品单（有存货明细）上传时不声明入账类型就按
   `posting_needs_review` 交人。要让这类单能自动，得先有「这家这类单按库存记」的规则来源（定时任务规则、或按公司记一次），否则档位再高也推不了。
2. **进项账套记忆按供应商记一个科目**（A 类剩下的错的主体）：记忆定的科目 7.6% 被会计记成别的科目、807 张一单多科目；A 类不能只凭「记过一次」。
   可考虑「记忆定的科目要连续 N 张一致才算 A」之类按数据的条件（不加开关）。
3. **抵进项按方向推断（B）0 错 / 13,878 张**：正式税票、印了税额、写明买方就抵（全平台共用的 `pearnly_core.tax_documents.rules.purchase_treatment`
   口径），数据支持改为 A；有正确口径的写死（用户长期口径）。B 类里 13,878 张只因这一项成 B。
4. **销项现 / 赊、收入科目**：本轮已按类改 B（审查处理）；现 / 赊要用真识别的票种（`receipt_tax_invoice` 等）核实后再定，收入科目可考虑按客户记一次。
5. **账套期间只认本年**：会计在同一份账套里接着记次年段的单（SINCERE 等），3,734 张被第 2 条判 C；T1 按日期选账套同样只认本年，两处口径一致，
   要不要认 `next_end` 由用户定（R1-5 当初为防跨年写错账套才不认）。
6. **录入晚于单据日期 60 天**（6,118 张）：会计常在报税前集中补录，`EARLIEST_DAYS = 60` 对补录的单一律交人，是有意的保守，数据给用户看。
7. **非票据被当票**：还款收据、内部费用单这类电子 PDF 能过识别闸（本轮 2 张），属 10-07 记录里还没修的那一类。

## 模拟的假设与偏差（报表解读要带上）

- 票面单据类型按「有税额 = 正式税票、没税额 = 收据」造，现 / 赊票面写没写也不知道（不造 `payment_status`）。会计用现销 HS 记的「税票 / 收据合一单」
  在真实识别里可能是 `receipt_tax_invoice`，回放区分不了，所以**销项现 / 赊本层核不了**，单列、不计入准确率。
- 入账类型：答案里没有存货明细（STCRD）的单按「服务」声明（录入第一步每批的选择，不改计分项），有存货明细的不声明。
- 没有公司规则、任务默认、分类映射、供应商档案、银行流水：只模拟网页上传 / LINE 入口，定时任务入口只换 `trigger` 与基线规则重算档位。
- 主档用每份账套原表（含模拟期之后才建的档，**偏乐观**）；CC 桌面版写入时找对方档按 `master_create._find_code` 同一级联在回放里模拟。
- 录入日取凭证 CREDAT（没有取单据日期后 7 天）；合格回读假定每期都有、在截止日后一天；推错的单在回读里就是「被改」（不计销项现 / 赊）。
- 账套记忆每份账套从空开始（生产同样按账套记）；Express 历史按录入先后只用这张单之前已录进去的单。
- 判定层只比四项；单号、日期、金额、分店由识别闸层管；存货、部门不计分。

## 与设计的出入

- **数据放哪**：设计写「先核生产机答案齐不齐，不齐才搬到测试机」。答案本来就在测试机（语料只放测试机），而且齐，所以直接在测试机跑，
  没有搬任何数据、没碰生产；生产机副本没有核（任务书不碰生产）。
- **识别闸层的来源**：设计要先在测试租户重跑 `scripts/ocr-replay-corpus.py` 补回放库、离线重跑 `prepare_history_batch`。测试机 cowork lab
  正被测试窗口用、库里也没有金标批次，改用测试机上已有的金标一轮记录（当前生产代码的按记录结果 + 同轮复核标记），不重跑后处理。分档没报。
- **写入层**（62 套回归核 `verify` 全为 ok）没做（任务书只要判定层与识别闸层）。
- **「62 家」**：语料有答案的是 39 家公司、158 份账套；62 是测试机 T8 / T9 测试账套份数。按公司报。
