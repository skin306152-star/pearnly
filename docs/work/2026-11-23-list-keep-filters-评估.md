# 产品列表回来时保留筛选（评估）

11-23，主会话 local_0d36f9f2 定（A）。分支 `pearnly/routed-page-keep-filters`，基于 main b08a771ec。起因：左下角头像「再点回到上次界面」
（`pearnly/user-menu-return`）实测时，ERP 物料页回来搜索框清空——浏览器后退回去同样清空，是这类页面原有的问题。

## 0. 需求原文与理解

用户 11-13：「……应该跳转到上次界面」。回到一个列表页时，人刚才输的搜索、选的筛选、点的排序、选的每页条数都应该还在，
不管是左下角返回、浏览器后退、还是从侧栏 / 面包屑点回来。

## 1. 现有同类与复用

- 三产品的列表都用同一个共用列表 `p.list`（`pearnly_core/public/desk/list.js` 的 `ProductList extends frappe.views.BaseList`），27 个调用处。
- 丢的原因分两类：
  - ERP 用 `p.routed_page` 的页面（物料、入库、出库、调拨、调整、采购、销售、收款、库存、库存卡、公司、团队等）每次显示都 `clear_page`
    再 `render`，搜索框等页面字段和列表一起重建；
  - 其余页面（Cowork 任务、DMS 推送记录等）不重建，同一次打开里回来还在，但**刷新 / 下次登录**就没了。
- 只修 `routed_page` 不够通用；在 `ProductList` 这一处做，所有列表一个口径。

## 2. Frappe 原生能力（锁定 16.33，已读源码）

- 原生列表 `list_view.js`：每次渲染前 `before_render()` → `save_view_user_settings({filters: filter_area.get(), sort_by, sort_order})`，
  经 `frappe.model.user_settings.save(doctype, view_name, …)` 存成**这个人**的设置（服务端持久，跨刷新、跨设备）；
  建列表时 `view_user_settings.filters` 优先恢复（「Priority 1」），其次 list settings 默认；`frappe.route_options`（链接带来的条件）在刷新时覆盖。
- 复用：存取一律走 `frappe.model.user_settings`（原生 API，不自造存储、不进 localStorage），时机照原生（每次取数前存、建列表时恢复、route_options 优先）。
- 原生只存筛选区条件与排序；我们的页面另有页头字段（搜索框、日期、仓库等 `page.add_field`）——同一份设置里多存一项 `fields`，恢复时按字段名填回。

## 3. 按类通用

`ProductList` 一处：三产品全部页面级列表自动生效，各页不改代码。**不生效**：嵌在表单里的列表（`options.container`，如销售 / 采购表单的附件行）、
页面显式 `remember: false` 的（预留，当前没有）。

## 4. 上下游数据

只读写本人的 User Settings（原生表 `__UserSettings`，按 用户 × doctype 一行 JSON）；不改业务数据、不加接口。

## 5. 隔离与权限

- 设置按人存，别人看不到。
- **按公司分开**：view_name = `pearnly:<页面路由>:<当前公司>`（`frappe.boot.pearnly_company`，没有公司体系的产品为空）。仓库、客户这类条件是
  这家公司的值，换到另一家时不带过去，免得一进页面就是空列表。
- 恢复时条件不再合法（字段已不在白名单、选项已不存在）照原生 `validate_filters` 丢掉，页头 Select 值不在选项里不填。

## 6. 入口：网页、手机、LINE、拍照

电脑 / 手机网页同一份；LINE / LIFF / CC 桌面版 / 智能体页不用 `p.list`，不受影响。

## 7. 共用件与连带回归

改 `list.js`（共用件「产品列表」）：`check-impact` 出影响清单，各列表页自动冒烟照跑；手工实点 ERP 物料 / 入库 / 库存卡（有日期默认值）、
Cowork 任务、DMS 推送记录各一，「输条件 → 去别页 → 回来 / 刷新 / 换公司」。

## 8. 存储与成本

每次取数前一次 `user_settings.save`（原生本身就是这么做的，框架内部合并去抖后写服务端）；每页一份几百字节的 JSON。无新增费用。

## 9. 删除、作废、追溯

清空条件（筛选区的 ×、搜索框清空）即存成空，下次回来就是空的。不需要另做「清除记忆」。

## 10. 文案与官方 UI

不新增、不改文案；没有新控件。

## 11. 测试与验收

- Node 测试（真实 list.js + 假 BaseList / user_settings）：取数时存、建列表时恢复页头字段 / 筛选 / 排序 / 每页条数；带 route_options 时不恢复；
  换公司不串；表单内列表不存。
- 回归实验室（复用本窗口那套，挂本分支）：电脑 + 手机宽度，ERP 物料「搜 TEST → 左下角进出 / 浏览器后退 / 刷新」各截一张，库存卡日期、
  Cowork、DMS 各一张；截图自看后交主会话。
- 闸门：全闸门、候选离线、产品地图、文案。

## 14. 实施与实测（11-23，主会话审定：照原生存个人设置；日期用上次选的）

- 提交 36bd80f90（存 / 取）、ce0b8f1bd（只在进页面时取回一次；拆列表时拆掉原生筛选区）。改动只在共用列表 `list.js`。
- 施工中发现并修的两处：
  - 库存页「显示方式」一改就整张重建列表：每张新列表都取回会「填回 → 重建 → 再填回」死循环，且会把人刚改的值盖成旧存档 → 改为每次换路由只取回一次，
    取回过程中引起的重建只再取回筛选与排序。
  - 原有问题：列表 `destroy()` 不拆原生 FilterArea 追加的「筛选」区，同一页重建列表（切「显示方式」）页头多出一颗「筛选」→ 一并拆。
- Node 测试 `tests/test-desk-list-memory.cjs` 8 条（存取、route_options 优先、换公司不带、表单内列表不存、非法条件丢弃、重建不死循环、
  同次进页人改值不被盖回、拆筛选区），已进 development.yml。
- 回归实验室（`*-old` 数据站点，本分支源码 + 镜像 fdf20d98），电脑 1280 / 手机 375：ERP 物料搜索、ERP 库存「按物料」、DMS 推送记录状态，
  各「设好 → 侧栏去别页再点回 / 浏览器后退 / 重新打开（= 刷新、下次登录）」全部保留；24 张截图 `~/pearnly-devtools/list-keep-shots/`，已自看。
- 没测到：换公司实点（实验室站点只一家可切的公司数据，换公司不串由 Node 测试覆盖）；Cowork 页面（与 DMS 同为不重建的页面，原来同一次打开就保留，
  这次只多了刷新后保留，未单独截图）。

## 15. 撤回原因与重新进批（11-24，窗口 list-memory-mobile-fix）

- 现象：main 4ec6f2aca 全套流程 `erp.inventory.by-product` 手机端新旧两套都不通过（按位置空表），已在 d8510e61a 撤出 11-23 部署。
- 复现（本机实验栈 `pearnly-listmem-lab`，代码同 4ec6f2aca）：同一站点先跑桌面格、再跑手机格 → 桌面过、手机空表；清掉库存岗的列表记忆后单跑手机格 → 通过。
  个人设置里存着 `pearnly:pearnly-inventory:CO-00001` → `filters: [product = PRD-…]`、`fields.search = 桌面那格的物料名`。
- 根因：不是手机端时序。桌面那格最后一步「点开按物料那一行 → 回到按位置、只看这件物料」由页面加了「物料 = …」条件，列表照原生把它存进**库存岗这个人**的
  个人设置；下一格（同站点、同账号、换成手机宽度）进页面照设计取回，再叠上这一格新建物料的搜索 → 空表（那件物料也已被上一格收尾删掉）。
  桌面格排在手机格前面，所以只有手机格红。产品行为与原生列表一致（人自己点开过，回来还是那样），缺的是测试隔离：
  列表记忆是新增的「按人持久」状态，跑测试的会话没有清。
- 修法（按类，覆盖所有用测试会话的入口：流程、自动冒烟、验收、性能、打印核对）：`scripts/smoke/session.py` 建会话时先清这个账号 `pearnly:` 开头的列表记忆
  （缓存先同步进库再改库、删缓存；原生列表设置不动）。列表共用件 `list.js` 与 11-23 版相同，不改。
- 会在这个缺陷上变红的断言（`erp.inventory.by-product`）：新会话进页面时搜索为空、看法是按位置、没有筛选条件（比对应有状态）；不带修法跑同一站点两格，
  桌面、手机都红（带着上一格的搜索与「筛选 1」进页面、空表）。另加一步「离开再回来」：去库存卡再点回库存，仍是按位置、搜索还在、筛选 1、这件物料的两仓两行
  （列表记忆本身的业务断言，电脑 + 手机）。
- 同类核查（读代码）：页面自己加条件或换看法时整张重建列表的有库存（点开物料、「显示方式」）、首页（类型 / 期间切换重建）；盘点（ERP / Cowork）在详情与列表之间
  切换时整页 `clear`。都走同一个 `p.list`，进页面只取回一次（b707c2abb），测试会话一律清记忆；Cowork 对账页的多看法这次只做了打开冒烟，没有专门的记忆用例。

## 16. 代人加的条件不进跨次记忆（11-24 主会话定）

- 口径：「点开某一行」或别页按钮带着预选进来，这类由页面替人加的条件，只在这次停留、以及浏览器后退 / 前进回到这一条历史时保留，
  不写进跨次进入的记忆；人自己在搜索框、筛选、视图、日期里选的才记住。从菜单、侧栏重新进入列表时不带上次点开的那一件。
  真人场景：昨天在库存里点开过某件物料，今天从菜单进库存只看到这一件、再搜别的是空表，会以为库存没了（正是 11-23 晚流程红掉暴露的同一件事）。
- 实现（共用 `list.js`，27 个列表同一套）：页面替人加条件一律走 `list.drill(条件)`（列表画好后再加）或建列表时的 `drill` 选项
  （页头字段值 / 条件）；这些记在**当前这一条浏览历史**（`history.state.pearnly_drill`，按记忆键分）上——后退 / 前进回到这一条会带回，
  菜单、侧栏、链接进来是新的一条，自然没有。存档时排除代加的条件，那个字段沿用人上次自己选的值；人改了代加的值，改后的才算人选的、照记。
  不按「换路由计数」判断后退：框架先渲染页面、再发 change，时序不可靠。
- 同类（读代码查全）：页面直接调 `filter_area.add` 的只有库存「按物料 → 点一行」；别页带预选进来的只有 Cowork 自动录入规则「查看待处理」→ 录入页「失败」
  （原实现里取回的旧状态还会盖掉这个预选，一并修好）。两处都改用 `drill`；node 测试另拦页面直接 `filter_area.add`。
- 断言：`erp.inventory.by-product` 「点开物料 → 去库存卡 → 浏览器后退」仍是这件的两行、筛选 1；「点开物料 → 去库存卡 → 再从菜单进库存」无下钻条件、
  搜索框与视图照旧、两行（搜索仍是这件的名字）。node 测试 12 条（新增：下钻不记 / 菜单进来没有 / 后退回来还在、人改了照记、预选不被旧值盖也不记、
  页面不直接 `filter_area.add`）。Cowork 录入页临时实测（本机实验栈 cowork-new）：人选「成功」→「查看待处理」进来是「失败」→ 菜单再进来「成功」→ 后退回那一条「失败」。
