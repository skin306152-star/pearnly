## 0. 需求原文与理解

- **原话**（用户 2026-10-26，经主会话转达）：「那做成正式版到 cc 桌面端吧，前端交互逻辑要设计好……遇到问题是怎么处理的，哪些能自主处理，哪些又一定必须要人工……我要的是一个全局覆盖完整的系统，而不是区区单一的系统……前端这边入口我建议和现在的直写分开，这是另一个功能，就像之前说的一样」。
- **前端设想**：见用户 10-25 晚的构想（桌面《CC代录Express-讨论记录-2026-10-25.md》第五节）。
  - 左上角切换「对话 ↔ 代录」；
  - 引导式收集资料，再做预检；
  - 开始后自动打开并登录 Express，一张张录；
  - 完成后汇报。
- **我的理解**：
  - 事务所会计（或老板）在 CC 桌面版里切到「代录」，选一家公司、一段期间、一批已识别好的单据。
  - CC 先把要人决定的事一次问完，然后在这台办公室电脑上真实打开服务器版 Express、自动登录，像人一样一张张录。
  - 会计可以看着录；录完给出汇报：录了哪些单号、哪些没录及原因、用时、费用、核对结果。
  - 覆盖目标是 **Express 里会计日常要录的全部**：买卖、费用、收付款、退货减价、库存、日记账、银行，以及主档。按单量从大到小分期交付。
- **两产品共用**（用户 10-26 补充）：CC 不管用 Cowork 账号还是 ERP 账号登录，都有左上角「对话 | 代录」切换和整套代录流程（准备 / 进行中 / 汇报、异常分级、写者锁与直写互斥），行为一致；单据来源各接各的（Cowork 的识别草稿、ERP 的采购 / 销售单据）。
- **第 0 期交付目标**（岳父 10-26 回复：有兴趣，做出来和现有方式比较，他找一家公司来试）：能给一家真实客户公司试用，并直接出对比报告（§11）。真实公司账套写入要等岳父选定公司、用户授权后才动，事先在 69EXP\test 全流程跑通。
- **不在本需求范围**：
  - 不改「直接写入」的现有行为；
  - 不改识别读法本身（只补落地时丢掉的明细字段，见 §4）；
  - 不做 Express 设置类操作（库存设置、用户权限、期间开关）；
  - 不做报表打印；
  - 不做月结签字（属数字会计员计划）；
  - 不在没有 Express 授权的电脑上运行；
  - 不破解、不注入、不改 Express 程序。

## 2. Frappe 原生能力

- 服务端只加接口和 DocType：代录批次、每张单的结果、异常（截图只在本机，不登记到服务端）。DocType 放共用层 `pearnly_core`（两产品站点都装），权限走原生角色加服务端校验；各产品的入口按 ADR-009 写在自己的 `hooks.py`（`pearnly_navigation`）、`features.json`、`i18n/messages.tsv`。
- CC 前端是 ADR-019 登记的 React 例外（`frontend/assistant`），按 `globals.css` 标准写法和闸门（`check-frontend-tokens` 等）施工，不新增 Vue 壳，Desk 不加自定义样式。
- **结论**：服务端用原生 DocType 和白名单接口；前端照 CC 现行规则。

## 3. 按类通用（「全局覆盖」怎么做到）

**做法：一个通用引擎 + 每种表单一份「配方」，不是每种单写一套程序。**

- **引擎**（通用，只写一次）：
  - 开 Express、登录；用 Alt + 数字走菜单；工具栏按命令号发命令；
  - 表头按回车走格，用 Win32 读出「焦点在哪一格」和格子左边的标签，按标签填，每格读回；
  - 点进明细表格，逐格录、逐格读回；
  - 弹窗按规则表处理（弹窗标题带 Message# 号，泰文内容读得到字）；
  - 读底部合计，存盘，按单号格确认已存，最后读 DBF 逐字段核对；
  - 判断不了才截图给 AI；放弃一律作废。
- **配方**（数据，不是代码），每种表单一份：
  - 菜单路径；
  - 要填的标签、各填哪个草稿字段、走到哪格为止；
  - 明细列、底部合计标签、单号格标签、特有弹窗。

  试点里四种买卖单就是四份配方。
- **新账套第一次先探路**：同一个 Express，不同账套的菜单、表头顺序、价格类型默认都可能不同（试点实测 69EXP 就和手册里的 70EXP 不同）。探路的做法：
  1. 开表单、点新建，只按回车走一遍，记下每格标签；
  2. 读菜单项，校验配方；
  3. 点取消：还没录明细时取消不写任何东西（试点已实测）；
  4. 把这本账套的配方版本存下来。
- 所有单种和主档共用同一个引擎、同一套异常处理、同一个前端；多个代录会话可以同时录不同账套（§15.1）。**新增一种单 = 白天在服务器版上录一次样本 + 写一份配方 + 离线回放测试。**

## 4. 上下游数据

- **ERP / Cowork 内的单据流**：代录吃的是直写同一份载荷，上游准备、记住的选择、待处理都不变。新增的只有：
  - 载荷里的 `entry_mode`（`direct` / `operator`）；
  - 代录批次：谁发起、哪台电脑、哪些单、进度、结果；
  - 每张单的代录结果：Express 单号、核对结果、作废单号、截图登记、费用。

  回执沿用 `meta.verify`，另加 `meta.operator`。
- **Express 映射**：
  - 写入一律经 Express 自己的界面，由 Express 编号、算成本、算税、拦负库存；
  - 录完读 DBF 核对，口径同直写（`write_verify`）；
  - 已知差别：现销按含税价录时，明细单价存含税价，直写存税前价（试点 B.4）。读回时表头和税额直接比，明细单价按价格类型换算后比。
- **CC 桌面版载荷**：要变。
  - `payload_contract.py` 升一个载荷版本：加 `entry_mode` 和代录要的明细字段（品码、单位）；
  - 旧版 CC 诚实拒收（`ERR_PAYLOAD_VERSION`）；
  - 服务端只把 `operator` 单派给心跳报了「能代录」的电脑。
- **识别字段**：Claude 识别本来就读出了明细的 `code`、`unit`、`item_type`、行折扣、`vat_rate`，但 Cowork 落地时（`ocr/execution/claude.py` 约 36–55 行）只留了品名、数量、单价、行金额。代录按明细录，要补上**品码、单位**（直写以后也受益）。
- **Cowork / ERP / DMS**：DMS 不涉及（不写 Express）。Cowork 和 ERP 都可以发起代录，共用层同一套批次与派单、CC 里同一套执行层：
  - Cowork：单据来自识别草稿（准备好的直写载荷），批次带 Cowork 的工作空间与 Express 连接；
  - ERP：单据来自 ERP 的采购 / 销售单据（`express/push.py` 出的同一份载荷），批次带 ERP 公司与 Express 连接；
  - 共用层只认「载荷 + 连接 + 账套」，不认产品；回执按来源各自回写（Cowork 回识别草稿的推送状态，ERP 回单据的 `express_state` / `express_docnum`）。

## 5. 隔离与权限

- **谁能发起**（两边各自角色，服务端校验，不靠前端隐藏）：
  - Cowork：和直写推送同一条——这个工作空间里有「收单」权限（`scope.allowed("intake", user)`）、且能用这条 Express 连接的人；
  - ERP：和 ERP 推送同一条——对这类单据有写权限（`express/api.py` 的 `guard.require(能力)`）、且公司在本人可见公司里（`companies.allowed_companies()`）的人；
  - 共用层的批次接口只收各产品校验后交来的载荷，再按连接核一次：批次的连接必须是发起人能用的那条，账套必须在这条连接的电脑报过的账套里。
- **谁的电脑录**：只派给这条连接下、心跳报「能代录」且本次被选中的那台电脑（ADR-021「谁的活谁的电脑做」）。网页和手机只能发起、看进度和汇报，不能执行。
- **跨公司不串**：
  - 每张单带公司和账套身份；电脑开账套前比对 Express 状态栏、标题里的公司名和路径，不符拒录；
  - 选公司时读公司列表文字核对（试点已验证）；
  - 一个批次只录一家公司的一本账套；换账套 = 换批次。
- **Express 登录密码**：只存在这台电脑、这个 Windows 用户的凭据管理器（DPAPI）里，服务端、模型、日志、截图都拿不到（试点附录 G）。

## 8. 存储与成本

- **AI 费用（试点实测）**：
  - 识别 + 录入一张约 ฿0.35；常规单据录入不调 AI（流程定型后 57 张都是 0 次调用）；
  - 判断不了才截图给 Haiku 5.5（一次约 ฿0.01），再不行交 Opus 5.5（一次接手约 ฿6）；
  - 全所 40 家每月约 15,190 张，约 ฿5,300 / 月，几乎全是识别费，和直写是同一份钱。
- **AI 在哪里调**：截图交给模型这一步放在服务端（产品站点代调，密钥不下发到电脑），走 CC 机器通道的新请求。截图只在要 AI 判断时上传，用完即删、不存档。
- **存证截图**：每张单存好后留一张，约 150–250 KB；全所每月约 3 GB。
  - 只存本机、保留 30 天，不进原件层、不上传（§12.1 第 4 条）；
  - **满 30 天自动删除，不靠人手清**（主会话 10-26）：每个批次的截图目录里有一份清单（批次号、批次开始日期、本批写过的文件名），按清单里的批次日期判断，不按文件修改时间；只删清单里列着的、本程序写的文件，目录里别的东西一律不碰，删空了才删目录；
  - 清理时机：每次代录批次开始前、结束后各扫一次，CC 启动时也扫一次（接线在共用件那一步）；不加常驻进程、不加定时轮询（守 CC 轻量）。
- **固定月费**：不新增。
- **电脑时间**：一行单约 26 秒，每多一行约 +6 秒。全所约要**一台专用电脑每天 5–6 小时**。这才是代录真正的「成本」：机器和 Express 授权名额。

## 9. 删除、作废、追溯

- **放弃单据只能作废**（试点附录 F 实测）：录完第一行明细，Express 就已占号写账；取消、关窗口都会直接存档，界面上没有「不存就丢」的路。
- **执行器规则**：
  - 明细前能核对的全部先核对，每格读回确认再提交；
  - 真要放弃 = 取消 → 读单号格确认已存 → 作废命令 → 确认框按「ตกลง」，并把作废单号报给会计；
  - 绝不用 Esc；绝不删单（删单会让单号断档且无痕）。
- **作废的两道硬保护**（10-26 实机事故后加）：
  - 事故经过：后台做法第一次试跑（69EXP\test），一张单在表头读回不符（泰文变「?」）要放弃。取消后 Express 的单号格显示的是**上一张已存好的单**，旧逻辑把它当成「这一张已经存上」去作废，结果把第 4 批已存好、读回核对过的三张测试单 **HP0000026、IV0000022、HS0000007** 误作废了（只在试点账套，没有真客户数据）；
  - ①只作废这一张开录之后、账套里新出现的单号（读开录前记下的行数之后的新行）；
  - ②批次再核一道：本批次开录后新建、且不是本批次已存好的单才许作废；本批次以外的单任何情况下都不作废；
  - 两道任何一道对不上都不作废，那张半截单报给人（「需要你」），有离线测试守着。
- **已录进 Express 的单要改**：代录不改已存的单。发现错 → 汇报里标出 → 会计决定作废重录（代录可代做「作废 + 重录」，要人点确认）。
- **追溯**：每张单留
  - 谁发起、哪台电脑、哪份配方（含版本）、每一步（按了什么键、读回什么值）；
  - 存档截图；
  - Express 单号和核对结果；
  - AI 接手时的对话摘要（不存截图原图）。
- **删除批次**：这些记录和本机截图一起真删（轻便工具口径）。Express 里的单不受影响。
- **截图过期**：满 30 天的截图自动删除（§8）；汇报里这张的「回看」显示「已过期」，不报错，步骤、读回值、单号照常能看。

### 12.1 定案（主会话 10-26 审定 3f9a0688，用户已把调度交给主会话）

1. 电脑：准备页选「哪台电脑录」（只列心跳报了能代录的电脑）+「现在开始 / 指定时刻开始（如下班后）」，默认本机现在开始；有人动电脑按 §14 暂停；专用 Windows 账户只是建议。
2. 授权名额：不问用户，运行时判断（-330 / 名额满 → 必须人工，写明原因）；只占 1 个，录完即退出。
3. 第 3 期前缺主档：预检里让人选，默认用 CC 现有直写建档（带查重）。
4. 截图：只存本机 30 天，不进原件层。
5. GL 分录：接数字会计员的客户规则，第一次人定。

## 14. 异常处理分类（哪些自主、哪些必须人工）

三级：
- **自动**：CC 自己处理，不打扰；
- **自动后报告**：CC 处理了，汇报里列出；
- **必须人工**：停下这张单、出「需要你」卡片，其余单照录。

| 情况 | 级别 | 怎么处理 | 理由 | 界面表现 |
|---|---|---|---|---|
| 新供应商 / 新客户 | 第 0–2 期：**必须人工**（预检问：用 CC 建档 / 选已有 / 跳过）；第 3 期起：人选了「CC 建档」后自动 | 建档前按税号、再按名称精确查重（同直写） | 建错主档影响全账；先人定，再自动 | 预检卡：名称、税号、建议 |
| 新商品 | 同上 | 品码规则按公司记住 | 同上 | 同上 |
| 主档税务设置与识别不符（如供应商主档税率 0、票面有 7% 税；或主档默认含税） | **必须人工**（预检问一次，按公司记住） | 试点实测：这类单在保存前被合计核对拦下 | 是记账口径，不能猜 | 预检卡：两边对比 + 选项 |
| 识别读错 / 存疑（校验位不过、合计不平、置信低） | **必须人工**（预检） | 沿用现有识别的异常判断，代录不改识别结果 | 录入只照草稿录；识别错，录进去也是错 | 预检卡 + 原件预览 |
| 记账口径（如这家供应商的进项税不抵扣） | 有公司规则时**自动**；第一次**必须人工** | 规则来自记住的选择 | 试点里有 5 张和答案不同就是这个原因 | 预检卡 |
| 疑似重复单（同对方同单号 / 同日同金额） | **自动后报告**（照录，口径「推送不查重不拦」） | 预检显示「疑似重复 N 张」，人可以取消勾选；Express 弹 1029（对方单号已存在）时按确定继续 | 用户定的口径 | 预检提示 + 汇报标注 |
| 陌生弹窗 / 画面不符 | 规则表认得出的**自动**；AI 接手解决的**自动后报告**；AI 解决不了的**必须人工** | 先 Haiku（≤8 轮），再 Opus（≤14 轮）；新弹窗事后补进规则表 | 试点：流程定型后 0 次；调试期 12 次接手 | 汇报列出；解决不了的出「需要你」 |
| 负库存被 Express 拦（4224 / 4091） | **必须人工**（这张挂起，其余照录） | 被拦的单若 Express 已占号，按放弃流程作废并报单号 | 由账套设置决定，CC 不改设置 | 「需要你」：哪个商品、哪个仓；选「先录进货再重录」或「跳过」 |
| 负库存提醒（605） | **自动** | 按确定继续 | 只是提醒 | 不显示 |
| 放弃一张已录明细的单 | **自动后报告** | 取消 → 确认已存 → 过两道作废闸（本张开录后新出现、本批次新建且未存好）→ 作废；闸没过就不作废、转人工 | Express 只有这条路；10-26 实机曾因取消后单号格显示上一张而误作废三张好单（§9） | 汇报「作废 N 张：单号」 |
| 「有人在用电脑」 | 前台做法：**自动**暂停；后台做法：只在人切到 Express 并在里面操作时**自动**暂停 | 开局记下当时的最后输入时间（登录、解锁的按键不算）；每次判定留证据（时刻、原因、系统与本程序的输入时刻、当时最前面的程序和标题），没有证据不停；30 秒没人动或人点「继续」就接着录 | 10-26 实机：旧口径把登录按键当成有人在用，每张白等 2 分钟 | 进度页「已暂停：有人在用 Express（几点几分）」+「继续」；汇报列出每次暂停 |
| 跨期 / 已关账月份（Message#.70 日期不在期间、期间已锁） | **必须人工**（预检拦下） | 预检读会计期间和锁月状态；录中遇到 70 不自动改日期，这张挂起 | 改日期是会计判断 | 预检卡 |

| Express 崩溃 / 进程没了 | **自动后报告** | 断点续录：重开、自动登录、进公司；按对方单号 + 日期 + 金额读 DBF 判断这张存没存，存了跳过、没存重录；同一张崩 2 次挂起 | 不重录是硬要求 | 进度区显示「重新打开 Express」；汇报列出 |

| 电脑要睡眠 | **自动** | 代录期间保持唤醒和屏幕常亮（扩展 `keep_awake`），结束后恢复 | — | 不显示 |

| Express 授权名额满 / 单据打不开（-330） | **必须人工** | 不绕过授权 | 授权是厂商规则 | 「需要你」，写明原因 |

| 断点续录（暂停、停止、电脑重启后接着录） | **自动** | 每张单状态落盘（未开始 / 录入中 / 已存 + 单号 / 已作废）；续录前先读 DBF 核对再决定 | 不重录 | 批次页「继续」按钮 |

| 预算或 token 到上限 | **自动**停，继续要**人工** | 每张单、每批都有上限 | 成本可控 | 「已达本批费用上限」 |

## 15. 架构

```
网页 / 手机（发起、预检、看进度）          CC 桌面版窗口（同上 + 实时画面 + 控制）
        │ 服务端接口                              │ QWebChannel（tomoDesktop）
        ▼                                         ▼
产品站点（Cowork / ERP）── 代录批次、预检、派单 ──► 共用机器通道 cc_desktop（载荷 entry_mode=operator）
        ▲ AI 判断请求（截图，只在需要时）                 │ 领单（只派给「能代录」的电脑）
        │                                                ▼
        └──────────── 托盘进程：写账线（单线程，与直写串行）── account_write_lock（PEARNLY.LCK，与直写互斥）
                                  │ entry_mode=operator 时才 import operator 包
                                  ▼
                operator：会话（开 / 登录 / 选公司）· 探路 · 引擎（键盘 · Win32 读状态 · 弹窗规则 · 合计核对
                          · 存档确认 · 放弃作废）· 配方（单种 × 账套版本）· 断点续录 · 读 DBF 核对（复用 write_verify）
```

- **服务端在共用层**：代录批次、每张单的结果、派单都在 `pearnly_core/express_operator/`（多产品共用，与 `cc_desktop` 同层），Cowork 与 ERP 只各自交来源载荷、各自声明入口和权限（§5）；CC 端不分产品，同一个包、同一套前端。
- **怎么操作 Express：后台做法（推荐，10-26 实测）**。不碰真键盘鼠标，直接给 Express 的窗口发消息，人照常用这台电脑：
  - 打字：给焦点格发泰文 cp874 字节的字符消息（A 版；发 Unicode 时系统按电脑代码页换，换不成就成「?」，实测踩到）；全选用编辑格自己的选中消息；
  - 回车走格：给焦点格投递按键消息，经 Express 自己的消息循环处理，与真按回车等效；
  - 菜单：按菜单项文字开头的数字找到命令号再发（单据窗口最大化时菜单栏第一项是空的，按位置数会开错单）；
  - 新建 / 保存 / 取消 / 作废：工具栏命令号；弹窗按钮：按钮点击消息（只按能用的那个弹窗）；明细表格：给表格控件投递鼠标按下 / 抬起；
  - 焦点、「前台」按 Express 自己的界面线程读；公司核对读状态栏（只认状态栏专用读法，缓冲区在 Express 进程里借、读完即还）；
  - 等待：不再死等，等 Express 忙完就走（发一个空消息，它忙时要等忙完才回，连续两次很快回、焦点和弹窗不再变就算处理完）。
  - **实测**（rec-laptop，服务器版 69EXP\test，四种单各 1 张、单行明细，读回逐字段全对）：
    | 做法 | 每张用时 | 说明 |
    |---|---|---|
    | 前台做法（真键盘鼠标，第 4 批 12 张） | 约 140 秒，暂停的约 260 秒 | 其中约 2 分钟是「有人在用」误判的空等；不暂停的实际约 25 秒 |
    | 后台做法 + 原来写死的等待 | 26–27 秒 | 22–24 秒是固定等待，真正干活约 3 秒 |
    | 后台做法 + 等忙完就走 | **10–11.6 秒** | 剩下约 6–7 秒是 Express 自己处理（查对方、存档、开单据窗口），读回账套约 1 秒 |
    | 后台做法，有人在用别的程序时 | 8.6–10.9 秒 | 前台一直是别的程序，真鼠标没动，Express 没被拉到前面 |
  - **开源对照**：pywinauto 0.6.9（BSD）同类后台接口实测不能直接用——menu_select 按位置数菜单开错了单、会把 Express 拉到最前面（抢屏幕）、get_focus 取到的是标签不是输入格；它还提示 Express 是 32 位程序要配 32 位 Python。AutoHotkey / AutoIt 的 ControlSend、ControlClick 是同一原理（投递按键与鼠标消息），只看了文档，没有安装。结论：用自写的几十行 ctypes（`bg_desk.py`），不引入 pywinauto 整包（安装包本来就排除它），没有许可证问题。
  - **第②档「后台桌面」**（同一登录下另开一个看不见的桌面放 Express）：要在那个桌面里另起一个 Express 并登录，依赖「授权一次自动登录」；登录窗口样本录好后再测。第①档已经做到不抢鼠标键盘、不抢屏幕，第②档主要是连 Express 窗口也不出现在人的屏幕上。
  - **锁屏**：后台做法发消息不经过输入桌面，按原理锁屏照常录，实测见施工记录。
- **执行器在 CC 桌面版里，守住轻量**：
  - 不新增常驻进程、不加网页内核（ADR-025 / 1.11.0 起的约定）；
  - `operator` 包只在领到代录单时才 import，不代录时零占用；
  - 不新增轮询，复用写账线每 3 秒的领单；
  - 只用 ctypes（Win32 读状态、`SendInput`、剪贴板、GDI 截图），PNG 用已有的 Qt 编码，不引 pywinauto / mss / cv2；
  - 截屏只在要 AI 判断、存档、窗口正在观看这三种时候做。
- **授权一次、之后自动登录**（试点附录 G 方案）：
  - 本人在代录页「授权登录」输一次，存凭据管理器（只限这台电脑、这个 Windows 用户）；
  - CC 只在本机把它填进白名单里的 Express 登录框，只回成功或失败；
  - 模型、服务端、日志、截图都拿不到；
  - 服务器文件夹访问凭据同理：只能由用户本人在 Windows 自己的凭据框里输，CC 提供「打开服务器文件夹」按钮弹出系统框（试点已实测）。
- **新账套第一次先探路**：见 §3。探路结果（配方版本）存本机，同时报服务端，同一条连接的其他电脑可以复用。
- **独占电脑与 Express 授权名额**：
  - 代录期间这台电脑的前台归 CC 用；建议专用电脑或专用 Windows 账户（例如晚上集中录）；
  - 一台电脑同时只录一批；
  - 服务器版 Express 的并发登录名额由授权决定（§12 第 2 条）。批次开始占一个名额，结束正常退出 Express 释放（试点收尾已实测正常退出）。
- **和直写共存（写者锁）**：
  - 同一账套，代录和直写不能同时进行：代录整批持有电脑侧 `PEARNLY.LCK` 和服务端写者锁（同一个锁身份）；
  - 期间直写单按「等账套」排队，代录结束后释放；
  - 代录开着 Express 时，直写本来就会因「Express 开着账套」而等（`account_lock`），两层一致；
  - 不同账套互不影响。
- **AI 判断**：
  - 截图经机器通道交给产品站点，站点用 Claude API 调 Haiku 5.5 / Opus 5.5（电脑操作工具集 `computer_toolset_20260801`）；
  - 电脑执行模型给的动作前，仍要过前台守卫和落点守卫；
  - 密钥只在服务端。
- **新增 ADR**：ADR-026「代录 Express：执行方式与边界」，写明入口分开、载荷 `entry_mode`、只用 ctypes、放弃即作废、密码只在本机。

### 15.1 多个代录会话并行（用户 10-26 晚提出，10-27 设计）

用户原话（经主会话）：「exp 好像支持多窗口和多会话打开的……就像现在的 claude 一样，每个窗口做一个公司，然后我开个新窗口，又可以让新窗口做另一个公司，两者不影响不冲突，也可以同时进行，甚至未来，可以 10 个 20 个同时进行，但是我们要做到 cc 最好少占电脑资源……也不做限制，反正就是最大优化我们 cc 吧」。

**口径**
- 一个代录会话 = 一个批次 = 一家公司的一本账套（已是这样）；代录侧栏像 Claude 侧栏的多会话，可以同时开几个、各自进度互不影响。
- **同一本账套串行、不同账套并行**：同一家公司（同一本账套）同时只能有一个会话在录（PEARNLY.LCK 按账套目录，与直写也互斥）；第二个会话选到同一本账套 → 排在后面，界面写「等账套」。
- **不设硬上限，按本机实时负载自动调节**：同时在录的会话数由调度器按 CPU 占用、可用内存、Express 响应时间（发一个空消息多久回）动态决定；负载高就让新的会话排队，负载降下来再开；老电脑自然开得少、新电脑开得多。

**执行层怎么改**
| 层 | 现在 | 并行要改的 |
|---|---|---|
| 每个会话的 Express | 认「任何一个 ExpressI 的主窗口」 | 每个会话绑定**自己的那个 ExpressI 进程**（启动时记进程号；接管已开着的按状态栏里的账套路径认），所有消息只发给这个进程的窗口，不会串窗 |
| 执行线程 | 托盘写账线一张一张录 | 写账线领到代录单只转交，不阻塞；每本账套一条代录线程（按需起、录完退出），同一本账套的单在自己的线程里串行 |
| 领单 | 服务端「每台电脑同时一件」 | 共用件：代录单按账套各算一件——同一台电脑可以同时领不同账套的代录单，同一账套仍一件（直写规则不变）；领单时带上本机此刻还能接几个会话（调度器给），服务端照这个数派 |
| 调度器 | 无 | 托盘里的小对象（不是常驻线程）：每次有会话要开始时看一次 CPU、内存、各 Express 的响应时间，够就开、不够就排队；不轮询，靠会话开始 / 结束时触发 |
| 授权名额 | 一个会话占一个 | 每开一个 ExpressI 占一个登录名额；满了 Express 自己会拦（-330 或登录失败）→ 这个会话排队，界面写原因，不重试轰炸 |

**CC 本体保持轻量**：代录包只在有代录会话时导入；每个会话一条线程、录完即退；不加常驻进程、不加定时轮询；进度页只在看得见时刷新。真正吃资源的是每个 ExpressI 进程本身，所以要实测给数。

**实测计划（rec-laptop，白天）**：1 / 2 / 4 个会话同时录（不同账套——试点只有 69EXP\test 一本，第二本起要用户指定一本能写的测试账套，或同一本账套验证「串行排队」）；每档记：每个 ExpressI 的内存与 CPU、CC 托盘进程的内存与 CPU、每张用时、Express 响应时间、有没有串窗或互相影响、授权名额在第几个被拦。再按实测推算老电脑（例如 4 GB 内存、双核）能同时开几个，写进 §8。

**还要用户 / 主会话定的**：第二本可写的测试账套（并行要不同账套）；Express 授权名额数（不知道就以实测为准）。

## 需求影响评估：被人打断后自己判断能否接着做，并在 CC 窗口说清状态（10-30 晚，交主会话审）

### 0. 需求原文与理解

- 用户（经主会话 10-30）：被外部打断时，CC 要自己判断工作有没有被介入、能不能接着做，再决定继续还是停下来问，并能从断点续，不能是「一按键就停 30 秒」的死规则。主会话定四步：①人在 CC 的 Express 里操作 → 立即停发（不和人抢），等人停手几秒；②复核现场；③一致就续、可确定恢复的自己修正后续并在汇报记一句、不确定的停在安全画面在 CC 对话里问一句具体问题（附截图），答完从断点续；④读不懂的画面才调模型看图。

### 实测事实（本节依据，均 10-30 晚录制机实机）

1. 任务页把「有人在用」这类自动暂停故意显示成「等电脑空闲」，单据行仍是蓝点「进行中」（`frontend/assistant/src/components/operator/model.ts:182`），人看不出停了。
2. 恢复条件是「全电脑 30 秒没有非 CC 输入」：录制机上有程序每 0.3 秒补发一次 Ctrl 抬起（注入、无签名），批次停住后永远恢复不了，暂停证据里每 30 秒一条（已改：键盘只算按下，0a1c7148）。
