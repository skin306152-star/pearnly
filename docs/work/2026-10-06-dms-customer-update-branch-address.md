# DMS 老客户「อัปเดตข้อมูล」失败：空分店、地址覆盖与电话收取（2026-10-06）

用户：「空分店补00000，地址按DMS规则，开始修」。
分支 `pearnly/dms-customer-update-branch-address`，基线 `origin/main` 3610ff1f。属 DMS 自有功能修复，不是迁移；
下面三处都是**有意改变**老产品照搬来的行为。

## 现场（ris，2026-10-05 11:41–11:42，Push Log 可查）

1. 销售发身份证照片 → 机器人要电话 → 销售先发 `0611655634`，紧跟一条「ที่อยู่ปัจจุบัน 142/5 ม.3 ต.แกลง … 21160 (ห้อง142/50) คะ」。
   收电话按"含数字即视为号码"，第二条把电话覆盖成整段地址。
2. 本地缓存没认出这位老客户（编号 15476，缓存是前一晚的）→「新客户」卡 → 建档时 DMS 实时查到已存在 → 差异卡，
   把身份证上的老家地址（บุรีรัมย์ / คูเมือง / หนองขมาร）列成户籍、联系、寄送三套地址的更新。
3. 点「อัปเดตข้อมูล」→ `cus/edit.php` 回 `err::ข้อมูลดังกล่าวถูกใช้งานในระบบ`。DMS 里没被改动，办理停在这里。

## 证据

- MR.ERP 框架（`~/mrerp-source`，ERP 源码，DMS 同一开发商）里这句话只在 MySQL 报 `constraint fails`（外键）时输出；DMS 服务端源码没有，
  这一层是推断。
- 只读对比 15476 与 9-25 改成功的 15268 的编辑表单：唯一差别是 `branchcusval`（空 vs `1`）。提交的地址链在 DMS 主档里有效。
- ris 客户缓存：15,258 个里 14,513 个分店为空，743 个 `00000`；测试账套 40 个里 37 个有分店（所以测试一直通过）。
- **测试 DMS 复现**（用户 2026-10-06 同意，测试客户 62）：原样提交空分店 → 同一句报错、无改动；只补分店 00000 → 成功；
  分店正常时电话换成那段地址文字 → **成功存入**（DMS 不校验电话）；电话已复原。客户 62 分店留为 00000（DMS 不允许改回空）。
- DMS 客户表单脚本（`cus/component/js/form.js`）：保存必填含「สาขา」和三套地址；三套是 ที่อยู่ตามบัตรประชาชน /
  ที่อยู่สำหรับติดต่อ / ที่อยู่จัดส่งเอกสาร；`dupaddr` 只把身份证地址填进**空着的**联系/寄送栏。
- 客户分店是泰国完整税票上买方的「สำนักงานใหญ่ / สาขาที่ xxxxx」，个人客户即 00000。分店列表：`cus/component/bshsd.php`，
  `elemname=txtbranchcus`，ris 的 00000 是 id 1，测试账套是 16。

## 改动

| 行为 | 入口 | 说明 |
| --- | --- | --- |
| 空分店补 00000 | `client/client_intake._ensure_customer_branch` | 建/改客户都适用；已有分店原样保留；表单没有这一栏不碰；DMS 里没有唯一的 00000 → `ERR_DMS_CUSTOMER_BRANCH`（新文案，四语），不提交 |
| 地址按 DMS 规则 | `contracts/customer_merge.secondary_addresses`，写入层 `_save_customer_locked` 覆盖分支、差异卡 `intake/review.build` | 身份证地址照写；联系/寄送只在 DMS 里整段为空（且表单有这一段）时用身份证地址补，有内容就保留；差异卡同一规则，只列真会写的项 |
| 电话只认像电话的一段 | `intake/phone_text.extract_phone`，`line/text_router.route` / `capture_phone` | 9–12 位数字（`+` 开头到 15 位）、可带空格/连字符/点/括号；门牌、邮编、13 位证号、两个号码都不算；身份证和电话都已收到时其它带数字的话不再插话（`nudge` → None） |

没改：网页编辑页里业务员手填的电话（本人明确输入，照写）；DMS 外键报错的文案（补分店后已知触发点消除）；
本地缓存漏认老客户（走 DMS 实时复核兜住，另案）。
