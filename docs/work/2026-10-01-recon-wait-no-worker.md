# 对账等识别时不占进程（2026-10-01）

分支 `codex/recon-wait-no-worker`，基线 `origin/main` 51e73a9f（开工时 aa1969bc，LINE 窗口 Cloud Run 一批合入后变基）。
归属：Cowork `recon_center`（对账编排），共用层 `pearnly_core.execution.work` 加一个产品钩子与两个只读工具。

## 问题与目标

生产压测（2026-10-01）：Cowork 全平台只有 4 个 long 进程，三种对账（银行、收入、销项税核查）从交识别到拿到结果一直占着一个
long 进程原地轮询（`document_ocr.wait`、`invoice_ocr.wait`、`admission.when_room` 都是 `sleep` 循环）。同时来的对账超过 4 套
就排队，一家交多了挡住别家。修复窗口上线的「每站点最多 N 套同时跑」（`slots`）只是把排队分到各站点，没有去掉占进程。

目标（用户）：对账等识别时不占进程，多少套同时推进都只受谷歌识别本身的速度限制；不加机器、不靠调低上限。

## 方案选择：等识别时结束这一轮，识别有结论再从头跑（方案 2）

不选「交给线程」（方案 1）的理由：线程一样是名额（N 个线程就是 N 套的上限），等着的对账把全部源文件（最多 200 份 × 25MB）
留在进程内存里；long 进程要改成不 fork、补心跳与内存回收，影响面比本方案大，又达不到「多少套都行」。

做法（`recon_center/waiting.py`）：

- 对账后台任务照常从头跑。走到要等识别的地方结果还没好，就抛 `Pending`（继承 `BaseException`，读取链上按 `Exception` /
  `ValidationError` 兜底「一份读不出就跳过」的地方不会把「还没读好」当成读不出）。
- `jobs.run` 接住：记下等待（参数、发起人、在等哪几份识别、最迟何时再看）到队列 Redis，结束后台任务、让出 `slots` 名额。
- 识别有结论时，共用层 `work._finish` 最后（状态落库、名额交还之后）调 hooks `pearnly_ocr_finished_handlers`，Cowork 登记
  `waiting.work_finished`：等它的对账按原参数、**以发起人身份**放回队列；有份识别结束就腾出了识别名额，按先来后到放一套等名额的对账。
- 每分钟 `waiting.tick` 兜底：提醒没送到、时限到了、在等的识别开始读了（要定读取时限）、名额腾出来了。
- 放回来的一轮从头跑：读过的识别按参考号直接用（`document_ocr.submit` / `invoice_ocr.submit` 先按 `work.name_for` 找已有的，
  找到就不再查余额、不再冻结设置），已有结论的立即取回结果，走到下一处要等的地方或出结果。

时限保持原口径，只是不再靠「守在旁边每几秒数一次」：每处等待的起算时间、延长到哪存在 `clock`（队列 Redis，按对账号 + 等待处），
「开始读了多久」「多久没有新进展」按识别任务检查点行的时间在数据库里算（`work.call_progress`，`TIMESTAMPDIFF` 与写入同一时钟）。
「开始读」不早于开始等它的那一刻（预先提交的照片在等到它之前就读了，读取时限仍从开始等它算起，与原来一致）。

## 保护（不能失效的几条）

- **同一套对账不重复执行**：放回队列前确认这套对账没有排着队 / 在跑的后台任务；记下等待、放回队列、被杀续跑共用一把锁
  （`cowork-recon-wake:<站点>:<对账号>`），锁里再判断一次。记下等待那一刻识别刚好有了结论（提醒看到它还在跑、没放回），
  这一轮在同一个进程接着跑，不靠兜底。`slots.promote` 也不再在上一轮还没结束时重排同一个任务号。
- **被杀续跑**：在跑的那一轮照旧可能被部署 / OOM 杀掉，RQ 照样判失败 + 弃置，`resume_if_abandoned` 判断不变；等着的对账没有
  进程可杀，重启后提醒或兜底照样放回队列。RQ 显示 finished 的对账：有等待记录就是在等识别（`_recovered` 据此在缓存被清时
  仍显示进行中），没有记录且没有结果就是旧逻辑的情形。
- **不重复付费**：识别任务按参考号认领、检查点按行存，放回来的轮次不再提交；余额只在第一次交时查一次（读完扣过费的余额不能
  拿来再判一次，否则会误报余额不足）。
- **页面进度与结果推送**：阶段只往前走（每轮从头跑不闪回「读取中」）；进度看板、结束推送、进行中清单不变；源文件与进行中清单
  只在对账真正结束时清。
- 记不下等待（队列 Redis 一时不可用）：原地等 15 秒再跑一轮，不丢对账。

## 顺手修的线上问题

`slots.promote` 放排队的对账进来时，`frappe.enqueue` 以**当前会话用户**排队：放它进来的是同站点别人的对账结束、或定时任务
（Administrator），被放进来的对账就以那个人的身份跑——结果、源文件读取、任务名都按错的人。现在排队表与等待记录都存发起人，
`jobs.requeue(..., user=)` 以发起人身份排。部署前已在排队表里的旧格式条目照旧放行（发起人未知，行为与原来一样）。

## 测试机强杀实测发现的两处续跑缺口（原有问题，一并修）

- RQ 2.6.1 里被强杀的任务执行记录已不在，`job.delete()` 先把任务移出失败登记表、再在清执行记录时报
  「Execution … not found in Redis」。续跑认领锁（一小时）已经占上、任务又不在失败登记表里，定时扫描再也看不到它，
  对账一直显示进行中（只有本人开着页面问状态时才会续上）。现在删任务出错就直接删任务本身（`jobs._delete_job`），
  续跑出错放开认领锁、下一次扫描再试。`requeue` 删上一份任务同样处理。
- worker 刚把任务从队列取出、还没登记开跑就被杀：RQ 维护时判「Job was stuck in intermediate queue.」失败，原来不认它是被杀，
  不续跑。现在算被杀（`KILLED` 加这一条）。

| 位置 | 内容 |

| `recon_center/slots.py` | 排队表存发起人；按第一次拿名额的时间排先后；上一轮没结束不重排；`tick` 改每分钟 |
