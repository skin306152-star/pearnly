## 做法：复制进 ERP 自有 App，不下沉共用层

两条路都看过：

1. **复制一份进 ERP 自有 App**（采用）：`apps/pearnly_erp_portal/pearnly_erp_portal/work/` 域 + 15 张 `ERP Work *` 表 + 页面
   `pearnly-tasks` + 词条 `erp.work.*`。
2. 把规则 / 服务下沉到 `pearnly_core` 做成「多产品共用」，两个产品各留自己的表。

选 1 的理由：

- **Cowork 不能动**：要求「行为、表和数据一律不变」。做成共用就得把 Cowork 线上正在用的 `work` 域（Python 约 2,400 行、页面约 1,970 行）
  改成调用共用层、255 条 `cowork.work.*` 词条换键、页面换取词前缀——等于给生产里的 Cowork 做一次大手术，还要和那批验收、上线排队。
- **表本来就得各有一套**：DocType 属于 App 的模块，Cowork 的表不能搬；ERP 站点不装 Cowork，ERP 必须有自己的表。共用层能共用的只剩
  规则与服务代码，而这部分处处带着表名、角色、词条键、产品判据（Cowork 的「工作空间」、ERP 的岗位 / 能力）——参数化之后两边都更难读。
- **改动频率低**：Cowork 任务管理 10 月只有 3 次改动，且都是全站横向改（音效、刷新按钮、导出），分叉成本小。
- **漂移由测试守住**：两边的**权限矩阵**（`board_rights`、`member_changes` 与权限词汇）由 `tests/test_erp_work.py` 逐个组合比对
  （4×2×2×2×3×2×2 = 384 种 + 成员变更 96 种），哪边改了权限口径另一边不跟，CI 就红。其余（视图、交互）允许各自演进。
- 架构上允许：`work` 是 ERP 自有业务域，只依赖 ERP 的 `access`（判据）与共用层已有公共入口（`pearnly_core.shell.entitlements`、
  `pearnly_core.exports`），不导入 Cowork（测试守着）。

复制时有意改的地方（其余逐行同 Cowork）：

| Cowork | ERP | 原因 |
| --- | --- | --- |
| 表 `Cowork Work *`（每张带 `workspace`） | `ERP Work *`，去掉 `workspace`；列表去掉旧的 `status` 列 | 见下节；`status` 只是 Cowork 第一、二批的遗留 |
| 判据：站点是 Cowork + 角色 `Cowork Work` / `Cowork Admin` | 站点是 ERP + 买了 `tasks` + 账号启用 + `guard.has("tasks.use")`（`ERP Menu tasks` 或 `ERP Tasks`）或 `ERP Admin` | 接 ERP 的岗位 / 能力体系，与侧栏同一判据 |
| 管理员 `Cowork Admin` 管所有看板 | `ERP Admin` 管所有看板 | 同口径 |
| 分享按 Cowork 的作用域拒 | `reject_share` 挂在 DocShare `validate` 上拒（与 `access.sharing` 并列） | ERP 没有 Cowork 的作用域模块 |
| 页面 `pearnly-work`、接口 `pearnly_cowork.work.api.*`、事件 `cowork_work_*`、词条 `cowork.work.*` | `pearnly-tasks`、`pearnly_erp_portal.work.api.*`、`erp_work_*`、`erp.work.*` | 产品各自声明；页面名不撞 |
| 上传用 Cowork 的 `post-file.js`（`p.pick_files` / `p.post_files`） | 页面里自带同样的两个小函数 | ERP 没有这个文件，不为它改共用层 |
| 活动记录里旧列代号（todo/doing/done）的兼容 | 去掉 | ERP 没有旧数据 |

## 工作空间在 ERP 对应什么

Cowork 记录上的 `workspace` 是**站点内部那一份归属**（`scope.default_workspace`，用户 2026-09-26：Cowork 不做公司隔离），每个站点只有一份，
是防重 / 写锁的锚，不是一个可选的范围。所以在 ERP 它对应的就是**站点本身**：租户 = 独立站点 + 独立数据库，看板直接属于站点，表上不设这一列。
跨租户读写在结构上不可能（每个请求只连本站点的库，代码里没有跨站点的路径）。

**不按 ERP 公司分看板**：ERP 一个租户可以有多家公司，员工可以被限到某几家（官方 User Permission），但那管的是业务单据；任务管理照 Cowork
按「看板成员 + 可见范围」隔离。所以被限到 A 公司的员工也看得到「团队可见」的看板；要只给部分人看，用私有看板。若要按公司分，另议。

## 菜单、目录、权限

- 侧栏：`hooks.py` 的 `pearnly_navigation`：`pages` 加 `('erp.nav.work', 'pearnly-tasks', 'square-kanban', 'tasks')`，`available` 加入；
  `groups` 在「销售系统」后面加 `(None, None, ['pearnly-tasks'])`——标题为 `None` 的不是分组，是放在这个位置的单独一项。原生侧栏只认
  「分组外的项排最上面」，所以共用层 `desk/navigation.py` 加了这一条通用规则（`_sidebar_items` 与 `extend_boot` 两处，ADR-009 增量一句），
  其它产品没有这种条目、行为不变。页面准入（`any_role`）沿用 ERP 菜单目录的生成方式：`ERP Menu tasks` / `ERP Tasks` / `ERP Admin`。
- 功能目录：`features.json` 加 `tasks`（Task Management，默认开，岗位 `ERP Tasks`，9 张主表全只读——写只走专用接口）。新租户开通时自动有；
  老站点由补丁 `v1_12_tasks_feature` 补功能码（同 `v1_1_enable_stocktake_feature`；功能对所有租户直接生效，用户 2026-10-07）。
- 岗位 / 能力：`rules.FEATURE_ROLES["tasks"] = "ERP Tasks"`、能力 `tasks.use`；`menu.CATALOG["tasks"]`（只读那 9 张表）。
  只勾任务管理的人**不**因此得到商品 / 库存读权限（`menu.NON_BUSINESS`，`setup.sync_roles` 也只给 `ERP Company` 读）。
- 团队管理：`role_catalog` 按 `menu.CATALOG` 自动列出「任务管理」勾选框，归在「常用功能」组（与首页同组，`permission_groups`）；
  没买 `tasks` 时不列（`assignable_roles` 按功能码筛）。前端菜单与服务端判权是同一份：侧栏看 `any_role` + 功能码，服务端看
  `guard.has("tasks.use")` + 功能码，`guard` 同样把没买的功能对应的角色剔掉。
- 看板内：成员 / 可见范围 / 权限矩阵照 Cowork（`contracts.board_rights`）：团队可见的板有任务管理权限的人都能看、成员才能改（默认看板人人能改），
  私有板只有成员，`ERP Admin` 管所有看板；归档的只读。原生 REST 只给读且按看板过滤（`permission_query_conditions` / `has_permission`），
  卡片附件按看板判（File 的两个钩子），写一律被 `documents.WorkDocument` 拦下，分享被拒。
