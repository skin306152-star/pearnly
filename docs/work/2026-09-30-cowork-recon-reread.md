# Cowork 对账识别：逐页自核、没过的页自动再读一次（2026-09-30）

来源：用户 2026-09-30「都同意」第 2 项——余额链断开、对不上的页自动再抽一次（每次约 0.5 泰铢，成本已同意）；压测窗口补充
（收入 / 销项 OCR 修复第 3 条）：税报页合计对不上也再读一次，再读仍不符或没读到页合计的页标「无法自核」；收入对账里同一页
多行和总账对不上的，提示「多半是照片读错」，别当成真实差异。

- 分支 `codex/cowork-recon-reread`，工作树 `.claude/worktrees/cowork-recon-reread`，基线 main `c97eac21`。
- 只改 `pearnly_cowork`（共用层未动）。只作用于企业档逐页抽取（照片、扫描件）；本地按版面拼平的、电子表格、带文字层的 PDF 不涉及、不多花钱。

## 做法

| 位置 | 改动 |
|---|---|
| `ocr/enterprise/self_check.py`（新，纯函数） | 银行：页内余额链断点数（页上承前余额 → 逐笔 → 页上结转余额）；税报：行合计对页合计（未税 / 税额 / 含税，印了哪个核哪个），累计到本页的合计（结转、最后一页的全表总计）也算对上；几份税报按上传顺序合起来判哪些页无法自核 |
| `ocr/enterprise/pipeline.py` | 每页抽取后自核；没过就这一页再抽一次（阶段 `enterprise_schema_reread`，检查点与第一次分开；提示里只说「上次没对上、逐行重读」，**不给页上的任何数**，免得模型凑数）。银行取断点严格更少的那次；税报只有再读对上了才用再读的；再读读不出照旧用第一次，不丢页。一份文件最多再读 10 页。自核结果记在页的留痕 `self_check` |
| `recon_center/document_ocr.py` | 再读那次不重复计看板页数、不再报「刚读出」 |
| `recon_center/vat_check.py`、`sources.py`、`jobs.py` | 识别读出的税报：无法自核的页点名（收入对账进标题下提示；销项核查存进 `report_notes` 显示在标题下）；每页单号记下来给收入结果页用 |
| `reconciliation/income_recon_*`、`revision.py`、`recon_center/sheets.py` | 收入读取记录新增 `photo_pages`（每页单号）；结果页按当前核对结果现算：同一页 ≥2 行和总账对不上（金额不同或总账里没有）就提示多半是这页读错 |
| 词条 | `reconciliation.report_pages_unverified`、`reconciliation.report_page_likely_misread` 四语 |

银行账单的契约没有笔数栏，自核只看余额链（页内断点、页末结转余额）。总账不核。

## 成本

每次再读约 0.5 泰铢（一次 3.8 抽取），只在自核没过时发生，一份文件最多 10 次；再读的钱记进识别成本观测，不向用户多扣页费。

  只能这样）。这轮测试机访问 Google 大面积超时（办公室上行被大批照片堵满），环境问题。
- 修 1：IMG_2535 一页 10 行金额在单号之间整体错开，页合计照样对上，自核放过；收入结果页也没点名它——结果行单号是总账写法
  （SI690512-011）、页上记的是税报写法（690512-011）。改：按配对同一套写法（`income_vat.number_key`，去字母前缀）归页；
  同一页对不上的几行税报金额与总账金额是同一组数的，单独点名「金额错行」（`reconciliation.report_page_shifted` 四语）。
- 修 2：销项核查几份税报里一份读不出（V01 IMG_2543 超时）原来整份报「读不出税表」；改为点名跳过、其余照常（与收入对账一致），

## rJ 中间结果跟进：「多半是这页读错」误报真实差异

- rJ I01：IMG_2535 点名成功（9 行）；但 IMG_2545 (2)、IMG_2546 (3) 被误点——5 行识别完全正确，是真实差异（4 行总账里没有，
  1 行税报 3,557.02 / 总账 2,339.36）。把真实差异说成读错比漏报更伤人。
- 改：只算有读错迹象的行——单号在总账里有、金额不同且只差一两位数字，或金额正好是同页另一行在总账里的金额（配错了行）；
  单号在总账里没有，但总账同一天有一笔同金额、单号只差一两个字符的。同一页 ≥2 行这样的才提示。

## 中途被杀的对账续跑（压测窗口 2026-09-30，测试机重载打断 rI 后提出）

- 现象：重载 / 部署 / OOM 杀掉正在跑的对账后台任务（RQ 判弃置），状态缓存被清，页面一直显示 running、文件列表为空；
  它提交的识别任务还在付费读，没人用。
- 改：`recon_center/jobs.py` `resume_if_abandoned`——被杀的（AbandonedJobError / Work-horse terminated unexpectedly）、结果
  没落库的，用原来的源文件按原参数重新入队（同一个任务号），识别按「对账号:口:类型」认领、读过的页有检查点不再付费，
  状态缓存由重新入队重建；只续一次，源文件没了或又被杀就标「中途中断，请重新提交」（`reconciliation.interrupted` 四语）。
  真失败（抛错、超时）不续。发现的地方：页面问状态、识别任务付费调用前（`document_ocr._recon_closed`，续上了就照读、续不了
  才停）、每 5 分钟定时扫描（`resume_abandoned`，只看 6 小时内的）。同一份用队列 Redis 锁只让一个调用方续。
- 验证：`tests/test_cowork_recon_resume.py` 7 条；真实中途重启待压测窗口验。

## 续跑与重交撞车（压测窗口 2026-09-30）

- 现象：rI（15:33 重载杀掉、压测窗口已手动重跑为 rJ）在新版上线后被定时续跑，又出了一份结果。
- 改（压测窗口选定）：6 小时时限保留；每次提交按「同一用户 + 同一种对账 + 两边源文件内容哈希」记下最新一次提交的任务号
  （队列 Redis，24 小时，清缓存不丢；不看标题、文件名）。被杀的对账续跑前，若本人后来交过同内容的就不续，标「已由你后来的提交取代」
  （`reconciliation.superseded` 四语）；任何对账走到核对前再看一次，不是最新那份就不出结果、不弹「未完成」，两边同时在跑也只出一份。
