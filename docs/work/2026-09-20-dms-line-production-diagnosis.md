### 映射与并发设计方向（待实现、待实测）

1. DMS 是业务主档的权威来源。把字段名、数据类型、必填/可选、稳定 ID、依赖关系、展示名称、请求编码和回读规则集中在所属业务域的契约/适配层；对话和编辑器复用同一套解析与校验。
2. 普通对话使用按公司、外部系统和授权范围隔离的短期缓存，并将同时到来的刷新合并为一次。刷新能力与定时任务运行配置必须现场核对；不恢复已停用的旧周期任务。具体新鲜度、队列容量和限流值由本地测量确定并登记。
3. 编辑器打开/保存、最终确认分别做相应的新鲜度校验。最终提交用一份权威快照构造与验证载荷，主档变化让用户重新确认受影响字段；不能先校验一份数据、再用另一份旧默认值写入。
4. 身份按公司/OA/操作员绑定；同一外部账号的登录和会话受互斥保护；同账套取号与写入只锁必要临界区。OCR、主档读取、附件、查询用有界队列和独立限流，不开无限线程，也不把所有请求串在一个全局锁上。
5. “DMS 任意字段”本轮落实为 **现有 DMS 接口与旧线上业务合同内的全部字段**逐项登记与验证；DMS 将来新增字段或改变接口结构，不可能可靠地自动推断业务含义。应识别契约变化、报告未映射字段并补适配，不能宣称零维护全自动。
6. 已发送的 LINE 历史卡片无法当作可实时修改的页面；主档变更后，新查询/新编辑取新数据，旧卡点击需再次校验并更新卡片，不允许旧 ID 静默写入。

## 同链的其他缺口：不能只修一行 SQL 就宣布成功

- **员工凭据没有接到实际连接**：新 roster 保存了 DMS 账号/密码，但解析器在没有本人 Endpoint 时回落到本站第一个 Endpoint，adapter 只读该 Endpoint 的凭据。当前实际只一条 EP-00001，其用户名与操作员所填用户名不相同。旧 `services/dms_roster/service.py` 为每个 member 建立自己的 endpoint；旧 `services/erp/dms_id_ocr.py:resolve_dms_endpoint` 按用户查本人连接。需保持员工身份、查询范围和提交归属；不能只把 actor 展示改名。
- **订车提交前权威复核仍未接齐**：旧固定 SHA 的 `_book_in_session` 使用 `authoritative_read_session`、`booking_preflight.readonly_preflight`、同一快照构造 booking payload，离开只读块后用销售会话写入。新 `booking/service.py` 仍直接 sales `fetch_masters` + `resolve_booking_payload`；新仓虽已有 `booking_preflight` / `write_authoritative_snapshot`，该调用链没有接它们。该差异尚未在这次真实任务走到，不能作为本单已发生的失败原因，但必须纳入修复。
- **提交后附件异常隔离缺失**：旧流程抓取附件上传异常，保留已经成功的 booking_id/no；新 service 的附件调用未加同等隔离，可能把“订车已成功、附件失败”折成整单失败，影响安全重试和回执。
