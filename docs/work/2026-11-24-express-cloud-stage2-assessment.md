# 需求影响评估：云端 Express 第二阶段（D3–D5、自动安装、连接页改版）

> 2026-11-24 写，交主会话审定后再施工。基线：main `c6fd4d177`；D1/D2 修复分支 `pearnly/express-cloud-fixes`（已变基、过审查，另行交合入）。
> 前一阶段事实见 `docs/work/2026-11-11-express-cloud-assessment.md`、`2026-11-15-express-cloud-build-assessment.md`、`2026-11-16-express-cloud-cc-stack.md`。
> 云端主机地址、账号一律用泛称（云端主机 / CLOUD-HOST / 云端账号）。

## 结论（一屏）

1. **云端那份 CC 现在起不来，是因为它不知道自己替哪个站点干活**（D3）。改法：配对成功后，桥把「这台云端电脑在哪些站点、哪种通道」经隧道的 `ctl` 交给云端，云端据此建成员（令牌只放占位，真令牌照旧由桥中转时换上），然后照本地一样找账套、上报。没有成员时不再退出，而是等着。
2. **找账套**（D4）：11-15 探针用同一套找法在这台云端主机上 2.7 秒找到过数据目录，所以大概率能找到；另加两条直接探的路（`<盘>:\<云端用户名>\` 与 Express 快捷方式的工作目录），再给「添加文件夹」手填路径兜底。「重新查找」改成真正让云端那份 CC 重扫，结果（数据目录、账套数）报回桥、显示在云端行展开处。
3. **自动安装**：连上云端会话后，若云端没有在跑的 CC，桥在自己的远程桌面窗口里按 11-15 实测唯一走得通的路（开始菜单 → PowerShell → 打一行命令）自动打进去，靠隧道里的配对回执判断成没成；不用剪贴板。**唯一的未知是云端默认泰文键盘**：要先验证控件能不能按 Unicode 发字（不受键盘布局影响；V1，合入前的前置验证，需用户确认云端没人在用的时间）；不行就退回「连接弹窗里如实写原因 + 给手动命令」。升级不再打字：云端 CC 自己看隧道里的新包，换版后自启。
4. **连接弹窗与 MR.ERP 同一套**：一个弹窗填地址 / 用户名 / 密码，点一次连接，「正在连接 → 正在安装 → 已连接 / 失败原因」都在弹窗里；抽出 MR.ERP 弹窗的外壳两边共用，密码改为页面交给桥（同 MR.ERP inline 的做法）。
5. **输一次记住、自动重连**（D5）：密码其实已存在凭据管理器，缺的是「CC 启动就连」与「连接先用已存密码」。改成：启动有存档就自动连；只有登录失败才在弹窗里再要密码并写原因；「···」给重新登录、代录登录、断开。
6. **连接页三组**（站点 → 账本 → 电脑）按已审定口径做；**云端行展开内容已画图**（`~/pearnly-devtools/handoff-1124/express-cloud-连接页草图.html`），需用户再看一次，审定前这页不写代码。
7. **同一台电脑两行**：照片是 testerp（ERP 站点）的电脑列表；ERP 列表按「设备记录」一条一行，不按电脑合并。两行名字相同、一行离线，说明 testerp 上这台电脑有**两条都没退役的设备记录**（设备密钥不同：换过 Windows 用户、重装或换过密钥）。**不是**两个产品各一行（ERP 页只列 ERP 站点自己的记录）。要定论需读一次 testerp 这两条记录（只读，需主会话排）。改法不合并不同记录：长期离线的旧记录在「···」里可移除；Cowork 上同一条记录挂 Express 和 MR.ERP 两条连接的，合成一行、小字写两种账本。
8. **账本归云端标签**：账本按「报它的电脑」的 `link_kind` 分：云端电脑报的进「云端 Express」标签，其余留「Express」。ERP 按账套行的 `device` 关联；Cowork 目录也带 `device`，同法。
9. **验证**（凡登录云端主机的一律 20:00–07:00）：先由我们在测试机1 + 云端主机做一次**真机最小闭环**（用户已存的密码可自动连，不用用户到场；但连云端主机、在上面装程序需主会话批），过了才合入；再约用户到场一次走通 6 段。
10. **拆分与工作量**（机器耗时）：服务端（连接页、标签、电脑列表）约 6 小时，随下一车部署；CC 侧（D3/D4/自动安装/升级/D5/弹窗/代录登录）约 16 小时，随 **1.12.26**（1.12.25 照现计划发、云端入口仍收起）；验证与审查约 5 小时。入口放开条件：用户到场 6 段全过 + 1.12.26 正式版发出 + 服务端已部署，再删 `cloud_entry.visible()` 的生产判断。

11. **同一云端账号白天有人在用**（用户 11-24 新规矩：那台云端主机 08:00–20:00 公司在用，只能 20:00–07:00 连）：远程桌面在登录前**查不到**这个账号有没有人正在用，一登录就把对方挤下线（11-15 实测）。所以「启动即自动连」改为「只在设定的可连接时段内自动连」；时段外不自动连，云端账本的单子排队到时段开始；被挤下线后当晚不再自动连。见 4.9。**用户已定**：发现账号有人在用要弹「继续 / 取消」、不自动挤；因登录前查不到，改为连上后立刻核实是不是挤了人，是就当场给「继续 / 断开」，自动连时一律断开让回、记「等待确认」（4.10）。
12. **直写也要占着云端会话**，不只是代录：云端 CC 跑在这个账号的会话里，唯一出路是远程桌面重定向的隧道盘，云端主机不能上网。所以同一账号「人白天用 Express、CC 同时直写」做不到；建议默认排队到没人用的时段，白天也要用的客户给 CC 单开一个云端账号（要问服务商、成本告知用户）（4.11）。

要主会话定的点见第 12 节（8 条；主会话 11-24 已答 #1 #2 #4 #5，#3 草图在等用户，#6–#8 新增）。

## 0. 需求原文与理解

- 原话（用户 11-24 首测现场，经主会话转）：
  - 「之前mr。erp的那个连接框和逻辑我就让人该过，学一下，这个以输入，并保存，但是显示失败」（U6）
  - 「这一步我希望做成自动不需要用户手动去装，我希望用户连接上然后选择公司即可使用」（U7）
  - 「为何不像mr。erp一样储存或者记住呢，每次用都要输入吗」（U8）
  - 「远端那边实测验证顺序不要搞错，从连接到主档信息的同步，到选公司到业务能不能正常，使用是否和本地exp一致，这些不能出错」（U4）
  - 连接页草图：「整体看上去可以」「都按你的」（U9）
- 理解：客户在自己电脑的 CC 里「设置 → 连接 → 云端 Express」填一次地址、账号、密码，点连接；之后 CC 自动把云端那份 CC 装好、配好、报上账套；客户去选公司就能用（直写与代录），以后开机自动连，不再输密码。
- 不在本次范围：Cloudflare / 云端主机本身的配置；同一通道多个站点（host.py 文件头记的限制）；云端代录以外的新业务；对 .rdp 签名。

## 4. 上下游数据

### 4.1 D3：云端成员怎么建（阻塞项）

现状：云端 CC 的成员表是空的；`main._run_dbf` 在云端（无界面）模式下没有成员就以 2 退出（`test_cloud_without_a_paired_member_exits_like_headless` 守着）。整条分支里没有任何一处在云端建成员；配对只换了设备密钥。

做法：
1. **桥下发成员**：桥的 `LinkStore` 里这台云端电脑每登记一个站点就有一条 `member(site)` 和桥本机的令牌。桥在三个时点写 `ctl\members.json`：配对成功后、每次换会话（`session.json` 之后）、`cloud_token` 存了新站点令牌后。内容：`[{site, channel, member_id}]`，**不含令牌**；用当前会话密钥加密并带会话号（同 `cred-resp.json`）。
2. **云端建成员**：`CtlWatch` 看到它就解密、核会话号，按 `member_id` 增删本机 `ProfileStore` 成员：`backend_url = https://<site>`、`channel`、`token_ciphertext` = 固定占位（DPAPI 保护的常量，请求经隧道时桥丢掉云端带的 `Authorization` 换真令牌，`tunnel_relay.py:172`）。桥那边没有的成员，云端删掉。
3. **找账套再落成员**：`ProfileRecord` 要求 Express 成员有 `account_dir` 与 `account_set`（`profile_store.py:157`），所以云端先找账套（4.2），找到后用本地同一个 `apply_roots / default_account` 写进成员；没找到时成员先不落盘，状态报「没找到账套」（见 4.2 的状态文件），设置页云端行显示出来。
4. **云端模式没有成员时不退出**：改成等 `members.json`（同等会话的退避，最长 15 分钟一次，靠 `CtlWatch` 秒级醒）。它是登录时从启动文件夹起来的，一退出就要等到下次登录。对应守护测试改成「云端无成员 → 等待、不退出」，本地 `--headless` 行为不变。
5. 之后上报、领单、直写全走现有路径（`step_cloud_loop` → `step_poll_loop`），心跳已带 `link {kind: cloud}`。

载荷：不改服务端载荷；ctl 新文件只在桥与云端之间，版本号放在文件里，旧云端 CC 看不懂就忽略（不会误建）。

### 4.2 D4：找账套、重新查找、添加文件夹

- 事实：11-15 探针在同一台云端主机上，用 CC 的找账套逻辑 2.7 秒找到数据目录（`2026-11-14-express-cloud-probe-run.md` 第 4 节 T6 行）；11-24「列 D:\ 只看到 Help Express」是我们在会话里手工 `dir` 的结果。两者不矛盾：找账套不只靠列目录，还读 Express 快捷方式的工作目录与注册表（`express_locate.candidate_roots`）。所以 D4 **大概率不是问题，但要在真机最小闭环里实测确认**（验证计划 V3）。
- 加固（便宜、只在云端模式）：
  - 直接探 `<每个本机盘>:\<云端用户名>\` 与其下一层（数据目录 `D:\<用户名样的目录>\ExpressI-Cloud` 的形状），不列盘根；
  - 读正在运行的 Express 进程的工作目录（若取得到）作候选。
- **重新查找做成真的**：设置页「重新查找」→ 桥写 `ctl\rescan.json`（加密、带会话号）→ 云端重扫 → 写 `ctl\status.json`。
- **状态文件** `ctl\status.json`（云端写、桥读，加密）：云端 CC 版本、成员是否就绪、`places: [{path, ledgers}]`、最后一次扫描时间与结果码（找到 / 没找到 / 无权限）。云端启动、扫描后、每 5 分钟（仅内容有变才写）更新。桥的 `cloud_status` 从它取 `places`（现在写死 `[]`，`settings_link.py:170–172`）。
- **添加文件夹**：云端没有可用的选择框，这台电脑也选不到云端的文件夹，所以是**弹窗里手填路径**；桥写 `ctl\add-place.json {path}`，云端核：路径存在、有 SCCOMP 登记表、不在 `\\tsclient` 下；结果回 `status.json`，失败原因显示在弹窗里。

### 4.6 自动安装与升级

- **实测事实**（11-15 T5）：这台云端主机上「登录即运行」「Win+R」都不通，只有「点开始菜单 → 打 powershell → 打命令」能启动程序；用户目录、临时目录、启动文件夹可写。11-24：云端键盘默认泰文；远程桌面关了剪贴板。
- **做法**：
  1. 桥连上云端会话后，等 20 秒看 `ctl\status.json`：有且版本对 → 已装，跳过；没有 → 进入自动安装。
  2. 桥对**自己的**远程桌面控件发键：`Ctrl+Esc`（开开始菜单，不依赖 Win 键转发）→ 打 `powershell` → 回车 → 打安装命令（令牌照旧一次性、2 分钟）→ 回车。字符用 **Unicode 键盘事件**发（远程桌面协议支持 Unicode 输入，不受云端键盘布局影响）；`Ctrl+Esc`、回车用扫描码。
  3. 成功判据：隧道里出现配对请求并配对成功，随后 `status.json` 报成员就绪。3 分钟内没有 → 失败。
  4. 连接弹窗显示「正在安装」；失败时弹窗写原因（例：「云端没有打开命令窗口」「配对超时」），并给「重试」与手动命令（现在的命令块降为兜底，放进「···」）。
  5. 有人正在这个云端会话里操作（11-15 T3：同账号只有一个会话，员工和 CC 共用桌面）时不打字：检测到最近有非 CC 的键鼠输入就等，并在弹窗写「云端有人在用，空闲后自动安装」。
- **未知 / 风险**：控件能否发 Unicode 键（`IMsRdpClientNonScriptable::SendKeys` 只收扫描码；Unicode 要么经控件的输入窗口 `WM_CHAR / VK_PACKET`，要么换接口）——**必须先在云端会话里实测（V1）**；不通时的退路是先发切换输入法的热键并读回、再按扫描码打（不可靠），或只做手动兜底。其他云端主机的开始菜单 / 策略可能不同，所以每一步都靠「隧道回执」判成败，不靠截图猜。
- **升级不打字**：云端 CC 启动时和 `ctl` 变化时比对隧道里 `cc\cloud.json` 的版本；新了就在两单之间：拷包 → 核 sha256 → 解压到新版本目录 → 改启动文件夹 `CC.lnk` 指向 → 起新版 → 自己退出；失败保留旧版并在 `status.json` 报码。顺带解决「升级后旧版跑到下次登录」（11-24 审查记的「不改」项）。
- 授权：用户这句话（U7）即产品授权；11-15 先例是「在服务商主机上运行未签名程序」要告知。建议界面不加说明文字，只在弹窗状态写「正在安装」；是否需要第一次额外告知一句，交主会话定（第 12 节 #1）。

### 4.7 D5：记住密码与自动重连

- 事实：密码已存两份（Windows 凭据管理器 `TERMSRV/<主机>` 与 `Pearnly CC/cloud/<主机>`），11-24 首测后仍保留；缺的是：①`tomo_bridge` 与 `host.py` 文件头明写「CC 启动时不自动连」；②`cloud_connect` 每次都弹原生小窗要密码、不看已存凭据。
- 改法：
  - 托盘启动后，有云端连接存档、有已存密码、**且此刻在这条连接的可连接时段内** → 自动起宿主连上；时段外到点再连（见 4.9）。
  - 「连接」「重新登录」先用已存密码；只有远程桌面报登录失败（用户名 / 密码类原因码）才在弹窗里显示密码框并写原因。
  - 被挤（原因码 3，11-15 实测）→ 当前时段内不再自动重连，行状态「被挤下线」，「···」里「重新登录」；下一个时段开始时再自动连。普通断线照旧自动重连（已有离线用例）。
  - 云端会话注销 / 云端主机重启：桥重连时是新登录，启动文件夹里的 `CC.lnk` 让云端 CC 自己起来（验证计划 V7）。
  - CC 升级后自动连（同开机）。
- 「···」：重新登录、代录登录、断开；下方小字主机名、账号、云端 CC 版本。

### 4.9 同一云端账号有人在用（用户 11-24 新规矩引出）

用户原话（经主会话转）：「以后cc连接的这个云端exp要打开进入云端界面必须晚上20:00-07:00，08:00-20:00是工作时间，公司要用」。真实客户同理：同一个云端账号，人白天自己用、CC 夜里用，或两边同时要用。

**事实（能不能在登录前知道有人在用）**
- 11-15 实测：这台云端主机同一账号只有一个会话，后连的接管先连的，被接管的一端立即断开（原因码 3）。会话被接管就是挤人，不存在「连上看一眼再退」。
- 远程桌面控件（`MsRdpClient10NotSafeForScripting`）与协议在登录前没有「查询这个账号现有会话」的接口；会话仲裁发生在服务器验证账号之后，结果直接是接管。
- 服务器端的会话查询（`WTSEnumerateSessions` / `query user`）要连服务器的 RPC / SMB 端口并有相应权限；我们只能连到服务商开放的远程桌面端口，**拿不到**。
- TSplus 是否有别的查询接口（网页门户等）：**未核实**，本评估不依赖它。
- 云端那份 CC 在会话里一直跑着，白天有人用时它也在，但那时隧道盘不在（是员工的客户端连着），它的信息传不到桥；等桥连上时人已经被挤了。所以「先问云端 CC 有没有人在用」也做不到。
- 结论：**登录前无法得知；只能靠规则不去挤**。

**做法比较**

| 做法 | 会不会挤人 | 白天能不能用云端账本 | 成本 |
| --- | --- | --- | --- |
| A 启动即自动连（原 D5） | 会，白天每次 CC 启动都挤 | 能（挤掉员工） | 无 |
| B 可连接时段：每条云端连接存一个时段，时段内自动连、时段外不连，单子排队到时段开始 | 时段内员工若在用仍会挤（规则是人定的） | 不能，排队到晚上 | 小（存一项设置、定时到点连） |
| C 时段外也允许人手动连：弹窗写明事实「此时可能有人在用这个云端账号，连接后对方会下线」，点「连接」才连 | 人知情后才挤 | 能，由人决定 | 小 |
| D 给 CC 单独一个云端账号（服务商另开） | 不会 | 能 | 客户要向服务商多买一个名额；用户 11-11 定「输入啥账号就用啥」 |

**建议**：B + C，D 只在说明文档里提，不强制。
- 时段在连接弹窗里填一次、记住（问一次记住）；默认值留空让用户填，还是预填 20:00–07:00，交主会话定（第 12 节 #6）。
- **主动去挤别人默认禁止**：自动连只在时段内；时段外只有人在弹窗里看到事实并点「连接」才连。
- 被挤下线：当前时段内不再自动连，下一个时段开始再连。
- 时段外云端账本的直写 / 代录排队，状态沿用现有「等电脑空出来」一类的排队状态（不新增说明文案）；时段开始自动处理。
- 我们自己的验证一律遵守 20:00–07:00（泰国时间），见 11.1。

### 4.10 用户已定：发现有人在用就弹「继续 / 取消」（11-24）

用户原话（经主会话转）：「登录前知道这个账号已经有人在用……发现有人在用就弹提示呗，选择继续还是取消，这个还是比较重要」。主会话补：自动连（开机重连、定时触发）时没人能答，一律不挤，记「等人确认」并在连接页那一行显示。

**能不能提前知道（核实结果）**
- 登录前：**不能**（理由同 4.9：控件与协议没有查询现有会话的接口；服务器会话查询要 RPC / SMB 端口，拿不到；11-15 实测同账号接管时被挤一端只收到断开提示，服务器不先问任何一方）。TSplus 有无别的接口未核实，不依赖。
- 登录时：控件的事件里也没有「这是接管来的」——连接成功只有 `OnLoginComplete`；被挤的是对方，不是我们。
- **登录后立刻能知道（待真机验）**：云端那份 CC 就跑在这个会话里，白天人用的时候它也在。让它每 10 秒在内存里记一次本会话「当前连着的客户端名、连接状态、最近一次键鼠输入时刻」（`WTSQuerySessionInformation` 的客户端名与连接状态、`GetLastInputInfo`，都是本会话查询，不要管理员）。桥一连上、隧道一通，它就把「我们连上前一刻」的记录经 `ctl` 报给桥：前一刻有别的客户端连着、并且最近有输入 → 这次是挤了人。耗时预计几秒（隧道通 + 一次 ctl 往返）。
- 如实的限制：对方在这几秒里已经被断开了（服务器接管是瞬间的）；我们能做的是立刻问人、或立刻断开让对方重连回来（对方重连会再挤掉我们，原因码 3，我们不重连）。

**做法**
1. **人点的连接 / 重新登录**：连上后若核实是挤了人，连接弹窗里出提示「此云端账号刚才有人在用，对方已下线。」+「继续」「断开」。选「断开」桥立刻断开，对方可以重连；选「继续」照常工作。没挤人就不出这道题。
2. **自动连（开机、升级后、时段开始、断线重连）**：一律不挤——核实是挤了人就立刻断开，那一行状态显示「等待确认」，等人在弹窗里点「继续」（那时再连，会再挤一次，所以要人决定）。
3. 前一刻那个会话只是「已断开未注销」（人关了客户端没注销）：不算有人在用，照常连，不出提示。
4. 我们自己被挤（对方重连回来）：沿用 4.7，不自动重连，显示「被挤下线」。
5. 若真机验证发现会话里取不到客户端名或输入时刻：退回 4.9 的「可连接时段 + 时段外人手动连时弹窗先写明可能有人在用」，并如实告诉用户提前知道做不到。

### 4.11 直写是否也要占着云端会话（用户问，11-24）

用户原话：「未来业务类是不是只有代录才打开界面，直写也要吗」。

**按代码事实：要。** 直写、读主档、对账读回、代录全都要桥保持一条远程桌面连接占着这个账号；代录只是还要操作 Express 窗口。

| 环节 | 事实 | 依据 |
| --- | --- | --- |
| 云端 CC 在哪跑 | 这个账号的交互会话里，登录时由启动文件夹 `CC.lnk` 起 | `packaging/cloud_install.ps1` |
| 它怎么联网 | 只经文件隧道：桥把本机一个文件夹 `subst` 成盘，远程桌面只重定向这一个盘，云端看到 `\\tsclient\<盘>` | `cloud_link/host.py` 文件头、`nonscriptable.py` |
| 云端能不能自己上网 | 不能（11-09 / 11-15 实测；云端离线有守护测试） | 自查清单 h |
| 桥断开时 | `\tsclient` 盘随客户端断开消失，云端领单、回执、主档、读回全停 | 远程桌面盘重定向的机制；待真机验 |

**有没有办法让直写不占交互会话**

| 办法 | 可行性 | 依据 |
| --- | --- | --- |
| 断开但不注销，云端 CC 与隧道继续 | 不可行：CC 进程还在（待真机验），但隧道盘随连接消失 | 盘重定向依附在连接上 |
| 云端 CC 以 Windows 服务运行 | 不可行：要管理员装服务（我们没有，也不该在服务商主机上装）；即使有，服务也没有出路（云端不能上网，隧道又只在会话里） | 11-15 T5：只有用户目录可写、无管理员 |
| 远程桌面虚拟通道代替文件隧道 | 不解决：虚拟通道同样依附在一条连接上，仍要占会话 | 协议机制 |
| 服务商给云端主机开出站网络，云端 CC 直连站点 | 技术上可行，但要服务商改网络策略，且令牌要落到第三方主机上（与现设计「令牌不落云端」相反）；不建议 | 11-11 评估第 4.2 节 |
| 给 CC 单独一个云端账号 | 可行：两个账号各一个会话，互不挤；云端两个会话各开一个 Express 能不能同时进同一本账、名额怎么算，**要问服务商并真机验**（11-15 T3：第二个 Express 能开到登录框，名额要登录才算，没测到） | 11-15 T3 |

**引出的产品问题（给用户）**

服务商一个账号同一时间只许一个会话，所以同一个账号上做不到「人白天用 Express、CC 同时直写」。三种做法：

| 做法 | 白天能不能直写 | 会不会挤人 | 成本 |
| --- | --- | --- | --- |
| A 只在没人用时工作：单子排队，到可连接时段（如 20:00–07:00）自动处理 | 不能，排到晚上 | 不会 | 无 |
| B 人在用时由人点「继续」 | 能，但会把正在用的人挤下线 | 会（人决定） | 无 |
| C 给 CC 单开一个云端账号 | 能 | 不会 | 服务商另一个名额的费用（**要问服务商**，告知用户后再定） |

建议：**默认 A**（符合「电脑关了就排队」的口径，这台主机的规矩本来就是夜里连）；B 作为人工兜底（即 4.10 的「继续」）；白天也要直写的客户再走 C，先问服务商是否支持、怎么收费，把成本告诉用户再定。
