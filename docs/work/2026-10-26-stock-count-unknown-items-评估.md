## A. 多仓核实：「一个公司只有一个默认仓，新建的仓不可用」是不是代码现状

**结论：不是。代码在生产版和 main 上都支持一家公司多个仓，各单据都能选仓，盘点按所选的仓取结存。**
演示里觉得「新仓不可用」，有三个原因：
1. 新仓本来就是空的。商品主档不属于哪个仓，货要经入库 / 进货 / 期初「选这个仓」才会进去。
2. 新建商品弹窗里的「默认仓位」是库位（货架），不是仓库，看着像在选仓。
3. 新单据的仓库默认填「卖货的那个仓」（收银台挂的仓），要手动改成新仓。
真正缺的是岳父要的「盘哪些货」：盘点只能按仓整仓取结存，不能只挑一部分商品。

### A1. 代码证据（生产 08bfb419 与 main 4561884f 都是这样；`inventory/warehouses.py` 两个版本之间没有改动）

### A4. 建议（要不要做由主会话定）

1. 盘点新建加「盘哪些货」：按分类 / 选商品 / 只要这个仓有结存的，抄成快照。现在只有「整仓」和「上传表」两种。

## B. 盘点扫到账上没有的货

## 0. 需求原文与理解

- 原话（岳父，泰文，10-26 演示）：
  - 「เวลาเราไปนับสินค้าเราต้องจดรายการสินค้าทุกตัวที่เราเจอ」：盘点时遇到的每一件货都要记下；
  - 「สมมติว่าบัญชีส่งรายการมามีแค่สองสามรายการ แต่พอไปโกดังมีสินค้าห้ารายการ เราต้องจดให้ครบทั้งห้า แล้วมาออกรายงานว่าบัญชีมีรายการแค่สาม ส่วนอีกสองบัญชีไม่มี」：会计给的清单只有两三项，仓库实际有五项，要五项都记，最后出报告：账上有三项，另外两项账上没有；
  - 「พอเขาสแกนเข้าไปมันขึ้นรหัส เขาสามารถคีย์ชื่อสินค้าเพิ่มเติมเข้าไปได้ / หน้าจอนี้ควรโชว์บาร์โค้ดกับชื่อสินค้า」：扫码时显示条码，能补录商品名称；这一屏要同时显示条码和商品名。
- 理解：盘点员（Desk 或 LINE 手机）扫到 ERP 里认不出的码时，不报「找不到」，而是显示扫到的码，让人当场输入名称、照样记数。这份盘点最后要分清「账上有的」和「账上没有、盘点新发现的」。
- 不在本需求范围：
  - 盘点员直接建正式商品；
  - 改商品主档的编码规则；
  - 多仓「盘哪些货」（见 A4-1，另立）；
  - Express 里建商品（存货码由谁定，见第 4 节）。

## 1. 现有同类与复用

- 已有：
  - `ERP Stock Count` / `ERP Stock Count Item`（快照行：product、code、barcode、book_qty、counted_qty…）/ `ERP Stock Count Entry`（每次录数）；
  - 认码 `count.products_of_code`（码的命名空间：系统编码 / 内部编码 / Express 编码 / 条码 / 二维码 / 单位条码）；
  - 录数 `add_entry`；补行 `ensure_item`；
  - LINE 页 `inventory/line_mobile.py: api_line_stocktake_lookup`；
  - 上传导入 `apply_import`：认不出的行进「问题清单」，原因 code_not_found；
  - 差异报表 `report/erp_stock_count_variance`。
- 现状：认不出的码，Desk 和 LINE 都报 `CODE_NOT_FOUND`「No product matches this code」（`count.py:127/138/313`、`line_mobile.py` 回空 → 页面显示「找不到」）；上传导入把它放进问题清单丢掉。
- 结论：**扩展现有**。在 `ERP Stock Count Item` 上允许「没有 product、带一个扫到的码和手输的名称」的行（建议叫「待建档」行），复用同一套录数 / 合并 / 过账流程。不新建平行的盘点单据。

## 2. Frappe 原生能力

- 子表行可以不填 Link（product 改成非必填，靠服务端校验约束），原生 Dialog / FieldGroup 可以加「名称」输入，报表用原生 Script Report（已有那张加一列「账上有 / 新发现」）。
- 结论：都用原生组件，不新建页面外壳。

## 3. 按类通用

- 这一类是「按码认商品、认不出时怎么办」。同类入口还有：
  - 收银台扫码、入库 / 进货明细扫码、期初扫码：这些是做账的单据，认不出时**不应**允许造临时品，照旧报找不到或跳去建商品；
  - 盘点是唯一「记录现场事实」的入口，所以只在盘点里开「待建档」。
- 盘点里要一起覆盖的：
  - Desk 录入弹窗（输码 / 扫码枪 / 相机）；
  - LINE 手机盘点页（输码 / 相机）；
  - 上传导入：表里码认不出、但填了名称和数量的行，也进「待建档」，不再丢进问题清单。

## 4. 上下游数据

- ERP 内单据流：
  - 「待建档」行**不进库存**：没有商品就没有结存，不能过账成出入库单。
  - 盘点过账时只过有商品的行。「待建档」行要么先被确认（选一个已有商品或新建商品，变成正常行），要么标「忽略」；还有没处理的「待建档」行时，过账要拦下（或提示后只过其余行——见第 12 节问题 3）。
  - 确认成新商品时：走正式建档（`products.service.create_product`，同样受码的命名空间约束，撞码就拒）。扫到的码按形状自动放进条码或二维码栏（同 `contracts.code_field`），名称取盘点员手输的，管理员可以改。
  - 差异报表加一列「来源」：账上有（快照）/ 盘点中补的账上有商品（ensure_item）/ 新发现（待建档）。新发现的另起一节，就是岳父要的「账上有三项，另外两项账上没有」。
- Express 映射：
  - 接了 Express 的公司，商品以 Express 为准（`express.locks`），盘点写成 TK（`express/stock_entry.count_document`），明细必须带存货码；存货码为空时 CC 报存货找不到，转人工。
  - 所以「待建档」行**一律不写 Express**：确认前不过账；确认后变成有商品的正常行，按现有 TK 流程写。
  - 新发现的货要进 Express，得先在 Express 里有这个存货码。两种做法：会计在 Express 建好、同步回 ERP，再把待建档行指到这件商品（推荐，现有路径不变）；或者以后 CC 代建存货码（另立需求，不在这次范围）。
  - 不接 Express 的公司：确认时直接建本地商品，过账照常。
- CC 桌面版：**载荷不变**。待建档行不出现在任何载荷里。
- Cowork：Cowork 也有盘点页（`cowork.page.stocktake`），是否同步加，见第 12 节问题 5；DMS 不涉及。

## 5. 隔离与权限

- 记录待建档行：有 `count.write` 的人（盘点员）就可以；LINE 页走现有票据身份。
- 把待建档行「确认成商品 / 忽略」：要 `products.manage`（建商品），或至少 `count.write` 加选已有商品——由服务端拦，不靠前端隐藏。盘点员不能顺手建主档（主会话倾向，我同意）。
- 隔离：
  - 待建档行挂在盘点单上，盘点单挂仓，仓属于公司，天然按公司隔离；
  - 扫到的码先按这家公司「看得见」的范围认（`products_of_code` 已按公司），认不出才进待建档；
  - 别家公司 Express 里有这个码，不算这家认得，也不提示别家商品名（同 a20f33b2 撞号口径）。

## 6. 入口：网页、手机、LINE、拍照

- Desk 录入弹窗：认不出时，在原弹窗里显示「扫到的码」（只读）+「名称」（必填）+ 数量，保存成一条待建档记录。相机是共用件，不改相机本身，只改认码失败后的分支。
- LINE 手机盘点页：同样的三栏，用页面现有的原生控件样式；按「相机权限三步」，不改相机流程。
- 上传导入：模板不改；认不出的行里有名称就进待建档，没有名称仍然进问题清单。
- 多人同时扫到同一个未知码：**按「这份盘点 + 这个码 + 仓 + 库位」合并成一行待建档**，两人的录数各记一条 Entry、合计成实盘数（同现有「多人分区盘点」口径，`recorded_entries` 能显示谁记过）。名称以先录的为准，后来的人看得到、可以改（改动留在 Entry 上）。
- 窄屏：Desk 弹窗原生自适应；LINE 页本来就是手机页。

## 7. 共用件与连带回归

`check-impact.py --files count.py line_mobile.py stocktake.html stocktake-entry.js express/stock_entry.py` 命中共用件 `erp-count-code`（盘点按码认商品），要实测的入口：

- `erp.stock-count.code`：录入弹窗输码 / 扫码、上传导入、LINE 盘点；
- `erp.page.stock-count`（自动冒烟）；
- `erp.line.stocktake`、`erp.line.stocktake.camera`、`erp.line.stocktake.liff-camera`、`erp.stock-count.entry.camera`；
- `erp.scan.pick-product`（撞号候选弹窗：待建档只在「一件都认不出」时才出，认出多件仍弹候选）；
- `erp.stock-count.upload`、`erp.cc.stock-entry`（TK 不带待建档行）、`erp.cc.stock-void`；
- `erp.records.scope`、`erp.browser-text`、`shared.page-errors`。

新入口要补进登记表，例如 `erp.stock-count.unknown-item`：扫未知码记待建档 → 确认 / 忽略 → 过账 → 报表分两节。冒烟加一条：造一个不存在的码，录两人各 2 → 合并成 1 行实盘 4 → 确认成新商品 → 过账 → 库存 4。

## 8. 存储与成本

- 每份盘点多几行子表 + 每次录数一条 Entry，量级和现有盘点一样；没有识别、没有 LINE 推送、没有云存储新增。凭证照片沿用现有「最多 5 张、走原件层」。
- 没有新增固定月费。

## 9. 删除、作废、追溯

- 待建档行在盘点过账前可以删；单条 Entry 照现有「撤销」。
- 盘点过账后，待建档行保留「新发现 → 确认成 xx 商品 / 忽略」的结果，留谁、什么时候处理（审计）。
- 待建档行不写 Express，作废时不涉及 Express。确认后生成的正常行跟现有 TK 作废流程走。

## 10. 文案与官方 UI

- 新增文案（预计）：「新发现」「待建档」「扫到的码」「商品名称」「确认建档」「忽略」「还有未处理的新发现商品」，报表分组标题「账上有」「新发现」。泰文的「新发现」请用户 / 岳父过目。
- 不改已有文案。A4-2 的「默认仓位」另议。
- 官方组件：Dialog / FieldGroup / Grid / Script Report；LINE 页沿用现有原生样式。

## 11. 测试与验收

- 单元测试：
  - 认不出 → 待建档；
  - 两人同码合并；
  - 别家公司 Express 码不算认得；
  - 确认时撞码被拒；
  - 有未处理行时过账被拦；
  - 忽略后能过账；
  - 报表分组；
  - 权限：盘点员不能确认建档。
- 实验栈：Desk、LINE（手机 adb 真机）各走一遍；接 Express 的公司确认后过账写 TK 并读回；不接 Express 的公司全流程。

## C. 待问：「去商品验收页面（ตรวจรับสินค้า），这个可以改吗？」

- 演示原话：「อ่ะไปหน้าจอตรวจรับสินค้า / อันนี้เราสามารถแก้ไขได้ไหม」（去商品验收页面 / 这个我们可以修改吗）。用户当时答的是多仓逻辑，没回答改什么。
- 「ตรวจรับสินค้า」在 ERP 里大概对应「入库」或「采购收货（收货单）」页面。要问清两点：
  1. 指哪个页面：入库，还是采购单的收货；
  2. 想改的是什么：已提交的单能不能再改，还是页面上的某个栏位（例如仓库、数量、单价）。
- 现状供参考（代码核对）：
  - 入库单只有草稿能改，提交后要作废重开（`inventory/documents.py: update_entry` 只认 draft）；
  - 采购单提交后可以「更正」：生成一张新单接替原单（`purchasing/entry.py: _post` 的 amended_from）；
  - 接了 Express 的单作废时，走 Express 原生作废。
