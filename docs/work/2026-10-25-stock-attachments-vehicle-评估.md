# 第一部分 库存单附图片 / 拍照

## 0. 需求原文与理解

- 原话（岳父 LINE，10-25，主会话转）：ระบบสินค้าและสต็อก เมนูรับเข้า เมนูจ่ายออก ให้สามารถแนบไฟล์ภาพหรือถ่ายรูปแนบได้ด้วยครับ
  ——「库存的入库、出库菜单，要能附图片文件或直接拍照附上」。
- 理解：仓管在 ERP 网页（电脑、手机）开一张入库单或出库单时，能从相册 / 文件选图片，或当场拍照，挂在这张单上；以后打开这张单能看到、能下载。
- 不在范围：识别图片内容（不调识别、不扣费）、把图片写进 Express、LINE 发图建库存单（列为待问）、给采购 / 销售单加附件（已经有）。

## 1. 现有同类与复用

| 同类 | 位置 | 能不能复用 |
| --- | --- | --- |
| 采购 / 销售上传框 | `P/public/desk/purchase-entry.js:55`（`u.upload_evidence`）、`sales-entry.js:88`：官方 `frappe.ui.FileUploader`，`allow_take_photo: true`、只收 `image/*` 和 `.pdf`、单件 20 MB、私有 | **直接复用**：同一套参数、同一个拍照（框架自带 `frappe.ui.Capture`，手机调系统相机，电脑走共用相机 `C/public/desk/scan.js:67-72`） |
| 上传去向 → 原件层 | `P/public/desk/erp-originals.js`（`p.erp_upload_with` / `p.erp_upload_original`，签名直传 + 经服务器两条路）；服务端 `P/recognition/originals.py`（`CAPABILITY` 只有 purchase / sales） | **扩展**：服务端加 `stock_in` / `stock_out` 两个方向，权限分别要 `stock.in` / `stock.out` |
| 上传前压缩 | `C/public/desk/product.js:379-415`（`p.shrink_photo`：转正、长边 > 2400 缩到 2400、JPEG 0.92；参数 `C/desk/upload.py:10-11`） | **直接复用** |

| 盘点记录照片 | `P/public/desk/stocktake-entry.js:121-136` + `P/inventory/count.py:650-687`：原生 FileUploader，**不压缩、不走原件层、存生产本机**；LINE 手机盘点页 `P/www/stocktake.html:283` base64 单张 1 MB | 同类但做法不一致，见第 3 节 |

结论：**扩展现有**，不新建上传组件、不新做相机。

## 2. Frappe 原生能力

- Frappe 16.33.0 原生 `File` 附件（`attached_to_doctype / attached_to_name`、`is_private`）+ 官方 `FileUploader`（含拍照）。库存单详情是自写页面（`P/public/desk/stock-entry.js`，`p.dialog` + 整页 `p.layout`），不是原生 Form，**没有原生侧栏附件区**；附件区用官方控件组合（FileUploader + 列表），不另做 UI。
- 原生 Form 侧栏不能直接用：`ERP Stock Entry` 的 `has_permission` 对 write 一律返回 False（`P/inventory/access.py`，只有服务层 `write_entry` 能改），侧栏的「添加附件」会被拒。挂接必须走服务端接口（同采购）。

## 3. 按类通用

- 这一类 = **所有库存单**。实际 DocType：`ERP Stock Entry`（入库 `direction=in`：退货 return / 其他 other；出库 `out`：领用 internal_use / 报损 damage / 其他 other）。仓库里**没有调拨、采购退货单**（主会话口径里的「调拨、退货」：退货 = 入库 return；调拨不存在）。
- 一起覆盖：入库、出库的全部用途（一套代码，按 direction 判权限）。
- 盘点：盘点记录已经能附照片，但不压缩、不进原件层、存生产本机。**建议同一步对齐**：盘点照片改走同一套上传（压缩 + 原件层），LINE 手机盘点页同样先压缩再传；不改盘点业务规则。属于「按类修」，否则同一类两种存法。
- 期初（`ERP Stock Opening`）是导入批次，不是单据，不加。
- 不覆盖：采购 / 销售（已有）、收银小票（无需求）。

## 4. 上下游数据

- ERP 内：附件只挂在库存单上，不影响库存流水、收发存、对账、同步对齐。作废单据附件照留。
- Express：**不写**。Express 没有单据附件；CC 载荷不变（仍是第 6 版库存单载荷），旧版 CC 不受影响。
- CC 桌面版：不涉及。
- Cowork / DMS：不涉及；原件层是三产品共用件（只加调用方，不改它）。

## 5. 隔离与权限

- 上传：服务端按方向要 `stock.in` / `stock.out` 能力（`P/access/guard.py`），并核单据所在仓属于当前可用公司（`scope.warehouse_allowed`，同 `P/inventory/access.py:13-17`）。
- 挂接：只能挂本人刚上传、私有、没挂过的 File（采购同规则）；只能挂到自己有写权限的单。
- 查看 / 下载：跟着单据读权限（`entry_permission`）；原件层下载走登记 File 的私有下载（`C/originals/registered.py` 的 `redirect_download`），不出公开地址。
- 跨公司：库存单没有 company 字段，公司由仓推出；附件的读写校验都以单据的仓为准，不会串。

## 8. 存储与成本

- 单件：手机照片压到长边 2400、JPEG 0.92，实测量级约 0.6–1.5 MB / 张（原件层另生成一张预览图，约 0.1 MB）；PDF 原样，上限 20 MB。
- 量的估算（偏高口径）：一家公司每天 30 张库存单 × 平均 2 张 × 1.2 MB ≈ 72 MB / 天 ≈ 2.2 GB / 月。
- 去向：生产租户都走 Claude 路线 → 原件层存**甲骨文**（`C/originals/store.py:18-24`）。甲骨文盘剩约 177 GB、不另收费；按上面口径**一家重度公司约 6–7 年用满，10 家约 8 个月**——这是容量风险，不是月费。若走谷歌桶：0.020 美元 / GiB·月，每家每月新增约 0.04 美元。
- 建议：每张单附件上限 10 个（同盘点 5 张的量级，略放宽）；不另降压缩参数（与采购同一套，改了要动共用件）。甲骨文剩余空间纳入外部守望（已有 `/opt/pearnly-watch`）的阈值提醒，属于运维跟进，不挡本需求。
- 生产只留登记（< 1 KB / 张）；无新增固定月费。

## 9. 删除、作废、追溯

- 库存单不能删除（服务端只允许 insert / save，`P/inventory/access.py:27-38`），只能作废：**作废保留附件**。
- 单张附件删除：草稿单可删；已提交单是否允许删附件 → 待问（第 12 节），建议「只能加不能删」以留证据。
- 删附件 = 删登记 File，提交后原件层后台删存放处那份（`RegisteredFile.on_trash` → `registered.purge` → `store.delete`），记录与存储一起真删。
- 追溯：File 自带上传人、时间；不另加审计表。

## 10. 文案与官方 UI

- 用官方现成词：「附件」用 Frappe 自带 `Attachments`，上传框文案全是 FileUploader 自带；不加说明文字。
- 可能新增的一条：附件数到上限时的报错（例：「最多 10 个附件」），按官方风格新写，过 `scripts/check-copy.py`。
- 组件：FileUploader、原生列表 / 链接；无自定义样式。

## 11. 测试与验收

- 单元：方向与权限（无 `stock.out` 不能往出库单传 / 挂）、跨公司仓拒绝、挂别人的 File 拒绝、上限、作废后仍可读、删附件触发 purge。
- 冒烟：第 7 节两条 + 采购 / 销售上传回归。
- 实验栈：手机（三星测试机经 adb）在入库 / 出库各拍一张、选一张 PDF；电脑假摄像头拍一张。
- 验收复核：验收窗口；用户只需看手机上拍照挂单是否顺手。

# 第二部分 车辆四项

## 0. 需求原文与理解

- 原话（岳父，10-25）：ERP「新增商品」加四栏——可手输的商品编码、รายละเอียดเพิ่มเติม 1 / Chassis No、รายละเอียดเพิ่มเติม 2 / Engine No、สี（颜色）。
  主会话后补：保留自动编码，另加「内部编码 / รหัสภายใน」（扫码、搜索、盘点都认，盘点界面显示）；汽车要车架号、发动机号、颜色、车型；做成通用；盘点 Excel 模板支持；库位要补。
- 理解：卖车类（也可能是手机、电器、设备）的公司，商品要有自己的编码规则，每一台要能记车架号 / 发动机号 / 颜色，进货登记、卖时选台、盘点扫台、税票上印号。
- 不在范围：金融公司开票、赠品、代收上牌费 / 强制险、订车标准合同（调研七.5，销售单据结构，另立需求）。

## 1. 现有同类与复用

| 同类 | 位置 | 结论 |
| --- | --- | --- |
| 商品编码 | `ERP Product.code`，系统发 `P-` + 6 位（`P/products/service.py:180-188`），界面只读（用户 2026-09-22 定「编码由系统发、不给手输」） | **不改 code**；另加「内部编码」字段，避免推翻 09-22 口径 |
| 批次 / 有效期 | 商品两个勾选 + 采购行、库存单行的 `batch_no`，库存账无批次维度 | 「按台管理」照它的位置加勾选；但按台需要独立档（批次只是行上文字） |
| 扫码认商品 | `P/inventory/count.py:88` `product_of_code`（code / barcode / qr_payload） | 扩展：加内部编码，认不到再认序列号 |
| 盘点模板 | `P/inventory/workbook.py:19` | 加列 |
| Express 附加说明 | CC 没有写 `ARTRNRM` 的代码 | 新建（第 4 节） |

## 2. Frappe 原生能力

- 站点不装 ERPNext（用户 2026-09-21 定），**原生 Serial No / Batch 不可用**；装 ERPNext 会带进整套业务 DocType，违背现有架构。
- 用 Frappe 原生 DocType 自建「ERP Serial No」（Link、唯一索引、原生列表 / 表单），不自研 UI。

## 3. 按类通用

- 一类 = **按台 / 按号管理的商品**：汽车、摩托车（车架号 + 发动机号 + 颜色）、手机（IMEI 1 / 2）、电器 / 医疗器械 / 设备（S/N；S 盘 GISS、GIZE、BP Siam 已在 Express 附加说明里记 S/N）。
- 「内部编码」对所有商品都有用（扫码、搜索、盘点），不限车辆。
- 不开按台管理的商品（批发、零售）只多一个可空的内部编码栏，行为不变。

## 4. 上下游数据

- ERP 单据流：进货行登记台（数量 = 台数）→ 库存流水仍按商品；销售行选台（一台一行）；作废把台状态退回；盘点按台扫；库存单出入同样选台。按台记录只跟着单据变状态，**不改 `ERP Stock Movement` 结构**。
- Express 映射（调研结论）：
  - 内部编码：接了 Express 的公司 = Express 商品编码 STKCOD（回读、只读，并进 `P/express/locks.py`）；ERP 本地新建、手输了内部编码的商品，CC 第一次写 Express 时用它当 STKCOD（冲突停人工，不自动改码）；没接 Express 的公司手输，按公司唯一。
  - 车架号 / 发动机号 / 颜色：Express 商品主档没有这些字段，`ISSN` 表没人用、SERIAL 只有 15 位放不下 17 位车架号；S 盘惯例写在单据附加说明表 `ARTRNRM`（`DOCNUM + SEQNUM + REMARK C(50)`，挂在行下，进货销售共用）。CC 照惯例写，ERP 自有、不回读、不锁。
  - **`ARTRNRM` 的行号对应和打印位置未实测**，已放进 C 盘录单清单第 7 条（`docs/work/2026-10-25-express-c-drive-recording.md`），实测前不写代码。
- CC 载荷：写 `ARTRNRM` 要在行结构加 `remarks`，并让 CC 用给定内部编码建 STKCOD → **升载荷版本**（出入库 B 段占第 6 版、B 段剩余部分占第 7 版，这里是第 8 版），旧版 CC 诚实拒收（`CC/payload_contract.py`）。
- Cowork：共用写账路径（`C/express_rules/push/`）加行说明，Cowork 推送全类型要回归；DMS 不涉及（`apps/pearnly_dms` 接品牌 DMS，和 ERP 无关）。

## 5. 隔离与权限

- 内部编码按公司唯一（`internal_key = 公司|内部编码` 唯一索引，同 `code_key`）；序列号按公司 + 主号唯一。
- 序列号档带 company，读写权限跟商品 / 单据（服务端 `has_permission` + `permission_query_conditions`，按当前公司）。
- 不同公司可以有同一个车架号记录（理论上不会，但不跨公司校验，避免泄露别家数据）。

## 6. 入口：网页、手机、LINE、拍照

- 网页 / 手机：新增商品窗口加「内部编码」「按台管理」；进货 / 销售 / 库存单行选台；盘点扫台。
- 扫码：用现有共用扫码（`C/public/desk/scan.js`），Isuzu 标签二维码 = 车架号，直接认到台。
- LINE：采购识别行加三个号（厂家进货单通常逐台列号）——放最后一步；拍车辆标签识别属于新增识别调用、有成本，用户同意才做。

## 7. 共用件与连带回归

- `product_of_code` 是扫码共用入口（商品页、盘点、收银台、采购 / 销售行、库存单行），改它要逐入口实测（10-15、10-23 扫码事故）。
- CC 写账共用路径（`cc-dbf-write`）、共用推送规则层（`express_rules`）：加行说明要跑 101 本 T 账套离线回归 + Cowork 全类型回归。
- 新入口登记：商品内部编码、序列号选台（采购 / 销售 / 库存单 / 盘点各一条）。

## 8. 存储与成本

- 数据量小（每台一行，几十字节）；无外部调用，无新增月费。LINE 拍标签识别若做，按每张约 ฿0.2 估，用户批准再做。

## 9. 删除、作废、追溯

- 单据作废：台状态退回「在库 / 未售」；序列号档不随单据删除。
- 序列号录错：未被单据用过的可删；用过的只能改状态（作废），保留追溯。
