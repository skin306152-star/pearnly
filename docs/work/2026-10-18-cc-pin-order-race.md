# CC 侧栏：别的设备排好的置顶顺序被旧对话列表收拾掉（10-18）

来源：测试窗口 10-18 在测试机实测 + lab 日志定位，开发窗口派工。分支 `pearnly/cc-pin-order-race`（工作树
`.claude/worktrees/cc-pin-order-race`），基线 main `ae7cd867`。只改 CC 前端（`frontend/assistant`），没有文案改动。

## 现象与证据

- 手机上把几条对话置顶并排好置顶先后（服务端 `order.pinned` 5 条）；一直开着的电脑（对话列表是旧的）拿到焦点 / 回前台后，
  服务端 `order.pinned` 被改回只剩 1 条。置顶标记本身没丢（对话的 `custom.starred` 还在），丢的是手机排好的置顶先后。
- lab 日志：02:28:43 手机最后一次 `save_layout` 回 506 字节；02:29:39 电脑提交一次 `save_layout`，回 448 字节。

## 根因（核实：与开发窗口的判断一致，另查出同类三处）

1. `thread-list.tsx` 的 `CompanyGroups` 里那个收拾副作用按**本页对话列表**的置顶标记算谁「已取消置顶」，再
   `forgetPinned(gone)`（按数据收拾，tidy）。
2. 电脑窗口一直可见：拿到焦点只让 `prefs-sync` 重取布局（`focus` 监听，隔 `REFETCH_AFTER` 10 秒以上）；侧栏同步
   `list-sync` 的核对只在 `visibilitychange`、`pageshow`、`online`、实时通道重连时做，**不听 `focus`**。于是布局是新的（含手机
   刚置顶的几条），本页对话列表还是打开时读的（推送漏了时那几条仍标着没置顶）。
3. `prefChanged(..., tidy=true)` 只看布局刚取过（`TIDY_FRESH` 2 秒内）就存，没看收拾所依据的对话列表是不是比布局新。
   改前的代码上新用例 1 存出 `{ order: { pinned: ["s1"] } }`，就是 lab 里电脑那一次提交的形态。

同类（都核实了，一并改）：

- `forgetInGroups(left, true)`（置顶了的从组里手排的先后里去掉）：手机取消置顶 X、把它放回组顶并存上；电脑本页 X 还标着置顶，
  就把 X 从组里去掉、存上，手机放回组顶的被撤掉。改前用例 2 存出 `{ order: { "group:": { keys: ["s7", "s8"], at: 100 } } }`。
- `forgetGroups`（侧栏没有这家公司了，整组去掉）：依据是公司列表。手机在侧栏还没有的公司开第一段对话、排了这一组；电脑的公司
  列表是旧的，就把这一组存成 null 删掉。改前用例 5 存出 `{ order: { "group:CO-Z": null } }`。
- 回前台核对（`list-sync` 的 `reconcile`）的漏处：第一页带全部置顶的，但本页标着置顶、又不在这一页里（很旧）的对话原来不改，
  核对后仍标着置顶。按新规则核对过的列表算作新的依据，这一处不补，同样会把别的设备放回组顶的去掉。改前用例 3 里它仍是置顶。
- 第 10 轮 B 段的 `starPending` 管的是本机请求还没回时的乐观更新，这次是另一条路径（依据本身旧），不重叠。

## 改法

原则：按数据收拾、要存到服务端的改动，所依据的每一份数据都不能比被改的那份布局旧。

- `lib/prefs-sync.ts`：记下本机这份布局是哪一次请求取的（`askedAt`，请求发出的时刻）。新 `tidyBasis(seen)`：依据（`seen`：
  读到它的那次请求发出的时刻）不早于 `askedAt`，并且这时收拾就能存上（知道是谁、没在取、刚取过），或者依据是 `TIDY_FRESH`
  内刚读到的（先取一次布局，换进来以后照这次的判断再收拾、那时再存）。`prefChanged` 回会不会存上；`clock` 导出给各处同一个钟。
- `lib/managed-agents/sidebar-order.ts`（「按数据收拾」一节）：
  - 每一行的依据时刻：读第一页（打开、重拉列表、回前台 / 联网 / 重连的核对；第一页带全部置顶的）把本页每一行对到那次请求
    发出的时刻（`noteListRead(at)`，后读完的为准）；推来的置顶变化、本机置顶 / 取消置顶得到服务端确认、别处删掉的只对到那几行
    （`noteListRead(at, keys)`）。公司列表看 `projects.ts` 的 `projectsSeen`。
  - `forgetPinned`、`forgetInGroups(…, true)`、`forgetGroups` 每一条按它的依据判断。依据不够新的这次不收拾，**本机也不改**：只改
    本机的话本机这份就少了它，对话列表更新以后它照样是置顶的，却排到了最上面（跟手机排的不一样）。
  - 依据够新、要先取一次布局才能存的，记下这几条（`tidied`，`TIDY_TTL` 30 秒内）：布局换进来、侧栏照新的那份再收拾时，它们照
    这次的判断收拾、存上去。本机取消置顶（`unpinChat`）、置顶（`starChat`）照旧当场收拾，依据是本机刚得到的服务端确认。
- `lib/managed-agents/session-list-adapter.ts`：读完第一页记 `noteListRead`（重拉时只认最后发出的那一次；置顶的到服务端上限
  100 条时不记）；别处删掉的记那一行。
- `lib/managed-agents/list-sync.ts`：推来的置顶变化记那一行；回前台等时刻的核对读完第一页记一次；核对时本页标着置顶、不在第一页
  里的换成没置顶（本机置顶请求还没回的不算）。
- `lib/managed-agents/projects.ts`：记最近读完的一次公司列表是哪一刻发出的（`projectsSeen`）。
- `components/assistant-ui/thread-list.tsx` 没改：收拾副作用照旧调这三个函数，依据在函数里查（方便 `pearnly/cc-drag-engine` 变基）。

### 「旧」怎么判定、为什么稳妥

- 拿到焦点时对话列表不重读：依据停在上一次读第一页，比刚取的布局旧，这次不收拾（宁可不存，不拿旧数据盖服务端）。
- 按请求发出的时刻比：依据要在取这份布局的请求发出以后才读。回前台时侧栏同步先重取公司、再读第一页，第一页总在布局请求之后
  发出；两份请求在同一轮来回里交错的窗口，跟原来 `TIDY_FRESH`（2 秒）同一量级。
- 宁可不存的代价：服务端置顶顺序里留着已经不置顶的编号（不显示；以后再置顶回到旧位置而不是最上面）、组里留着已置顶的编号
  （不显示）、留着侧栏已没有的公司组（不显示，服务端按上限截）。发起的那台设备自己的收拾照旧当场存，正常不会留下。

## 已知限制 / 没做

- 一直开着、只拿到焦点的电脑：侧栏仍显示旧的置顶标记（手机新置顶的几条不在「已置顶」里），要等回前台（最小化再打开、切走再
  切回）、联网、实时通道重连或收到推送才更新。服务端的顺序不再被盖；本机这份布局是新的，列表更新后照手机排好的先后显示。
  拿到焦点也核对列表（同 `prefs-sync` 隔 10 秒以上）是产品取舍，本次没做；也没加实时推送。
- 只在本机测试脚本里验证；测试机 lab 复测、推送、合并、部署都没做。

## 测试窗口复测步骤

1. lab 同步本分支实时源码，CC 前端是构建产物，带 `PEARNLY_TESTENV_LOCAL_SPA=1` 一起同步；先从外部读回确认 `index.*.js` 是新包。
2. 电脑（浏览器窗口，一直可见；CC 桌面版用第 3 步里断网的做法）与手机同一账号打开 testcowork，各自刷新一次。
3. 让电脑漏掉推送：电脑浏览器开发者工具 → Network → 拦截 `*socket.io*`；或者先让电脑断网，手机做完第 4 步再联网（联网时布局与
   列表同时重取，布局先回来的那一下就是这次的情形）。
4. 手机：置顶 4–5 条对话，拖着排好置顶先后，等 1 秒。
5. 电脑：等 10 秒以上，点一下窗口让它拿到焦点（不最小化）。lab 日志里电脑这时不应再有一次把置顶顺序变短的 `save_layout`；
   手机刷新，置顶先后仍是手机排的。
6. 电脑：最小化再打开（触发回前台核对），「已置顶」照手机排好的先后显示那几条。
7. 同样漏推送的条件下再测两条：手机取消置顶一条（它回到所在组的组顶）→ 电脑拿到焦点 → 手机刷新，它仍在组顶；手机在侧栏还没有
   的公司开第一段对话并在组里拖排 → 电脑拿到焦点 → 手机刷新，这一组的手排还在。
8. 回归（不漏推送）：电脑取消置顶一条，手机刷新后它不在置顶里、在组顶；拖动置顶顺序、组里排序、多选取消置顶两端照常同步。
