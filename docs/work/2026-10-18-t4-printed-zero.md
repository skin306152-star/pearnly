## 结论

1. **真实件上规则做对了，没有一张拆错。** 13 张会拆的（G 组油票 9 张、收据 1 张、ABB 照片 3 张）在独立金标里税额都是「票面没印」（null），按 ABB 价含 VAT 拆 7/107 正是规则本意；
   64 张不拆的都读出了票面印的税额（G 组 7 张与金标逐张相同；S 组 57 张都是 VAT 7% 含税小票）。M4089b2bf（部分免税商品，印 VAT 2.81）读出 2.81、没拆，也对。
2. **「票面印 0」这一支在 Claude 路线上不会生效（结构问题，真实件里没撞上）。** Claude 路线的识别结果 `source_refs` 恒为 `{}`（`ocr/execution/claude.py: invoice`），
   `_vat_printed` 永远取不到原文，`printed_zero` 永远是 False。Claude 的读法口径是「没印给 null，明确印了 0 才给 "0.00"」（`claude_ocr/spec.py`），
   所以票面印 0 的 ABB 会读成 `vat="0.00"`，照样被拆。按 Claude 路线的字段形状离线核（`pages.included_vat`，零费用）：
   `vat="0.00"`、没写免税字样 → `split` 112.15 + 7.85（错拆）；同一张带 `source_refs.vat.source_text="0.00"` → `vat_printed_zero`；备注里有 `VAT-exempt` → `no_vat_marked`。
   也就是说，现在挡住「印 0 被拆」只靠备注 / 品名里刚好写了免税字样。
3. **谷歌路线（生产默认）同样基本取不到来源**（读代码与回放库，未调谷歌）：看图读的提示词 `IMAGE_SYSTEM` 不要 `source_refs`，而且口径是「vat "0" 只在票面没印 VAT 时给」，
   印 0 与没印分不开；测试机共享回放库 313 份谷歌识别结果（含金标 215 份）没有一份带 `source_refs`。只有走 `L2_SYSTEM` 的表格 / PDF 文字层读法会写来源。
4. **真实频率很低**：这批 77 张简式税票、金标 215 份里都没有一张「票面税额印 0」的 ABB（金标里唯一印 0.00 的 6901973 是收据，Claude 归成 `receipt`，不走拆税规则）。
   全免税商品的 ABB（蛋、蔬菜之类）在这批语料里没找到，第 2 条目前是推出来的问题，不是实测出来的。

## 错在哪类、建议（未施工）

- 错的一类只有一种：**Claude 路线 / 谷歌看图路线上票面税额印 0 的简式税票**（全免税商品小票），会被按 7/107 拆出不存在的税额；判据缺的是「税额印着 0」这条原文，
  不是规则本身的条件。
- 一次到位的修法（只动 Claude 路线，零成本）：Claude 读法本来就区分「没印 null」与「印了 0.00」，`claude.invoice` 在读出的 `vat` 是明确的 0 时把它记进
  `source_refs.vat.source_text`（或 `_vat_printed` 认 Claude 读法的显式 0），`printed_zero` 就能生效；补一条「Claude 字段形状 + vat "0.00" 不拆、vat null 照拆」的测试。
  谷歌看图路线读法口径分不开两种情况，要改提示词才行（会加输出、要过金标闸门），按「没有实测问题不加成本」暂不建议。
- 按「只修实际问题」的口径，这两条都等有真实件撞上再定；开发窗口要做时先做 Claude 那条。

## 限制

- 印 0 的真实样本为 0 张，第 2 条只用代码与构造字段验证，没有真实件上的「错拆」实例。
- SM 组只证明「印了税额的含税小票不拆」，没逐张核税额读数（10-17 Claude 评测已核过 SM 86 张 0 / 238 格错）。
- P 组 120 张照片没有一张被认成简式税票，说明 06 语料的进项照片几乎都是完整税票 / 收据；要专门找全免税 ABB 需另选语料（超市生鲜小票等）。
