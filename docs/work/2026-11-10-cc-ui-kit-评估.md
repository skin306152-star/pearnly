> 主会话 local_e395dace 11-10 派活；分支 `pearnly/cc-ui-kit-af5f7a`，基线 `81ec70ae3`（= 当时 origin/main）。
> 选型调研见分支 `pearnly/frontend-selection-3b576d` 的 `docs/work/2026-11-10-cc-frontend-selection.md`。

## 0. 需求原文与理解

- 原话（用户 11-10，主会话转达）：「我不重构」，但要一套大厂的标准 UI 组件——把整套组件搬进我们的库，我们直接引用，而不是每个组件自己发明、自己写；拍板「搬」。消息状态层这次不换。
- 理解：在 `frontend/assistant/` 里立一套**唯一的**标准组件库（来源 shadcn/ui），以后 CC 界面上的按钮、弹窗、菜单、表格、输入框、勾选、单选、页签、提示、徽章、消息、附件、工具步骤、提问卡等一律从这里取；现有界面一行不动，**改到哪换到哪**；加检查拦新的手写通用组件，存量登记基线、只许减少。
- 不在范围：不换状态层（assistant-ui 的 runtime、`lib/managed-agents/` 不动）；不改任何现有界面的外观与行为；不碰服务端；不顺手把现有手写组件换成新组件（那是以后各窗口改到哪换到哪）。

## 1. 现有同类与复用

- 现状：CC 已有一套「CSS 类型」的设计系统——`globals.css` 约 200 个 `cc-*` 类（Claude 实测值，用户 10-17 定的 ccs 标准，`docs/development/ccs.md`），组件里手写 `<button className="cc-btn">` 这样用；`components/ui/` 只有 6 个 React 组件（dialog、menu、tooltip、sidebar、skeleton 是早先 shadcn 拷进来再改写到标准的，drag、marquee 是自写）。**没有 Button / Input / Checkbox / Table 这类 React 组件**，所以每个窗口都在手拼。
- 手写数（`components/ui/` 以外的 .tsx，基线候选）：`<button` 150 处 / 31 个文件，`<input` 8，`<select` 5，`<table` 3，`<textarea` 1，手写 `role="switch|radio"` 2；直接从 `radix-ui` 引底层件的 7 个文件（6 个手拼弹窗、1 个手拼页签）；直接写通用外观类：`cc-btn` 38、`cc-card-btn` 29、`cc-icon-btn` 20、`cc-row-btn` 20、`cc-alert` 14、`cc-chip` 10、`cc-input` 9。
- 结论：**扩展现有 `components/ui/`**，不另开第二个目录。现有 5 个 shadcn 来源的件（dialog、menu、tooltip、sidebar、skeleton）保留原导出、原行为，只补 shadcn 有而我们没有的子件；新组件按 shadcn 的文件名、导出名、属性名进来，**外观映射到现有 `cc-*` 类**（换上之后视觉零变化），缺的类在 globals.css 新开「标准组件」一块补，数值只引用现有刻度层。

## 2. 「原生」能力（本需求对应：上游 shadcn/ui 原样）

- 来源：shadcn-ui/ui 仓库 `apps/v4/registry/bases/radix/ui/*.tsx`，**锁定提交 `8ab27715521cbd4f87ae6886cd989cbb678f6de7`（2026-11-08）**。选「bases/radix」这一版的原因：它是 shadcn 新版的「结构 + 语义槽类名（`cn-button`、`cn-button-variant-ghost` …）」写法，数值全在单独的主题 CSS（上游 `style-vega.css` 等），正好对上我们「数值只在 globals.css」；底层是 `radix-ui`，我们已锁 1.6.5，不引第二套底层（不用 `@base-ui/react` 那一版）。
- 搬法：按文件手工拷入（不跑 shadcn 命令，守 `components/NOTICE.md`「不用命令整份重新生成」），每个文件头登记上游路径与提交；`cn-*` 槽类名改成 `cc-*`（与现有类同名的直接用现有类），上游写在组件里的 Tailwind 数值（`h-9`、`gap-1.5`、`duration-200`、`opacity-50`、`[contain-intrinsic-size:…]`）改成变量写法，过 `check-frontend-tokens.py` R1–R15；`IconPlaceholder` 换 lucide 图标；`cn` 用现有 `lib/utils.ts`。
- 必须自定义的：外观（照 ccs，不用 shadcn 默认黑白灰的数值）；英文文字换词条（第 10 节）。

### 搬哪些（新增 37 个文件，现有 5 个补子件）

| 类 | 组件 | 备注 |
|---|---|---|
| 按钮 | button、button-group、toggle、toggle-group | Button 的 `variant` 一一对应现有按钮类：文字按钮 `cc-btn`、卡片按钮 `cc-card-btn`（次 / `primary` 主）、图标钮 `cc-icon-btn`、行尾钮 `cc-row-btn`、链接 `cc-link-btn`；toggle-group = 现有分段 `cc-op-seg` |
| 弹层 | dialog（补 Header / Footer / Description）、alert-dialog（删除确认）、sheet、popover、tooltip（现有）、dropdown-menu（并入现有 `menu.tsx`，保留翻边 `pickSide`） | 遮罩 `cc-overlay`、进出场 `cc-pop`、层级在调用处给，照 ccs |
| 表单 | input、textarea、input-group、label、field、checkbox、radio-group、switch、select、native-select | switch 外观 = 现有 `cc-switch`；checkbox / radio 是新类（复核卡要用） |
| 展示 | table、card、badge、alert、empty、item、separator、avatar、kbd、progress、skeleton（现有）、spinner、collapsible、tabs | table = `cc-table`，tabs = `cc-tabs`，alert = `cc-alert`，empty = `cc-empty`，kbd = `cc-kbd`，spinner = `cc-spinner` |
| 侧栏 | sidebar（现有，已是改写过的 shadcn 版） | 不换，只登记 |
| AI 对话 | message、bubble、attachment、trace（工具步骤）、questionnaire（提问卡）、code-block、marker | 都是展示件，不碰 assistant-ui 的运行时；questionnaire 的逻辑在 `@shadcn/react/questionnaire`（单选、多选、其他、上一题 / 跳过 / 下一步、翻页） |

### 不搬（写明理由）

| 组件 | 理由 |
|---|---|
| message-scroller（滚动跟随） | 对话视口现在由 assistant-ui 的 `ThreadPrimitive.Viewport` + `lib/follow-scroll.ts` 管（用户 10-17 定「不跟随、这一轮顶到上面」，B 线正在改），同一视口叠第二套滚动控制会互相抢；等以后换状态层再一起搬（调研文档「最大的风险」1）。 |
| 输入框（AI 版 prompt-input）、确认（confirmation） | 新版 shadcn 里没有这两个件。输入框的外观用 input-group + textarea，发送 / 附件 / 输入法行为仍是 assistant-ui 的 `ComposerPrimitive`（B 线归属）；允许卡 = card + button 组合，留在 `tool-uis`（业务卡）。 |
| calendar、chart、carousel、command、combobox、drawer、form、input-otp、resizable、sonner、toast | 各自要新的运行依赖（react-day-picker + date-fns、recharts、embla、cmdk、@base-ui、vaul、react-hook-form + zod、input-otp、react-resizable-panels、sonner）而 CC 没有对应界面（只有月份选择、没有图表 / 轮播 / 命令面板）或已有自己的（手机抽屉 `mobile-shell`、分栏 `split-handle`、提示条 `cc-toast`）；用到时再按本流程补。 |
| hover-card、navigation-menu、menubar、breadcrumb、pagination、context-menu、accordion、scroll-area、slider、aspect-ratio、direction | 网站导航型或触屏没有悬停（hover-card）；列表是无限加载不分页；右键 / 长按用同一个 DropdownMenu；accordion 由 collapsible 覆盖；scroll-area 用原生滚动（老办公机更省）；aspect-ratio 用 CSS 原生；没有从右到左的语言。 |

## 3. 按类通用

- 类别：CC 前端所有「通用控件」——任何不带业务含义的按钮、输入、选择、弹层、表格、提示、徽章、消息外壳。
- 覆盖：`frontend/assistant/src` 全部；检查（第 7 节）按类拦，不按文件点名。
- 不覆盖：Frappe Desk 里的 Cowork / ERP / DMS 网页（官方 Frappe UI，ADR-005/007，另一套规矩）；`frontend/`（旧 SPA）。

## 4. 上下游数据

- 不涉及：只加前端展示组件，不改接口、载荷、事件、存储。CC 桌面版载荷不变（不碰 `payload_contract.py`）。

## 5. 隔离与权限

- 不涉及：组件不取数、不带权限判断；展示页不调接口、只用假数据。

## 6. 入口：网页、手机、LINE、拍照

- 现有入口全部不动。
- 展示页（只在开发环境）：独立入口 `frontend/assistant/kit.html` + `src/kit/`。Vite 开发服务器直接可开；生产构建只打 `index.html`，**只有设了 `CC_KIT=1` 才把展示页一起打包**（测试机实时源码构建时设），从 main 构建的生产镜像里没有它（测试核对产物）。四语（`?lang=th|zh|en|ja`）、深浅色、电脑 / 手机宽度（390）可切。
- Qt WebEngine：CC 桌面版 PySide6 6.11.1（Chromium 134 内核）。Tailwind 4 本身要 Chromium 111+，现版已在跑；搬进来的件用到的新 CSS 只有 `:has()`（105+）、逻辑方位属性，都在支持范围；不搬 message-scroller，也就没有 `content-visibility` 的问题。验收在测试机 CC 桌面版和三星浏览器各打开一次展示页实测。
