# 需求影响评估：服务品进项税口径按账套历史定（直写与代录同一规则）

> 2026-10-29 实操窗口起草，交主会话审定后施工。

## 0. 需求原文与理解

- 主会话 10-29 转用户定：服务品进项税口径不一律写死；按这本账套的历史单据定，一贯同一种就照用、不问人；历史上没有或两种都有，
  才在开始前让人选一次、按公司记住；直写也改成同一规则，两边口径必须一致。
- 口径是 APTRN.SRV_VATTYP：`1` = เกณฑ์สิทธิ（权责制），`2` = เกณฑ์เงินสด（收付实现制），`-` = 没有税。赊购单（RR）有服务品时，
  Express 存档途中弹窗问（10-29 rec-laptop 实机）。现在直写恒写 `1`（`dbf_fields.audit_fields`），代录配方恒答 เกณฑ์สิทธิ。

## 1. 语料实测（测试机 06-录入推送答案 158 本，只读）

- 按账套看：一贯 `1` 的 45 本，没有历史的 18 本，两种都有的 95 本（多数是 `1`，少数是 `2`）。
- `2` 只出现在赊购单（RECTYP 3）上：14,003 张；现购单（RECTYP 1）全是 `1`（25,773 张）。
- 按供应商看：一贯 `1` 的 10,829 家（178,165 张），一贯 `2` 的 999 家（9,670 张），两种都有的 523 家（11,565 张）。
- 结论：口径跟着供应商走（如水电、电信这类付款时才开税票的服务商记 `2`）。按公司只记一个值，95 本里会把一贯 `2` 的供应商记错。

## 2. 建议规则（与原话的差别：判定粒度从「公司」细到「供应商」，问也按供应商记）

1. 现购单（HP）：恒 `1`（语料无例外）。
2. 赊购单（RR）：
   1. 先看这家供应商在本账套的历史。一贯一种就照用。
   2. 这家供应商没有历史：看本账套赊购单整体，一贯一种就照用。
   3. 还定不了（本账套两种都有、或整本没有历史）：开始前问一次「เกณฑ์สิทธิ / เกณฑ์เงินสด」，按供应商记住，下次同一家直接用。

## 3. 落点（按类通用，直写与代录同一规则）

- 读历史：CC 桌面版 `account_rules.service_vat_basis(account_dir, supcod)` 只读 APTRN。直写和代录都在 CC 里，调同一个函数，回 `1` / `2` / 空（要问）。
- 回空时：载荷带了人选的值（`srv_vattyp`）就用它；没带就拒写，回错误码 `SERVICE_VAT_BASIS_CHOICE`（同供应商分店不明的流程），由服务端问人。
- 判定规则写成纯函数放 `pearnly_core.express_rules`（输入：单种、供应商历史计数、整本计数、记住的选择；输出：值或要问）。CC 里用同一份规则的副本，用契约测试守住两边一致（同 `tests/test_companion_contract.py` 的做法）。
- 记住的选择：Cowork 放公司规则（`companies.rules`），ERP 放 `express.choices`，键「服务品口径 | 公司 | 供应商」。代录在预检里出选项卡片；直写在推送停下的同一处问。
- Express 弹窗：代录按判定值点 เกณฑ์สิทธิ 或 เกณฑ์เงินสด（配方改成按值选按钮，不再写死）。

## 4. 成本、作废、文案、验收

- 不调模型，不加固定月费。读 APTRN 一次约等于现有读账套的耗时（CC 已有读档缓存）。
- 已写的单不改。
- 文案只用 Express 原词「เกณฑ์สิทธิ / เกณฑ์เงินสด」，不加说明。
- 验收：
  - 离线：158 本账套回放判定结果，和历史逐张比对。
  - 契约测试：两边规则一致。
  - 实机：69EXP\test 录一张一贯 `2` 的供应商赊购单（代录、直写各一张），读回 SRV_VATTYP。
