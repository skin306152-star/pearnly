# 对账结果页慢、对账识别吞吐卡在每分钟约 10 份（2026-10-01）

分支 `codex/recon-speed`，基线 main `12ab7a05`。用户在测试机打开一套收入对账要等 18 秒（"慢得跟狗屎一样"）；压测窗口报三租户时对账识别
每分钟只出约 10 份、单套单独跑也要 3.5–10.8 分钟。用户（经压测窗口转达）定：与 1020、直传日志、网页首开一起修完一起部署。

## 一、结果页慢：每次打开都把整本 Excel 重做一遍

- 测试机浏览器计时：页面框架 0.36 秒就绪，`recon_center.sheets.load` 一个请求 17.3 秒。
- 原因：结果页由导出用的那本 Excel 逐格画出（`sheets._view` → 生成工作簿 → 读回 → 逐格转成页面数据），不缓存，每次打开重做。
  剖析（7300 行收入对账）：
  - `export/theme.py` 统一外观时每格新建字体 / 底色 / 对齐 / 边框对象，openpyxl 每次赋值都要按值比对样式表（33 万次）；
  - `export/income_workbook.py` 每写一行读一次 `ws.max_row`，它每读一次把整张表的格子数一遍（平方级，单这一项 7 秒）；
  - 银行导出的 `styles.border_range` 逐格加边框，同样逐格比对；
  - 页面画表（`sheets._sheet`）逐格读样式对象。
- 改法（结果不变）：同一种"原样式 + 同样处理"第一次算出的样式下标直接复用（openpyxl 按值去重，同样的值本来就拿到同一个下标）；
  `append` 之后的行号直接取它记着的当前行（`_appended`）；页面样式按样式下标记一次。合并区里还没有样式的格子照旧逐格处理。
- 测试机（测试租户副本）收入 / 银行 / 销项税各取数据最大的 3 套，旧代码出一次、挂上本分支实时源码再出一次，**页面数据与 Excel
  逐格（值、数字格式、字体、底色、边框、对齐、行高列宽、合并区）完全一致**：

| 套 | 格子数 | 原来 | 现在 |
| --- | --- | --- | --- |
| 收入 CIR-c28b… | 58102 | 18.1 秒 | 3.3 秒 |
| 收入 ×2（小） | 4.5k–5k | 1.0–1.1 秒 | 0.3–0.6 秒 |
| 银行 ×3 | 15.8k–24.4k | 6.1–9.0 秒 | 1.9–3.0 秒 |
| 销项税 ×3 | 10.7k–15.4k | 2.9–4.4 秒 | 0.9–1.6 秒 |

## 二、对账识别吞吐

压测窗口的证据：Cloud Run 每份对账文件 p50 15 秒，但每分钟只完成约 10 份，Cloud Run 160 并发空着；同一时刻在调模型的请求最多 4 个；
单套 B07-BAY-CA-03（一份 12 页 PDF）10 分 38 秒，Cloud Run 一页一页读、每 90–100 秒让出一次、来回 5 次。

1. **全平台同时只能有 4 份对账文件在云上读**：`document_ocr.run` 与 `invoice_ocr.run`（销项税核查的发票）把发往 Cloud Run 的读取也包在
   本机识别名额里（`pool.local_slot`，每进程默认 1 个；生产 4 个识别进程）。录入发票本来就只在本机读时占名额（ADR-015）。
   改成同一口径：`document_ocr.reading_slot()`——走 Cloud Run 不占，本机读照旧占。
2. **对账文档在 Cloud Run 上一页一页读**：`enterprise.pipeline.run` 每页"第一遍抽取 → 自核 → 必要时再读"串行。改成各页**第一遍抽取同时做**
   （`map_pages`，Cloud Run 用 `OCR_PAGE_THREADS`、与发票同一个开关和同一个 `page_mapper`；本机用 `PEARNLY_OCR_PAGE_THREADS`，生产为 1 即照旧），
   之后自核、再读、税报结转累计照旧按页码顺序一页一页来：
   - 第一遍抽取只用本页的图和转写稿，与别的页无关；
   - 再读名额（`MAX_REREAD_PAGES`）按页序先到先得、税报按前面各页（含再读后采用的）累计核，这两处都在顺序阶段，判断与原来相同；
   - PDF 渲染加锁（渲染库不是线程安全的，与发票引擎 `_SerialSource` 一样）；同时读时不把整份图留在内存，要再读的页再渲染一次
     （同一页渲染与转正结果不变）；一页一页读时照旧只渲染一次。
   - 唯一区别：整份读不出（非"单页结果不明"）时，一页一页读会在出错那页停下，同时读时其余页的第一遍已经发出。
   - 证明结果不变：`tests/test_cowork_recon_speed.py::PagesTogetherTest` 用假模型（后面的页先回来、第 2/3/5/6 页要再读、第 4 页结果不明、
     再读名额 2）比对一页一页读与同时读：发出的请求集合、再读的页与先后、最终每页结果完全相同；另把 main 上原来的 `pipeline.py` 放进同一场景，
     银行 / 税报 / 总账三类与原代码完全相同（一次性核对，未入库）。
   - 让出时限（文档 90 秒）不改：各页同时读后 12 页一般在一个请求里读完；让出后续跑的已完成调用照旧从检查点取回、不重复付费。

PDF 付费，要先核清读取顺序再说。
