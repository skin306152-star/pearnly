# 多页文件各页同时读（2026-10-01）

用户目标：100 / 1000 人同时用都只等识别本身的时间。分支 `codex/ocr-page-parallel`，基线 main b5858198。与 LINE 窗口
（Cloud Run 端也用同一个 `map_pages`）、修复窗口已对齐分工。

## 改动

- 引擎 `run_invoice(..., map_pages=None)`：不给就照旧一页一页读；给了（且页数 > 1、`max_escalations` 不设上限，线上即如此）
  各页同时读。每页用自己的 `_Run`（自己的调用证据与升级计数），读完按页码合并结果与计费证据；取页面图像加锁
  （PDF 渲染库不是线程安全的）。签名、回调参数、结果顺序不变。
- 核查：各页之间没有依赖。跨页唯一的共享状态是升级次数上限（线上不设）与 `pattern_memory`（线上不传）；分组、汇总票判断
  都在全部读完之后。银行文档的「改用 Vision」信号不走这条路。
- `pearnly_core/execution/pages.py`：每页一个线程，各自的站点上下文与数据库连接，带上同一工作单（检查点按行存，同时写不覆盖）、
  提交人与界面语言；任一页出错时等其余页结束后抛出页码最小的那个（已完成的调用都有检查点）。开关 `PEARNLY_OCR_PAGE_THREADS`
  （compose 里 `PEARNLY_COWORK_OCR_PAGE_THREADS`，默认 1 = 不开）。每个页线程占一个数据库连接，开之前按 `max_connections` 核算。
- 录入（`ocr/execution/workflow.py`）开了时按「已读完几页」推进度（原来「读到第 N 页」在并发时不成立）；对账发票识别
  （`recon_center/invoice_ocr.py`）同样接上（每页的 `last` 记录按页码分开）。
- 代价：一页「结果不明」时，一页一页读不会开始后面的页，同时读会已经读完它们（整份仍按原规则判结果不明），多付这几页的费用；
  只在这种少见的失败情况下发生。

## 验证

- 引擎离线 50 条（新增 5 条）：两种读法每页结果、计费证据（含顺序）完全相同（含直读缺金额走复核、一页读不出、文字层页）；
  6 页同时读耗时不到一页一页读的 40%；设了升级上限或只有 1 页时照旧顺序读；出错时抛页码最小的、其余页读完。
- `test_pages` 3 条：默认不开、每页各自站点上下文且结果按页序、出错语义。`test_cowork_recon_scanned_docs` 118 条、
  `test_cowork_accounting` 12 条通过。`check-production-capacity` 23 项（含新开关默认 1）。
- 测试环境真实跑：两份 6 页合成 PDF（顺序 / 同时）都因测试机连谷歌读超时 60 秒判结果不明（测试环境旧代码这几天每天几十到
  几百次同样的超时，9-30 当天 417 次），检查点按页分行写入、Work 整块 JSON 为空、按页进度推送正常。真实耗时对比改到生产测试
  租户上做（部署后）。
