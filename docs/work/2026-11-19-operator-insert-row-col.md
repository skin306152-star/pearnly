# 代录：行号栏可编辑的账套，品码打进了行号栏（11-19）

分支 `pearnly/operator-insert-row-col`，基线 main fd7b6fb30。主会话 11-19 定：随 1.12.22 发（不等 1.12.23）；1.12.23 分支里保留同一个提交。

## 现象（现网缺陷，1.12.21 起都一样）
CC 代录点进明细表格（`grid_click`，偏移按品码栏）后直接打品码。账套设了「允许插入明细行」（`ISINFO.INSERTIT = Y`）时，
明细最左多一栏可编辑的「No.」行号，新行的焦点停在这一栏：品码打进行号栏只剩 3 个字，读回对不上，整张转人工
（`line1.item: cell is '000', want '000158'`）。

## 证据
- 测试机2，CC 1.12.22 测试包（main f9ddfe11f），本机 maclab erp：69EXP\NLTTEST（INSERTIT = Y）代录采购，品码「?J3012506102」「000158」
  两张都停在第 1 行品码格，停下截图里文字落在「No.」栏。比 NLTTEST 与 TEST2 的 ISINFO：INSERTIT 一个 Y 一个 N；把测试账套 TEST2
  的 INSERTIT 临时改成 Y 再代录一张普通采购，同样落进行号栏（读回「53-」），改回（按基线整本还原）后照常。
- 影响面：测试机2 只读按原始字节读 S 盘 760 本真实账套的 ISINFO：INSERTIT = Y 206 本（约 27%），N 554 本。
- 一度怀疑「?」开头的品码（S 盘约 100 万个品码里 28 个以「?」开头）：对照普通品码同样失败，与「?」无关。

## 修法
- `express_operator/engine.py` `enter_lines`：第 1 行点进明细后 `_onto_clicked_column`——焦点格整个在点击处左边（落在行号栏）
  就按回车往右走到那一栏，最多 3 次；没有这一栏的账套焦点本来就在点的那格，什么都不多做。之后的行照旧（逐行回车回到下一行的品码格，
  原有判据按第 1 行品码格的位置认）。
- `express_operator/bg_desk.py` `grid_click`：后台做法也回报点击的屏幕坐标（同前台做法），引擎拿它比焦点格位置。
- 假 Express 加注入 `line_no_column`（点进明细焦点在行号栏、行号栏只收 3 个字、回车走到品码栏）；
  `tests/test_operator_engine.py` 新一条：四种单在这种账套上照常录成、不调 AI、不转人工。先红后绿。

## 检查与真机
- 全闸门、候选离线、CC 全量：见提交时的汇报。
- 真机（测试机2 + maclab erp，测试账套 69EXP\TEST2）：INSERTIT 临时改 Y 录一张、原值 N 录一张，结果见下行；用完按基线整本还原。
