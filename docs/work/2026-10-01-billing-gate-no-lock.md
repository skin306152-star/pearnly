# 余额闸不加锁（2026-10-01）

分支 `codex/billing-gate-no-lock`，基线 `origin/main` 1a432fed。归属：控制面 `pearnly_control.billing`（计费服务的余额闸）。
来源：压测窗口转来的产品问题（生产 Cloud Run 发票压测）。

## 现象与证据（生产，只读查）

- 两轮压测（03:34–03:50、04:16–04:33 UTC）提交时余额闸返回 `lookup_error`，页面「稍后重试」，提交被拒收。
- 产品侧日志：cowork-web 79 次 + ocr-worker 194 次全部是 `Read timed out (read timeout=10)`，另有 9 次计费服务回 HTTP 500。
- 计费服务 `billing-web`：gunicorn 2 进程 × 4 线程（同一时刻 8 个请求位），512MiB。

## 原因

`billing.gate()`（开工前问一句余额够不够）用的是加锁读：`wallet_of(tenant)` 默认锁租户行与钱包，`pages_used` 默认锁本月全部
按量用量行，`_active_by_cycle` 锁订阅行——与同租户每一笔扣费（`charge`，同样先锁租户行）抢同一把锁。几十个识别线程同时扣费、
同时提交新识别时，8 个请求位都被等锁的请求占住，问余额的请求排到 10 秒读超时，产品端把它当成「查不到余额」拒收。

## 改动

- `gate()` 只读、不加锁：`wallet_of(create=False)`（没有钱包就是余额 0，不在问余额时建钱包）、`pages_used(lock=False)`、
  `_active_by_cycle(lock=False)`。三种答复（放行 / 余额不足 / 查不到）不变。
- 扣费不变：照旧在租户锁里重新读余额、用量与订阅，钱以扣费时为准。问余额与扣费之间的竞态与原来相同（原来也是问完放锁、
  稍后才扣费），所以不新增风险。
- `tests/test_control_billing_gate.py`：问余额不加任何锁、三种答复不变、读失败报「查不到」不报「余额不足」、扣费仍加锁；
  换回旧代码时其中 2 条失败。已加入候选镜像离线检查。

## 验证

- 离线：新测试 4 条通过；`python3 scripts/check-architecture.py`。
- 测试机（生产同一镜像 51e73a9f 的测试栈，计费服务同样 2×4、512MiB；同一租户每轮同时 150 次问余额 + 100 笔扣费，3 轮；
  扣费扣在测试账本副本上；新代码只临时放进测试栈计费容器，测完已重建容器还原）：

  | | 问余额 中位 / 95% / 最慢 | 问余额出错 | 扣费 中位 / 95% / 最慢 |
  | --- | --- | --- | --- |
  | 旧代码 | 0.64 / 2.82 / 5.01 秒 | 1（HTTP 500） | 2.80 / 4.33 / 5.20 秒 |
  | 新代码 | 0.14 / 0.28 / 1.00 秒 | 0 | 1.70 / 3.30 / 4.13 秒 |

  测试机比生产快约 5 倍，生产上的超时在这里表现为秒级排队；耗时对比只说明「问余额不再等扣费的锁」。
- 剩下：扣费之间偶发数据库死锁（新旧代码各 1/300，`QueryDeadlockError`，计费服务的有限次重试用完后回 500）。产品端把这次扣费
  记成「待记账」、60 秒后按同一参考号重扣，不重复、不丢；如压测仍常见再单独处理。
- 压测副作用：测试账本里 testcowork 被扣了 1017 页 / 779.25 泰铢（参考号 `loadtest:*`），测试余额变成 -118.75，待用户定如何还原。

## 没做 / 待定

- 计费服务容量（进程 / 线程 / 内存）是 compose 与 runtime.env 的事，先看本改动上线后的压测再决定，需与 LINE 窗口商量。
- 余额闸按租户短时缓存：本改动后问余额已是毫秒级只读，暂不做（缓存会让「刚充值 / 刚用完」的判断晚几秒）。
- 生产部署：未做，需用户同意。
