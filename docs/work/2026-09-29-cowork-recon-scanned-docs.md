- 银行电子 PDF 先走免费文字解析（旧线上企业档对所有 PDF 都 OCR）。

## 选型调研（2026-09-29，只读网上调研，未调用任何新服务）

用户问：市面上有没有专做多行密集表格的识别，还是只有谷歌在成本和质量上占优。结论：

- **没有任何产品公开过泰国银行账单 / 总账 / 税报逐行准确率**；泰文基准只测文字或表格相似度。只能拿压测语料（有答案）自己比。
- 谷歌的优势在「便宜的读字 + 坐标」：Enterprise OCR 每页约 ฿0.05、支持泰文印刷体、新加坡区域；真正保证质量的是我们自己的本地拼行 + 余额链校验，任何服务都不替我们做这一步。
- 不适用：AWS Textract 不支持泰文；谷歌 Form Parser / Custom Extractor / Bank Statement Parser 官方不列泰文或只支持英文；Azure 银行账单预置模型只支持美国英文。
- 值得比的：Azure Layout（泰文印刷 + 手写、单元格表格、东南亚区域，每页约 ฿0.35）；Mistral OCR 4.1（每页约 ฿0.14，批量 ฿0.07，带逐词置信度）；
  Typhoon OCR 1.5（2B 开源泰文专用，但泰文基准字错率不如 Gemini；旧项目当年也试过 Typhoon 输了）；iApp 泰国银行账单接口（直接出交易行，每页约 ฿0.9–1.25）。
- 大模型逐页读（1600×2200 一页、输出约 3000 token）：3.1 Flash-Lite 约 ฿0.17–0.22；3.8 Flash 约 ฿0.44–0.57（调研称是截至 2026-12-31 的优惠价，2027 起约翻倍）；Qwen3-VL-Flash 约 ฿0.05 但数据出境需核对。
- 现在真正的成本在「本地拼行算不平 → 整份逐页 3.8」：测试机两份样本都走到了这一步。优先方向是提高本地拼行通过率、税报补本地拼行、只对不平的页升级。
- 下一步（需用户同意）：在测试机语料上做对照赛，指标为逐行完全一致率、漏行 / 重复行、余额链通过率、耗时、每页成本。只用谷歌各档不需要新账号；接 Azure / Mistral / iApp 要用户开账号，并同意把真实客户资料发给新服务商（PDPA）。

## 围绕谷歌优化（2026-09-29，用户：「就围绕谷歌这边搞吧」）

测试机上压测窗口已跑的 33 个识别任务（只读重放已存的 Document AI 结果，不再付费）：

- 30 份银行账单有读字结果：旧线上本地拼行一次算平 18 份（都是 KBank 电子账单照片，即 9 月 3 日试点的版式），其余 12 份走 3.8。
- **结果不明 3 份（约 9%），整份失败**。原因两种（在测试机单独重发核实，Document AI 共 5 次调用约 ฿0.7）：
  1. 回复超过共用层 8MB 上限：旧线上请求带逐字符坐标（enableSymbol），SCB 3 页扫描件回复 9.6MB；多页扫描件每次都会撞上，生产同样。
  2. 上传写超时：共用层连接超时 10 秒也管请求体写入，测试机办公室上行慢时 7MB 请求写不完。生产服务器上行快，较少遇到；未改共用层。
- 旧拼行在一页没有日期行时报 `statistics` 错，被当成页数不符整份失败（BBL 网银账单）。
- 多照片对账清理临时文件时锁等待超时（删除保护检查 `FOR UPDATE`，二十张照片在一个事务里删，与并发对账互等）。
- 谷歌同一文件连读两次结果有细微差别（356 / 355 行），加不加字段过滤都一样。

改动：

| 位置 | 改动 |
|---|---|
| `ocr/providers/client.py`、`ocr/enterprise/pages.py` | Document AI 请求加 `fieldMask`（只要文字、页、行、词、表格；旧线上请求体函数不动），回复 9.6MB → 2.8MB；每次读 15 页 → 5 页（按页计费，费用不变） |
| `ocr/enterprise/pipeline.py` | `_local`：只有真的页数不符才整份失败，旧拼行其他报错转模型；银行账单旧拼行算不平时再试按表头定列 |
| `ocr/enterprise/header_bank.py`（新） | 按表头文字（泰 / 英 / 中）定列、余额列每个数一行、同高度取金额与日期（照片倾斜按斜率校正）；之后照旧线上：相邻余额定方向、有界余额链修正、`check_document` 和日期行数核对。另：“0.00”这类小金额不再当时间、两位年份按不晚于明年取公历、泰文月份缩写、行号贴在日期前、日期倒退就不收 |
| `recon_center/jobs.py` | 临时文件一份一提交，清理失败只记日志、不改任务结果 |

重放结果：按表头定列多救回 2 份（都是小照片）；其余失败件多是读字本身错（存折手写、金额与杂字粘连、日期丢位，如“23/02”读成“2/02”），按规则交给 3.8。新平台没有降低旧线上已能算平的部分（只在旧拼行不平时才用）。

验证：Cowork 离线 1683 项（2 个既有错误：样板缺 python-docx，新增 9 项）；旧版对照 0 差异（8 文件逐字节、7 函数、24 种请求）；架构 0 违规。

未做 / 待定：本地拼行算不平时先花 ฿0.05/页 重读一次再试（利用谷歌读字的不稳定），再考虑 3.1 Flash-Lite 先读、不平再 3.8；税报本地拼行器；模型结果两位年份（1982）按同一规则校正。都要在测试机语料上实测后再定。

## 压测第一轮回报的 5 条（2026-09-29，压测窗口）

1. **超过 10MB 的文件整单被拒**（V03 Big C 发票扫描件 10.7 / 14.8MB）：对账临时文件用的是 Frappe 老的 `file_manager.save_file`，它的默认上限是 10MB；站点的实际上限是 25MB（System Settings 为 0 时走 `frappe.core.api.file` 的默认值）。已修：改为原生 File 插入，与卡片附件相同，按站点上限走，和 `MAX_BYTES` 25MB 一致。
2. **ocr.enterprise_page_count_mismatch**（B09 04.69.pdf 存折扫描、BBL6764 Apr）：用已存的读字结果重放，两份都是旧拼行抛 `StatisticsError`，被报成页数不符。上一提交的 `_local` 已覆盖，改为交给模型读。04.69 另一份 4 页的是“结果不明”，属于回复超 8MB，已由 fieldMask 和 5 页一读覆盖。
3. **当月 0 笔的总账整单失败**（B05 02 月）：旧线上 `services/recon_jobs/bank_handler.py` 同样判失败（`no_rows`）。用户 2026-09-29 定：对产品有利的直接做，所以有意改为：
   - 总账表格里印了期初、当月 0 笔时，按“本月无发生额”照常对账，银行那边的每一笔都显示为总账未记。
   - 连期初都没有的空表照旧读不出。
4. **锁超时显示成“数据格式不对”**（B01 18 张照片）：那次锁超时发生在清理阶段，结果已存；界面上那句泰文是 7 个校验码共用的，而这些校验错误原来不记日志，所以 B01 的真实原因没留下来。已改：
   - 对账任务每次失败都记错误日志。
   - 数据库锁或超时这类系统错误，提示“系统繁忙，这次对账没有完成，请稍后重试”（`reconciliation.system_busy`，四种语言）。
   
   B01 重跑后按日志定位真实原因。
5. **对账任务串行、互相阻塞**：
   - 旧线上：`RECON_WORKER_CONCURRENCY` 默认 2 个对账并发；银行对账一侧多份文件 4 份并行读（`_parallel(max_workers=4)`）。
   - 新平台生产：Cowork 的 short / default / long 共用 1 个 `bench worker`（`infrastructure/production/compose.yml` 的 `cowork-worker`），识别用 `worker-pool` 2 个进程。一个对账任务在等识别的这段时间（最长 25 分钟），会占住 Cowork 全部普通后台任务。
   - 已改（应用内）：银行对账先把所有照片一次提交识别，再逐个取结果。2 个识别进程可以并行读；同一参考号的提交复用同一个识别任务，不会重复收费；PDF 不预先提交，因为带文字层的先免费解析。
   - 未改（运行定义，需用户同意部署）：给 Cowork 的 long 队列单独起 `worker-pool --num-workers 2`，让对账之间、对账与其他后台任务不再互相等待。在此之前，这一条记为已知限制。
   - 实际影响（压测第二轮观察）：一个对账任务占着这唯一的 `bench worker` 时，default 队列里堆了 12 个 `run_scheduled_job`，也就是 Cowork 站点自己的定时任务，全都排在对账后面没有执行。所以受影响的不只是其他对账，还有 Cowork 的定时任务。
