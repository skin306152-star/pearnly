## 0. 结论（一屏）

1. **第 1 期做对了一半**：题目、选项、推荐、已定项、四语文字、问一次记住、大列表搜索，都已经由服务端出，Cowork / ERP、直写 / 代录同一张卡。这一半原样留用。
2. **另一半要在铺开前收口**（否则每加一项业务都要改界面代码，就是用户担心的「以后前端又要重搞」）：
   - 业务清单写死在三处代码里，加一项业务要改三处；
   - 引导卡只认「一批单据」，收款、对账、增值税、读回、盘点这类没有单据的业务套不进去；
   - 每一步都要模型发起，连「选客户、选月份」这种确定的事也过模型，花钱、会走偏；
   - 题卡、代录开始卡、复核、结果还是各一条路。
3. **收口的办法**：一项业务 = 一份**声明**（产品自己写，ADR-009），一个**共用引擎**把声明跑成对话里的卡片。页面只有三种卡（题卡、复核卡、结果卡）+ 有限几种输入方式，
   新增业务只写声明和它要调的服务函数，不写新界面。Cowork / ERP、直写 / 代录、三种账本的差别全部落在声明和选项来源上。
4. **对话为辅**：打字入口不动。打字和点卡片最后调的是同一个服务函数、同一份规则；确定性的步骤不经模型、不花钱，模型只在读票后的判断、用户打字、出错要解释时出场。
5. **一张总表**：以 11-12 总表的 12 格为骨架，引导状态并成它的一列，位置固定一处；业务声明就是机器可读的总表，检查脚本对着它核。11-14 覆盖计划那张表作废改指针。
6. **分期**：P0 收口 → P1 ERP 收款 → P2 ERP 采购 / 销售 → P3 Cowork 常规 → P4 其余；MR.ERP、云端 Express 不单独成期，随各自那条线交付逐期点亮。
   合计约 **120–150 小时写码 + 45–55 小时机器跑测**（不含等人、排机器）。每期结束都是可上线的完整状态。

## 1. 现状：第 1 期到底是什么

第 1 期（`pearnly/guided-3-0cc915`）的实际形态，按一次采购走一遍：

1. 输入框上方出**业务菜单**（`thread.tsx` `BusinessMenu`）：清单来自产品 hooks `pearnly_guide_businesses = {chat: [...], operator: [...]}`，服务端 `guided.offered()` 过滤、
   `sessions.set_business` 记在会话上（`business` / `business_at`）。
2. 选了业务，**页面**在对话里画一句「请上传采购票据。」（`BusinessPrompt`，不进模型上下文；模型从每批末尾的系统说明 `contracts.business_note` 知道）。
3. 用户上传 → **模型**读票（产品识别工具）→ **模型**调工具 `pearnly_guide {company, doc_ids}`。
4. 工具出卡前，**服务端** `guide_tool.prepare` 调写账前置判定 `write_precheck.api.card` → `write_precheck/guide.py:build` 出卡：`questions`（每题 key / kind / 三档 tier / 选项 / 推荐 / 预选 /
   服务端搜索 / 依赖 when / 是否记住）、`decided`（已定 N 项，展开可改）、`facts`（结果不明 / 写不了 / 等电脑）。卡存进这次工具调用的执行记录，页面按调用号取（`api.guide_card`）。
5. 页面用提问卡同一个组件（`AskCard`，一题一页）渲染；提交 = 这次调用的「允许」带答案（`sessions.confirm` → `toolrun.decide` → `guide_tool.check / result`），
   服务端记下（`write_precheck.api.record(guided=True)`，卡上没点过的预选不生效），模型只收到「答了几项、哪些能办、哪些留下」。
6. 模型调 `pearnly_write_plan` 复述一句 → 用户点输入框上方的按钮或说一句 → `pearnly_write_start`（三道服务端保险）→ 产品推送工具 → 模型报结果。

## 2. 引导框架

### 2.1 四个概念

| 概念 | 是什么 | 谁写 | 几份 |
|---|---|---|---|
| **业务声明** | 一项业务的引导怎么走：在哪可用、问什么、选项从哪来、怎么自动定、复核什么、确定后调谁、何时失效 | 产品（ADR-009），放 `apps/<app>/<app>/guides/<业务>.py`，hooks `pearnly_guides` 列出 | 每项业务每个产品一份 |
| **出题源** | 把「这次要定的事」算成统一的卡。两种：**按单据**（现有写账前置判定，题目由必填登记表与产品判定决定）；**按表单**（新，题目由声明的步骤清单决定） | 共用层 | 两种，产出同一种卡 |
| **引导运行** | 一次引导的服务端记录（哪段对话、哪项业务、当时的公司 / 账套 / 月份、每步答案、走到哪一步、状态），随对话删 | 共用层 `pearnly_core/assistant/guide/` | 一份引擎 |
| **三种卡** | 题卡（现有 `AskCard`）、复核卡（一批一张，就地改）、结果卡（每项一行，带账本单号 / 文件） | 共用前端 `frontend/assistant` | 各一份，所有业务共用 |

### 2.2 业务声明的形状

纯数据 + 点路径（指向产品已有的服务函数），没有界面代码。以 ERP 收款为例（字段名是设计稿，施工时定稿并加形状检查）：

```python
# apps/pearnly_erp_portal/pearnly_erp_portal/guides/collection.py
GUIDE = {
    "id": "collection",
    "label": "guide.business.collection",          # 菜单上的字（术语表键，四语）
    "icon": "wallet",                               # 图标名，取共用白名单（lucide）
    "order": 10,                                    # 菜单顺序
    "modes": ["chat"],                              # chat = 直写，operator = 代录
    "ledgers": ["express_local", "express_cloud", "mrerp"],   # 这项业务面向哪几种账本；真亮不亮看 2.5 的能力判定
    "allowed": "pearnly_erp_portal.collection.plan.allowed",  # 权限：勾了这个功能的人（服务端一处判断）
    "opening": "guide.open.collection",             # CC 发的那一句（术语表键）
    "source": "form",                               # form = 按表单；documents = 按单据
    "steps": [
        {"key": "customer", "input": "choice", "ask": "always", "search": True,
         "options": "pearnly_erp_portal.collection.guide.customers"},
        {"key": "invoices", "input": "amounts", "ask": "always", "after": ["customer"],
         "options": "pearnly_erp_portal.collection.guide.open_invoices"},
        {"key": "method", "input": "split", "ask": "always", "after": ["invoices"],
         "options": "pearnly_erp_portal.collection.guide.methods"},
        {"key": "voucher", "input": "file", "ask": "always",
         "when": {"key": "method", "has": "transfer"}},
        {"key": "staff", "input": "choice", "ask": "auto",
         "default": "pearnly_erp_portal.collection.guide.staff"},   # 销售员 / 部门：按第一张发票与单据簿默认，进「已定」可改
    ],
    "draft": "pearnly_erp_portal.collection.guide.draft",       # 答案 → 草稿（service.create_draft / update_draft）
    "review": "pearnly_erp_portal.collection.guide.review",     # 草稿 → 复核视图（service.card）
    "confirm": "pearnly_erp_portal.collection.guide.release",   # 确定 → service.release(name, version, consent)
    "result": "pearnly_erp_portal.collection.guide.status",     # 结果行（service.status）
    "expires": ["ledger", "company", "master"],                 # 失效规则（2.4）
}
```

按单据的业务（采购、销售）声明更短：`"source": "documents"`，步骤只有一步「交票据」，其余题目由出题源按必填登记表与产品判定算出，不在声明里列。

**声明里可以写的部分（穷举，引擎只认这些）**

| 部分 | 字段 | 说明 |
|---|---|---|
| 在哪可用 | `modes`、`ledgers`、`allowed`、产品（声明在哪个 App 就是哪个产品） | 菜单只列此刻真能办的（2.5） |
| 要问的项 | `steps[].key`、`input` | 输入方式是有限集合（下表），不许自造 |
| 选项来源 | `steps[].options`（点路径）+ `search` | 统一签名（2.3） |
| 何时问 | `steps[].ask`：`auto` 自动定 / `remember` 问一次记住 / `always` 每次问；`tier`：怎么办 / 做不做 | 三档规则沿用第 1 期 |
| 依赖 | `after`（先后）、`when`（只在某项取某值时出） | `when` 沿用现有 `contracts.applies` |
| 复核 | `review`（点路径，回统一的复核视图） | 会改账本或删东西的业务必须有；只出草稿 / 报表的可以没有 |
| 确定后的动作 | `draft`、`confirm`（点路径） | 必须是打字路径那个工具背后的**同一个服务函数**（第 3 节） |
| 结果 | `result`（点路径，回统一的结果行） | — |
| 失效 | `expires` | 引擎统一执行（2.4） |
| 要模型判断的点 | `judge`（可选，点名哪一步之后交给 CC 判断，及给它的事实） | 默认没有 = 全程不经模型（第 3 节） |

**输入方式（题卡上一题能长成的样子，共九种，前端各实现一次）**

| `input` | 样子 | 第 1 期有没有 | 首次用到 |
|---|---|---|---|
| `choice` | 单选，可带推荐、说明行、服务端搜索、「其他」自己填 | 有 | — |
| `multi` | 多选 | 提问卡有（`multiSelect`） | P3 对账预设 |
| `amounts` | 多选 + 每行可改金额，默认全额，带合计（收款勾发票） | 无 | P1 |
| `split` | 一个总额分到几种方式上，合计要对上（现金 / 转账 / 折扣） | 无 | P1 |
| `file` | 卡上交文件（走上传唯一入口，2.4） | 无（现在用输入框） | P1 转账凭证 |
| `month` | 选月份（默认本对话月份） | 无 | P3 |
| `number` / `text` / `date` | 一格输入（单位成本、名称、日期） | `free` 那一格算一半 | P1（收款日期）、P2（新建对方 / 物料） |

九种之外的需求先问能不能用这九种拼出来；真要加第十种，是共用层的改动，走主会话。

### 2.3 步骤规则

- **自动定（`auto`）**：服务端 `default` 给得出值就不问，进「已定 N 项」，展开可改；给不出值就降成问。来源写明（记住的 / 主档唯一 / 账套设置 / 票面 / 历史），同第 1 期 `source`。
- **问一次记住（`remember`）**：第一次问，答案按声明的范围记（公司 / 公司 + 对方 / 账套），以后进「已定」。记在产品现有的记忆里（`products.remember` 那一路），不新建第二处记忆。
- **每次问（`always`）**：钱和对象的事（收哪家、收多少、哪种方式、哪个月）每次明选，不记不预选（收款方式不记，11-12 第 5 问已定）。
- **三档**沿用：怎么办的题推荐项排第一并预选、点了才算；做不做的题不预选、必须明选；卡上没点过的预选不生效。
- **依赖**：前一步的答案是后一步选项来源的入参（选了客户才列它的未收清发票）；已定的上下文（对话选择器的公司、账套、月份，会话业务，答过的题）是固定输入，后面的步骤只读不重判
  （记忆 `cc-target-is-selected-ledger`）。
- **选项来源统一签名**（沿用 `write_precheck.api.search` 的形状，所有业务同一个）：

  ```python
  def options(ctx, txt="", start=0, page_length=20) -> {"options": [{"code", "name", "note"?, "recommended"?, ...}], "more": bool}
  # ctx = {company, book（账套身份与种类）, period, session, answers（前面各步的答案）, docs?}
  ```

  服务端分页与搜索（AGENTS「列表、选择与搜索」），不一次取全。`amounts` 的行另带 `amount`、`max`；`split` 的项另带 `kind`。
- **必须是产品网页同一处的数据**：选项函数只转调产品已有的服务函数（例：收款客户 = `collection.service.customers`，即网页「新建收款」和 LINE 用的那一个），不另查库。

### 2.4 引擎

位置 `apps/pearnly_core/pearnly_core/assistant/guide/`（多产品共用，文件头写明）：

| 模块 | 职责 |
|---|---|
| `registry.py` | 收各产品 `pearnly_guides` 声明，核形状（纯函数，离线可测）；按产品 × 模式 × 账本能力 × 权限给菜单 |
| `steps.py` | 纯函数：声明 + 已有答案 + 事实 → 下一张卡（沿用 `write_precheck/guide.py` 的卡格式，版本 +1 加 `input`）；全部已定 → 直接到复核 |
| `run.py` | 引导运行记录（新 DocType `Pearnly Assistant Guide Run`：会话、业务、状态、当时的公司 / 账套 / 月份、答案、草稿号、声明版本；随对话删）；开始 / 作答 / 复核里改 / 确定 / 取消 |
| `feed.py` | 把运行记录投影成对话事件并进 `sessions.events`（同代录 `feed.project`：不另存事件表、编号由记录推出、刷新与跨设备回放一致、页面按编号去重） |
| `sources/documents.py`、`sources/form.py` | 两种出题源；`documents` 就是现有 `write_precheck.api.card` + `guide.build`，不重写 |

**一次引导的状态**：`asking`（在问）→ `reviewing`（复核中）→ `confirmed`（已确定，在办）→ `done` / `failed`；旁路 `cancelled`（用户取消）、`expired`（失效）。

**走法（不经模型的主路径）**

1. 点菜单上的业务 → 页面 POST `guide.start(session, business)` → 服务端建运行、算第一张卡 → 对话里出现 CC 那一句 + 题卡（都是运行记录投影出来的事件，留痕）。
2. 用户在卡上点选 → POST `guide.answer(run, answers)`（核对：值在选项里、运行没失效、是本人）→ 记下 → 回下一张卡；没题了就调声明的 `draft` 生成草稿、进复核。
3. 复核卡：就地改 → POST `guide.edit(run, cell, value)`（版本 +1，标红不拦，同 `write_precheck/review.py` 的契约）。
4. 「确定」→ POST `guide.confirm(run, version)`：服务端核版本没变、没失效、没点过停止 → 调声明的 `confirm`。**同意凭证是本人在页面上点的这一下**
   （同网页收款 `submit_web` 的 `web:<request>`、同 `ledger.choose(by="page")`），记成 `guide:<运行号>:<版本>`，幂等。
5. 结果卡：声明的 `result` 给每项一行（状态、账本单号、原因码的四语说明、生成的文件）。写账本的业务，状态变化由产品现有回执推（同代录 `feed.receipt`）。

**与写入计划的关系**：写入计划（`write_plan`）的三道保险里，「用户确实又说了一句」是防模型替用户确认；引导路径上没有模型，同意就是复核卡上的点击，另两道
（逐张重算判定摘要、点过停止不放行）与「本对话账套变了不办」照旧由同一份代码执行。实现上给 `write_plan.start` 加一种来源 `by="page"`（凭证 = 运行号 + 版本），
不另写一套放行。打字路径不变（复述一句 → 用户回话 → `pearnly_write_start`）。

**交文件**：`file` 步骤提交时，在同一个请求里调唯一入口 `pearnly_core.assistant.files.commit(row, file_ids, via="guide")`；卡上移除调 `assistant.api.drop_upload(session_id, file_id)`；
不自建上传口、不自己触发识别（上传窗口的接缝约定）。按单据的业务，文件交上去之后由产品现有的识别入口处理，识别有结论时引擎接着出题
（等待与进度沿用 `assistant/waits.py` 的键与 `pearnly.progress`，只用真数）。

**失效规则（引擎统一执行，声明只选哪几条适用）**

| 触发 | 处理 |
|---|---|
| 本对话的公司 / 账套 / 月份变了（右栏改、CC 换） | 运行标 `expired`；旧卡置灰只剩一行；若正在问，自动按新上下文重开同一业务（已答且仍有效的答案带过去） |
| 同一对话里同一业务又开了一次，或换了业务 | 旧运行 `cancelled`，旧卡置灰 |
| 选过的主档值不在了（客户停用、发票已收清、科目被删） | 作答 / 确定时服务端核出 → 这一题退回重问，其余答案保留（第 1 期 `refused` 的做法，粒度从整卡细到题） |
| 草稿在别处被改（另一台设备、网页、LINE） | 版本对不上 → 复核卡刷新成新版本再让人确定（收款 `release` 已有 `changed`） |
| 放了太久 | 过期时长按 `cc-card-expiry` 那条线定的数（一处常量），到点置灰 |
| 点了停止 | 运行停在当前步，卡留着可继续；已交给账本的不撤 |

置灰后的卡不可点，服务端对失效运行的作答一律拒（不占用、不记）。

### 2.5 差异落在哪

| 差异 | 落点 | 不许的做法 |
|---|---|---|
| Cowork / ERP | 各自 App 里的声明与选项函数；同名业务（采购、销售）两边各一份声明，形状由 `registry` 核成一致 | 共用层里出现 `if product == ...` |
| 直写 / 代录 | 同一份声明的 `modes`；差别只在 `confirm` 之后走哪条执行路（直写 = 产品推送；代录 = `express_operator.api.hand_in`），由引擎按会话模式转，声明不分叉。代录的「电脑在不在线、Express 开没开」是卡上的事实行，不是题 | 代录另有一张开始卡、另一套判定形状（G4） |
| 本地 Express / 云端 Express / MR.ERP | ① 选项来源读**统一主档可见范围**（公司接入线第 2 批的 `masters/access.py`：`usable` / `scope_sql` / `master_query`；评估里叫 `master_scope`，代码里没有这个函数名），按本对话账套（`book_for(company, 日期)`）取，不关心它从哪种账本同步来；② 「这项业务必须问全哪些字段」读**该账本的必填登记表**：Express 一张（已有，云端共用——字段相同，只是通道不同），MR.ERP 一张（照同一形状新登记）；③ 「此刻能不能办」读**能力判定**：`registry` 问产品 `capable(business, mode, book)`，回 是 / 否 + 原因码，否的不上菜单 | 声明里写 `if ledger == "mrerp"`；菜单上出现点了才说做不了的业务 |

能力判定是覆盖总表的机器可读来源（第 4 节）：某格从「依赖别的线」变成「能办」，只是那条线交付后 `capable` 返回变了，不改引导代码。

### 2.6 兜底与乱用（引擎一处做，所有业务都有）

| 情况 | 处理 |
|---|---|
| 没点菜单直接上传 / 直接打字 | 照旧走打字路径；模型判断出业务后调 `pearnly_guide` 把同一个引导开出来（第 3 节），之后同一条路 |
| 卡挂着时用户打字 | 这句照常发出，卡留着；CC 听懂是答案就调作答工具记下（等同点卡），听不懂照常回答，卡仍可点 |
| 选了业务又问别的 | 当普通聊天答；运行留在 `asking`，卡在对话里，菜单恢复 |
| 中途换业务 / 重新点同一业务 | 旧运行取消置灰，开新的 |
| 选了采购却交了销售票、一批混几种 | 沿用第 1 期：卡里一道「做不做」题，不预选 |
| 交的文件不是这项业务要的（对账交了发票） | 这一步退回，卡上用一行事实说明收到的是什么，可重交 |
| 同一批重复交 / 已办过 | 先核账本实际，在则卡里问一次「跳过 / 再办一次」，不预选（11-10 口径）；不拦 |
| 两台设备同时点 | 作答 / 确定按运行记录行锁抢占，后到的拿到最新卡（同 `toolrun.decide`） |
| 刷新、换设备、断网重连 | 事件由记录现投影，回放一致；页面按编号去重 |
| 权限中途被收回 / 公司不可用 | 下一步服务端拒，卡置灰，一行说明 |
| 出错（服务函数抛错、账本拒收、结果不明） | 结果卡按原因码给四语说明；确定性的补救（重试、去核对）是结果卡上的选项；说不清的交给 CC 判断（第 3 节「要模型判断的点」） |
| 关掉题卡（跳过） | 这一步不记，运行停在这一步，卡留着可继续；依赖它的项这次不办（同第 1 期 `skipped`） |

管钱底线（金额不闭合、必填缺失、身份不符、只写选中账套）仍在业务函数里守，引擎不重复、不放松。

## 3. 对话为辅怎么落

- **入口都在**：输入框、附件、打字办事全部保留；现有工具一个不下线。菜单不是必经之路（11-12 已定）。
- **同一个函数、同一份规则**：每项业务「最后办事」只有一个服务函数（收款 `collection.service.create_draft / release`、采购销售的产品推送、对账 `recon_center` 的开始……）。
  引导的 `draft / confirm` 与打字路径的工具都只调它；选项函数与工具的列表函数也是同一个。新增检查：`scripts/check-cc-guides.py` 断言声明里每个点路径存在，
  且 `confirm` 指向的函数与声明的 `tool`（打字路径的工具）处理函数最终调用同一个服务入口（登记表写明，测试对拍）。
- **打字进引导**：模型听出用户要办某项业务（「帮我收 ABC 公司 5 万」），调 `pearnly_guide {business, prefill: {customer: "ABC", amount: 50000}}`——服务端开同一个引导运行，
  能定的直接进「已定」，只问剩下的；之后与点菜单完全一样。模型不出业务题（`refuse_ask` 沿用）。
- **卡上的事用话答**：「这家都是现金」「第 3 张不要」→ 模型调作答工具（现有 `pearnly_precheck_answer`，扩成按运行号 + 题 key），等同点卡；没答的预选不生效，同一口径。
- **模型何时出场（其余时候不开模型、不花钱）**：

  | 时机 | 模型做什么 |
  |---|---|
  | 用户打字 | 听懂意图、开引导、替用户作答、解释卡上的事实、自由聊天 |
  | 读票后的判断（按单据的业务） | 服务端规则判不出的：这几页是不是一张票、是不是发票、方向、疑难件的根因（记忆 `cc-agent-not-rules`）。声明用 `judge` 点名，引擎只在规则没结论时才交给它 |
  | 办完出了规则外的错 | 看失败证据、读回账本、给补救，用话说清；确定性的原因码不找它，结果卡直接给说明 |
  | 引导全程顺利 | 不出场。运行的经过在用户下一次打字时随系统说明带给它（同 `notices.uncarried`、`business_note`），它知道刚才办了什么 |

- **要先实测再定的一点**：采购 / 销售「上传 → 识别 → 成单据」这一段，今天有多少判断是模型在做（分票、方向、非票据），多少产品函数已经能独立做完。P2 开工第一步先量这一段
  （约 4 小时，只读 + 假智能体流程），按结果把每个判断归到「服务端规则」或 `judge`。量之前不承诺采购 / 销售能全程不经模型；收款、对账、增值税、读回、盘点这些按表单的业务可以。

## 10. 代录：开始前问完，中途只做兜底（用户 11-14 补充口径）

用户原话（经主会话）：「在 cc，选公司，选菜单，按引导式点击，上传，上传发送后，代录按规则和选择已经识别结果开始，引导式的作用就是为了减少或者不需要代录时又出现新问题，

这与 10-30 否决的那件事不冲突：10-30 否决的是「有人在用 Express、代录被打断后的复核 + 状态文案 + 提问」（中断恢复，记忆 `operator-interrupt-judge-not-script`），那项照旧不做。

### 10.1 两类选择点（必须分清）

| | 甲类：开始前就知道会遇到 | 乙类：存单途中才冒出来、没登记过的框 |
|---|---|---|
| 例 | 物料单位对不上（`หน่วยนับ`）、服务品进项 / 销项税按哪种基础、单据菜单落到子菜单（`menu_choice`）、对方 / 物料不在主档、日期不在期间、单号已存在 | 这家公司定制过的 Express 弹出的、配方和实录里都没见过的选择框（11-14 真机验的那种） |
| 什么时候问 | 开始前，引导卡一次问完；答过按公司记住 | 冒出来那一刻；只此一次，记住并登记，下次进甲类 |
| 没答怎么办 | 这张单留下，**同一批其余的照办**（10-29「要选的单挪到最后、其余照录」只适用于这一类） | 框是模态的、单已存了一半：**这本账套停住**，别的账套照跑；没法「先挪到最后」 |
| 谁来点 | 答案随载荷下发，CC 桌面版遇到框按答案点 | 见 10.4 两种做法 |

### 10.2 选择点登记表（甲类的来源）

现状：两份配方各有一节 `dialogs`（`companion/src/companion/express_operator/recipes/express-1.0.1.94.json` 13 项、`mrerp_operator/recipes/mrerp-2026.11-src.json` 6 项），
每项有名字、匹配文字、是否自动、点哪个钮或落什么原因码；其中服务品税基础已经按账套设置自动选钮（`button_by_srv_vattyp`），子菜单已经有「问一次记住再交」
（`express_operator/menu_choice.py`）。缺的是：**站点这边不知道这张表**，所以开始前没法问；表里也没写「什么情况下会弹、有哪几个选项、每个选项什么意思」。

设计：

- **一张登记表，放共用层纯契约** `pearnly_core/express_operator/choice_points.py`（照 `contracts.py` 与 CC 桌面版 `contract.py`「两边同值、测试比对」的现成做法）。每个框一行：

  | 字段 | 内容 |
  |---|---|
  | `name`、`ledger`、`doc_types` | 名字（同配方）、Express / MR.ERP、哪几种单会遇到 |
  | `match` | 认这个框的文字（同配方） |
  | `class` | `notice` 只是知会（只有确定钮，自动点）· `choice` 业务选择 · `block` 账本拒绝 |
  | `trigger` | 这张单会不会遇到：纯函数，吃单据事实与账套设置，回 会 / 不会 / 说不准 |
  | `options` | 每个按钮：原文、选项码、四语说明（这个选项在账上意味着什么） |
  | `decide` | 怎么定，按顺序：账套设置（如 `srv_vattyp`）→ 按公司记住的 → 问（对应 `write_precheck` 的哪个题类；已有的 `service_vat`、`unit`、`operator_form` 直接用） |
  | `evidence` | 原生证据：哪天、哪台机器、哪本测试账套实录的；没实录过标「未核实」 |

- **开始前**：引导卡的出题源对这批单逐张跑 `trigger`：「会」「说不准」且没法由设置或记忆定下的，出一题；「说不准」的题只在这家公司第一次遇到时问，答了记住，以后不再问
  （多问至多一次）。答案随写账载荷下发（`operator.dialog_answers = {name: 选项码}`，同现有 `form_choice`）。
- **运行中**：CC 桌面版遇到登记过的 `choice` 框，有答案就按答案点；`notice` 自动点；`block` 落原因码（第 9 节：每个原因码都要有下一步）。
- **机器检查**（闸门）：① 配方 `dialogs` 里的每个名字都在登记表里，反之亦然，字段两边同值——配方里出现但登记表没有 = 红；② 每个 `choice` 行都有题类、四语标题与选项说明；
  ③ 每个 `block` 行的原因码都在第 9 节的出口表里；④ `trigger` 有离线用例（会 / 不会 / 说不准各一）。

### 10.3 做不到的地方（如实说）

1. **登记表列不全**。Express 闭源、各家还定制过菜单和弹框，只能登记配方和原生实录里见过的。「开跑后零提问」是目标，不是保证；乙类兜底必须有，而且每遇到一次就登记一个，表会越来越全。
2. **有些框事先判不了会不会弹**（取决于 Express 当时的库存、价格历史、别人刚做的操作）。这类只能标「说不准」：第一次多问一题并记住，或者等它真弹出来走乙类。
3. **乙类没法不停账套**。框弹在存单途中，单头和明细已经写了一部分；不答，这张就是半截单，同一本账套后面的单也不能动。能做到的只是：只停这一本、别的账套照跑、把问题立刻送到用户手上。
4. **人不在就只能等**。不设超时自动处理：超时要么关 Express 留下半截单，要么替人点，都违反「没有用户明确的选择不动手」。
5. **MR.ERP 的框多数还没核实**（配方里 6 项只有 1 项 `verified`），登记表里先标「未核实」，等 MR.ERP 代录真站点探路。
6. 业务选择框**永远不交给模型猜**（现有 `engine.is_choice` → 直接转人，保留）。

### 10.4 乙类框的两种做法（差别写清，请用户定）

| | 做法 A：留着等人到电脑上答（今天 CC 桌面版分支已写） | 做法 B：把框带进对话，用户选了由 CC 桌面版去点 |
|---|---|---|
| 用户要做什么 | 走到那台电脑前，在 Express 里自己点 | 在对话里（电脑或手机）点卡上的选项 |
| 对话里看到什么 | 一行「Express 里有一张未存完的单」+ 单号 | 一张题卡：框的原文、每个按钮原样列出；选了之后这张单接着存完，结果卡更新 |
| 人不在那台电脑旁 | 办不了，只能等 | 能办（只要那台电脑和 Express 还开着） |
| 记不记住 | 不记，下次同样的框还得人去点 | 按公司记住；同一个框再出现自动答；并记成「待登记」，下一版进登记表、以后开始前问 |
| 谁动了账本 | 人自己 | CC 桌面版，但只点用户选的那一个按钮（按原文匹配；框变了就不点、重新上报） |
| 风险 | 人一直不来，这本账套一直占着 | 多一条「远程点一下」的路：框的原文是泰文、不解释就让用户选，用户可能看不懂（卡上可以让 CC 用话解释，但选择必须是用户点的） |
| 要做的 | 已写，等合入 | 在 A 之上加：框的上报、对话里的卡、把选择送回那台电脑、点完续存。A 仍是 B 的兜底（人已经在电脑前自己答了，CC 发现框没了照 A 补报） |

我的建议：**做 B，A 留作兜底**。依据是用户今天两句话（「要点的要做的可以引导式啊……决定交给用户」「把一切要用户做的选择提前备好」）；10-30 否决的是另一件事。但 B 多了一条远程点账本的路，
属于产品方向，请用户点头后再排（排在 P2 的代录各类票里，约 10–14 小时写码 + 测试机实机 4–6 小时，要发新版 CC 桌面版）。

### 10.5 与 CC 桌面版窗口的接缝（可直接转发）

> 引导式总设计的要求（经主会话），接在你今天的半截单接缝（a–e）之后，不改已定的五条：
> **① 登记表**：框的登记放共用层纯契约 `pearnly_core/express_operator/choice_points.py`（名字、匹配文字、类别 notice / choice / block、选项按钮原文与选项码、怎么定），
> 配方 `dialogs` 每一项按名字对上它，两边同值由跨边测试比对；配方里有、登记表没有 = 闸门红。请确认现有 13 + 6 项各自的类别和按钮清单，以及每项的原生证据（哪天哪台机器）。
> **② 运行中按预先的答案答**：载荷新增 `operator.dialog_answers = {框名: 选项码}`（同 `form_choice` 的做法）；遇到登记过的 choice 框，有答案就点对应按钮，没答案按 ③ 上报并带上框名。
> **③ 没登记的框怎么上报**：回执 `meta.operator` 新增 `dialog = {digest, title, text, buttons: [按钮原文…], doc_type, stage: saving | editing, name?}`——标题、正文、按钮都是屏幕原文
> （不翻译、不归纳），长度与条数上限你定，服务端 `clean_operator_meta` 照此放行；`digest` 由标题 + 正文 + 按钮 + 单种算出，用来认「是不是同一个框」。请告知现在
> `win32_desk.windows` 的 buttons 列能不能稳定读全按钮原文，读不全的情况有哪些。
> **④ 收到选择后怎么点**：服务端派一个只给 `held.computer` 的指令（投递号 = 原来那件、`digest`、按钮原文）。CC 先核四样：还是当初那个 Express 进程、框还在、digest 没变、
> 按钮还在；都对才点这一个按钮，然后接着走原来的存单流程，用同一件的回执报终态（就是接缝 e 的补报）。任何一样不对：不点，回 `dialog_changed` 并带新的 `dialog`。
> 请告知指令从派出到 CC 领到要多久（held 期间现在是 60 秒只读看一次，要不要为这种指令缩短）。
> **⑤ 记住与待登记**：用户的选择站点按公司 + digest 记住，下次同一个框随 ② 的 `dialog_answers` 下发（键用 digest）；站点另记一张「见过但没登记的框」清单给开发，下一版进登记表。
> **⑥ 不变的**：业务选择框不交模型（`is_choice`）；人不在就一直等、不超时；只停这一本账套。做法 B（③④）等用户点头才施工，①②⑤ 的登记与下发不依赖它。
