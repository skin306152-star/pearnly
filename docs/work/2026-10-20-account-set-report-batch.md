# 工作包：账套整份上报批量写（CC 教程问题第 10 条的服务端部分）

## 目标和范围

- 目标：CC 桌面版把整份账套名单（实测 679 份）随心跳 / 配对健康检查报给一条连接时，服务端不再逐行登记、长时间持连接行锁；
  679 份首次上报在测试机 < 1 秒级，重复上报更快，同一连接上别的电脑的领取不再被拖到秒级。
- 本次不做：客户端（`pearnly/cc-desktop-runtime-fixes` 已加重试、放宽整份心跳读超时，不动它）；合入 main；部署；生产复测。
- 本次范围状态：待审查（分支已推，CI 结果见下）。收尾状态：交接保留（等开发窗口按主线集成合入、随下一批部署）。
- 分支 `pearnly/account-set-report-batch`，基线 `origin/main` `241b9ef8`；工作树为本任务的独立工作树（桌面 App 建的 `agent-a121a1fc…`）。
- 必要外部操作：只用了测试机 cowork 栈（抢锁 `~/pearnly-devtools/locks/testenv.lock`），没切域名、没碰生产。

## 计时与根因

测试机（WSL2，生产同一份镜像 `sha256:1d71f442…`，`testcowork` 导入副本），脚本
[`scripts/cowork-account-set-report-lab-timing.py`](../../scripts/cowork-account-set-report-lab-timing.py)：建两条带合成标签的
Express 连接，按心跳同一条路（先锁连接行 → `reports.plan_report` → `collector.ingest`）报合成的 679 份名单，每轮单独提交；带「领取」的轮次
另开一条数据库连接对同一连接行 `FOR UPDATE`（`companion.queue_api.lease` 的第一步）量被挡多久；结束删掉合成连接在池里的全部行。

基线剖析（`--profile`，cProfile 本身约拖慢 3 倍，看比例）：

- **首次整份 679 份**：`targets.identity.resolve` 占约一半——第 2 条规则逐份扫整张登记、逐份规整网络路径（`normalize_location`
  23 万次，n²）；另一半是 1359 次 Frappe 文档 `insert`（每次校验、钩子、`clear_in_redis` 清文档缓存，真正的 SQL 只占 0.5 / 3.0 秒）。
- **第二台首次 / 录入标记全变**：每份认上的登记都 `get_doc(for_update=True)` + `save`（CC 1.9.1 的录入标记每天变，两台电脑扫的时刻不同
  也会互相改写 `attributes_json`），679 次读 + 679 次存。生产 11:02:17 那次「已登记过、仍 10.28 秒」的例行整份心跳属于这一类。
- **待认定整份认上**（旧版电脑升级后带文件号重报，另一台等着的 679 行在同一次心跳里认上）：`reconsider` 每认上一行就整表重读登记与
  可达、每行重算一遍认定表，n² 次 SQL 行与计算，14 秒；整份待认定期间每次心跳重核也要 1.6 秒。
- 全部发生在心跳一开始锁住的连接行之内；领取第一步也锁这一行，所以被挡的时间 = 心跳处理时间。生产比测试机慢约 5 倍
  （测试机首次 2.1 秒，生产 10.2 秒：共用的数据库 / Redis / CPU），量级一致。

## 变更与决定

- `targets/identity.py`：新增纯内存索引 `Registry`（按文件号、规整后网络路径 + 内容键、内容键、规范键），`resolve` 每行只看命中的
  那几份；同一条件仍取登记顺序里的第一份（与逐份扫逐条相同，测试用随机数据对照）。`resolve` 仍接受列表（内部建索引），外部调用不变。
- `connections/pool.py`：
  - `apply_report`：登记与可达开头加锁读一次（原来也读），认定共用一份索引；新登记、可达行攒到最后批量写（`_Writes`）：
    多行 `INSERT … VALUES (…), (…)`（参数化，每条 200 行；不用 `frappe.db.bulk_insert`，它逐值拼查询构造器，1358 行要 0.35 秒），
    改了的行只写变了的列、同一组列一条 `UPDATE … SET 列 = CASE name WHEN %s THEN %s … END … WHERE name IN %s`，删一条语句；
    内容没变的行一条不写。
  - `reconsider`：同样一次读、一份索引；之后在内存里跟着改（不再每认上一行整表重读），认上一行只换那一份登记在各台电脑索引里的样子，
    写入同样批量。
  - 文档写入做的事照样做：名称取 `record_key`、唯一列空值存 NULL（核过 Frappe 16.33 `get_valid_dict`，本表只有 `record_key` 唯一；
    `uid` 是普通索引）、整数列空值存 0、文字超长报错不截断、规范根只从空补一次（`_refresh_registration` 里同控制器一样拒绝）；
    `modified` / `modified_by` 照写。新行一行一个创建时刻（相差 1 微秒），`ORDER BY creation, name` 仍是上报顺序。
  - 零散的单行写（标 `stale`、记最近写入、改挂电脑、补登记、账套资料）不变，仍走文档写入。
- 加锁顺序、读视图规则（`test_cowork_connection_read_locks`）、身份 / 写者锁 / 幂等 / 唯一性都没动；认定规则本身没改。
- 有意的细小差别：重核在同一轮里若某行已被前面一行认上（同一台电脑同一份账套那一行），不再拿它的旧副本再处理一遍（旧代码会删掉刚写好的
  那行再按旧值重插）；重核看到的登记是本轮已改过的（旧代码只在新登记后才重读，补上文件号后仍拿旧值）。两者最后都与库里一致。
- 没有表结构、补丁、hooks 变化，**无迁移**；`connection` 列两张表上本来就有索引。
