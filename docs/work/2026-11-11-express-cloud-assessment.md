## 一屏结论

1. **做法**：云端主机上跑一份「云端 CC」（就是号池里多一台电脑，直写、代录代码不改）；它不能上网，所有联网改走「文件隧道」：
   请求写进映射盘，由**客户装了 CC 的那台电脑（桥）**代发到本站、回复写回。桥上的 CC 自己挂一个看不见的远程桌面会话来连云端。
2. **服务端几乎不改**：云端 CC 的登记由桥上已登录的对话页代办（现有 `register` 接口本来就收设备密钥），通道、派单、写者锁、
   PEARNLY.LCK、ISRUN 占用探测全部照旧。只加一个显示用的「经哪台电脑」字段（可选）。
3. **零新增固定费用**；桥电脑多一个系统自带的远程桌面进程（估 50–80 MB 内存），空闲时 CPU 取决于隧道轮询频率，要实测压到近 0。
4. **能不能做成取决于 6 项实测**（第 11 节 T1–T6），其中两项一票否决：远程桌面会话藏起来后云端是否继续跑（T2）、
   CrowdStrike 是否拦没签名的 CC（T6）；T3（同账号会不会挤人、第二个 Express 占不占名额）照测，结果定「同一账号」规则的细则。
5. **工期**（机器耗时）：先实测约 3 小时（要用户输一次云端密码）；施工写码约 30–38 小时 + 机器约 8 小时；之后真写测试公司验收。
6. **第 12 节的待定项**：测试公司已定 Z1、账号问题已按用户口径删掉、「经哪台电脑」字段做；还剩实测哪天、云端包分不分（等 T5）。

## 0. 需求原文与理解

- 原话（用户，11-09～11-11，中文）：CC 要支持「云端 Express」（Express Software Group 托管、经 TSplus 远程桌面访问）；
  直写和代录都要、Cowork 和 ERP 都要；设置-连接里加「连接云端 Express」，由用户本人输入远程桌面账号密码授权；
  不请 Express 放行 IP（「不问，就按计划做」）；中转用客户自己装了 CC 桌面版的电脑，关机就排队、开机补写；开发测通先用办公室测试机当桥。
- 我的理解：事务所 / 客户里有人的 Express 账套不在本机或局域网，而在 Express 云上（例：主机 CLOUD-HOST，数据根
  `D:\CLOUDUSER\ExpressI-Cloud`，16 家公司）。要让这些公司在 Cowork、ERP 里和本地账套一样：读主档、直写、代录、读回核对、等账套排队。
- 不在本次范围：
  - 不做我们自己的中转服务器 / 租机器（用户已否）；不请 Express 开白名单；
  - 不做云端的「文件夹自动录入」（云端没有客户的单据文件夹，票据照旧在客户本机 / 网页上传）；
  - 不做 MR.ERP 在云端（MR.ERP 本来就是网页，与此无关）；
  - 不做多台桥电脑分摊同一个云端（两台桥填了同一账号按「同一账号」规则处理，不互抢，见第 4.1 节）；
  - 不改直写、代录本身的业务逻辑。

## 3. 按类通用

- 这一类 = 「CC 桌面版够不着、要经别的电脑才能到的 Express 账套」。目前只有 Express Cloud（TSplus / RDP）一家。
- 做法按类通用：隧道 transport 不认 Express Cloud，只认「这份 CC 没有直接网络、经桥出网」；远程桌面那一层只认标准 RDP
  （TSplus 便携客户端底下就是系统 mstsc）。以后别的托管商只要是 RDP + 磁盘映射就能复用，不为 CLOUD-HOST 写死任何东西。
- 覆盖 Cowork、ERP 两种成员、直写、代录、按需读取（`express_read`、`express_masters`、`express_marks`、`account_history`、`express_receivables`）。
- 不覆盖：文件夹自动录入、MR.ERP 只读成员（云端不需要）、自动更新（云端版本跟着桥走）。

### 4.1 桥：CC 桌面版内嵌「云端会话管理 + 隧道转发」

- **放哪**：`companion/src/companion/cloud_link/` 新域包（`session.py` 会话、`tunnel_relay.py` 转发、`deploy.py` 部署云端 CC、`state.py` 状态），
  跑在单独子进程 `companion.exe --cloud-link`（同 1.9 窗口进程的做法：托盘按需拉起，经本用户本地管道说话）。没连云端的电脑不导入、不起进程，
  对现有用户零影响（「CC 桌面版要轻量」）。
- **会话怎么起**：不用 TSplus 便携客户端（参数加密、拉起的就是 mstsc），CC 自己写 `.rdp` 调系统 `mstsc.exe`：
  `full address:s:<主机>:<端口>`、`drivestoredirect:s:<隧道盘>`（只映射隧道盘，不把客户整个 C 盘给云端看）、`redirectclipboard:i:0`、
  `audiomode:i:2`、`keyboardhook:i:1`、低分辨率（1280×800、16 位色，够代录截图）、`autoreconnection enabled:i:1`。
  主机地址怎么来：首选从 TSplus 客户端拉起的 mstsc 进程命令行 / 临时 `.rdp` 里读（用户只需指一下 Express 给的那个 exe）；读不到就让用户填地址（T1 定）。
- **怎么不打扰用户**：首选把 mstsc 开在 CC 自己建的**独立桌面**（`CreateDesktop` + `STARTUPINFO.lpDesktop`）上，用户屏幕、任务栏都看不到；
  窗口不是「最小化」，客户端不会叫云端停画。备选（T2 不通时）依次：①CC 子进程里内嵌 RDP 控件（`mstscax`）放在屏幕外窗口；
  ②普通 mstsc 最小化 + `HKCU\Software\Microsoft\Terminal Server Client\RemoteDesktop_SuppressWhenMinimized=2`（任务栏看得见一个图标）。
- **怎么保活**：
  - 断线（网络、云端重启）：子进程看 mstsc 进程退出 → 1、2、4…最多 15 分钟重连；桥睡眠 / 关机就断，开机后 CC 自启时接着连（排队补写由服务端照旧派）。
  - 云端空闲断开（服务器策略）：云端 CC 在会话里每几分钟发一次不可见的输入（带 `CC_INPUT_MARK`，`presence` 已经会忽略自己的输入），T4 实测要不要。
  - 防睡眠：沿用 `keep_awake`（「CC 开着时保持电脑唤醒」默认开）——有云端成员连着就算「有成员连着」。
- **授权入口（用户 11-15 定，覆盖下一条的「Windows 原生凭据框」）**：放在 CC 桌面版「设置 → 连接」，与 Express（本机文件夹）、MR.ERP（登录）并列加一行「云端 Express」；
  点「连接」在 CC 自己的界面里出账号、密码输入（照 MR.ERP 登录那套组件与样式），不弹 Windows 系统密码框，也不放进对话。CC 拿到后：
  ① 账号按 TSplus 的写法拆成用户名 + 域（11-15 实测：TSplus 成功时送的用户名是 `CLOUDUSER-01`、域 `example`；用户在 Windows 框里改了用户名那栏就连错 7 次，原因码 2055）；
  ② 用 `CredWrite` 存进本用户的 Windows 凭据管理器（`TERMSRV/<主机>`，域凭据类型，DPAPI），密码不进服务器、不进日志；③ 自己写 .rdp（`full address` 只写主机、`server port` 单写端口、`username` / `domain` 写上）发起连接。
  失败不自动重试：连接页这一行显示「登录失败」等状态（原因从客户端日志的断开原因码判断：2055 = 账号或密码不对），人改了再点「连接」才再试，防止云端锁账号。
- **11-15 实测补充**：新版 Windows 对没签名的 .rdp 每次连接都弹「远程桌面连接安全警告」，并且默认不勾「驱动器」。CC 要么给自己生成的 .rdp 签名（自签证书加进本用户的受信任发布者），要么由 CC 在自己起的 mstsc 上自动勾驱动器并点「连接」（实测可行）。TSplus 存的凭据是旧式 Generic 类型，我们开网络级身份验证的连接用不上，不能沿用。
- **凭据存哪**：授权那一次用**可见**的 mstsc 窗口，由用户本人在 Windows 原生凭据框里输入云端账号密码并勾「记住」——
  密码由系统存进 Windows 凭据管理器（`TERMSRV/<主机>`，DPAPI 加密），**CC 自己看不到、不经手、不进服务器、不进日志**；
  同一次接受云端证书（存 `HKCU\…\Terminal Server Client\Servers\<主机>`），以后后台连接不再弹框。断开时 CC 删这条凭据和证书记录。
  （若云端策略「每次都要求输入密码」，后台连接会卡在登录框 → T3 实测；那时改为 CC 用 `CredWrite` 自己存同一位置，仍然只在本机、仍然用户本人输。）
- **同一账号（用户 11-11：输入啥账号密码就用啥账号密码连接）**：产品不区分 CC 专属账号还是员工账号，不要求客户另开账号。用员工自己的账号时，
  桥连云端可能把员工挤下线，员工登录也可能把桥挤下线。按类处理，照 MR.ERP 被踢的做法（`mrerp_operator/session.py` 的 `KICKED`、原因 `account_in_use`：
  不自动重登、被踢后不走退出登录）：
  - **挤人 / 被挤都记标记，不自动去抢**：桥连上时发现把别处同账号的会话挤下线了（判断依据 T3 定：例如连上的是一个已有会话、云端 CC 在会话里看到别的程序开着），
    或者桥自己的会话被别处登录挤掉（mstsc 断开原因是「另一处连接接管」，RDP 错误信息 `ERRINFO_DISCONNECTED_BY_OTHERCONNECTION`），就记「账号在别处使用」标记，
    后台**不再自动重连**（来回互挤）。设置-连接那一行和对话里显示这个状态，人点「连接」才再连。普通断线（网络、云端重启）照旧自动重连。
  - **被挤后不注销**：被挤后会话已经是那个人的，桥只关自己的 mstsc，不让云端 CC 执行注销（同 MR.ERP 被踢后不走 `logout.php`）。
  - **代录占界面，有人在用就不开**：开一批代录前，云端 CC 看自己这个会话里有没有人在用（连着的客户端不是这台桥、或最近有不是 CC 发的键鼠输入，判断依据同 `presence`），
    有人就不开，这一批照现有「等电脑空出来」排队；**直写照常**（不碰界面），账套被员工开着就照旧「等账套」排队。
  - T3 测出来的结果定细则：服务器允许同一账号多个会话 → 一般不会挤人，主要处理「第二个 Express 占名额」（占名额时代录按「等电脑空出来」排队、不抢员工的名额）；
    一账号一会话 → 连接就会接管员工的会话，规则按上面「挤人记标记」走，并在第一次连接时就能看到。

### 4.2 云端那份 CC：部署、升级、配对

- **程序**：同一份构建（PyInstaller onedir），启动参数 `--cloud`：不起托盘、不开窗口、不发系统通知、不自动更新、不写开机自启、不防睡眠；
  文件夹自动录入、MR.ERP 成员不起。为省拷贝量，可在 `release.ps1` 多出一份去掉网页内核（QtWebEngine 约 200 MB）的「云端包」
  （估 60–90 MB，按 11-09 实测 2 MB/s 拷一次 30–45 秒）。是否值得多一份包，T5 看拷贝时间再定；不值得就整包拷（约 2 分钟，只在升级时一次）。
- **怎么放上去、怎么启动**：桥把云端包放进隧道盘的 `dist\<版本>\`；云端由一个很小的启动脚本把它拷到云端用户目录（11-09 证实 D: 可写；具体目录 T5 定，
  不放 P: 漫游桌面），再运行。启动脚本怎么在云端第一次跑起来（云端没人点）：
  - 首选 `.rdp` 的 `alternate shell:s:`（登录即运行启动脚本，会话里只有它，不开资源管理器）——服务器策略允许才行，T5 实测；
  - 备选：授权那一次（可见窗口、用户在看）由 CC 自动按 Win+R（`keyboardhook:i:1` 让 Win 键给云端）打一行命令，把启动脚本放进云端「启动」文件夹，之后每次登录自动跑。
- **升级**：云端版本**跟着桥走**：桥升级后，下次会话开始时启动脚本比对版本，不同就拷新的、换目录、删旧目录；中途不热升级（正在写的单写完再换）。
  不走现有自动更新（云端下载不到安装包，也不该在客户托管主机上跑安装器）。
- **配对（自动交接，不用配对码）**：
  1. 桥为这台云端电脑生成一把**设备密钥**（存桥的 DPAPI，与现有 `device_link` 同样格式）；
  2. 云端 CC 启动后经隧道报「我在了」+ 找到的 Express 数据根（`express_locate`，已在云端跑通）；
  3. 桥上**已登录站点的对话页**用这把云端设备密钥调现有登记接口（ERP：`pearnly_core.cc_desktop.api.register`；Cowork：`pearnly_cowork.companion.api.register`），
     设备名写「<云端主机名>」；拿到的令牌**只存桥上**（DPAPI）；
  4. 云端 CC 请求里的 `Authorization` 由桥的隧道转发换上真令牌——**令牌和设备密钥都不落云端磁盘**（第三方托管主机上不留我们的密钥）。
  - 服务端因此不需要新的配对接口；电脑列表里多一台「CLOUD-HOST」，移除它 = 吊销令牌，桥收到 401 后停用这条云端连接（沿用 1.9.1 的 401 规则）。

### 4.3 文件隧道：协议、并发、超时、安全

- **映射范围**：桥用 `subst`（或 `DefineDosDevice`）把 `%LOCALAPPDATA%\Pearnly\cloud\<连接>\` 映射成一个空闲盘符，`.rdp` 只映射这个盘。
  云端只看得到隧道文件夹，看不到客户的 C 盘、S 盘（T2 实测 mstsc 能否映射 subst 盘；不能就退回映射 C 盘但云端 CC 只碰隧道路径，并在评估里记风险）。
- **目录**：`in\`（云端→桥的请求）、`out\`（回复）、`ctl\`（会话握手、版本、停止）、`dist\`（云端包）。
- **一次请求**：云端写 `in\<序号>-<随机>.part` → 写完改名 `.req`（改名是原子的，桥不会读到半个文件）。头一行 JSON：
  `{v:1, id, epoch, seq, method, path, query, headers(白名单), body_sha256, timeout, mac}`，后面是正文字节。
  桥用 `ReadDirectoryChangesW` 盯 `in\`（本机文件夹，事件驱动，空闲零 CPU）→ 校验 → 代发 → 写 `out\<id>.part` 改名 `.resp`（状态码、白名单头、正文）。
  云端等回复时每 100 ms 起、逐步放宽到 1 秒看一次 `out\`；读完删。桥每 10 分钟清一次超过 10 分钟没人取的文件。
- **防伪造、防重放**：每次会话开始桥生成会话号 `epoch` 和 32 字节密钥 K，经 `ctl\` 交给云端 CC（云端只放内存，读完桥删文件）；
  每个请求带 `HMAC-SHA256(K, epoch|seq|id|method|path|body_sha256)`；桥只收本会话 `epoch`、`seq` 递增或在窗口内、`id` 没见过的；
  不靠两边时钟（云端时钟可能和桥差几分钟）。
- **只放行本站**：桥只发到**这条云端连接配对时记下的站点**（`https://<租户域名>`，固定 443），路径只许
  `/api/method/pearnly_cowork.companion.*` 与 `/api/method/pearnly_core.cc_desktop.machine.*`（按现有调用逐条列白名单，测试守住），
  不跟随重定向，请求里带的主机名一律忽略。所以云端 CC 只能经桥出网，而且只能到本站这几条机器接口；隧道不能被拿来当通用代理。
  `operator_ai`（代录 AI 接手）本来就走站点的机器接口，照样通；`updater` / `health_check` 在云端模式不起。
- **并发**：云端 CC 有好几条线（取任务、按需请求、心跳、认电脑、代录 AI），可以同时有多个请求在路上；桥用 4 条线并发代发（共用一个保持连接的 httpx 客户端），
  云端最多 8 个在路上，多了在云端排队。各请求互不依赖，不保证顺序（现有代码本来也不依赖跨线程顺序）。
- **大小**：单个请求 / 回复上限 32 MB（现有按需请求按 4 MB 分块交回，`request_contract.CHUNK_BYTES`；最大的 `express_read` 整件 50 MB 本来就分块），
  超了在云端直接报错，不写进隧道。
- **超时与出错的样子**：云端等待时间 = 原请求超时 + 5 秒；桥那边失败（站点连不上、超时、桥不在）一律在云端变成 httpx 的**网络错误**（`ConnectError` / `ReadTimeout`），
  **绝不伪造 401 / 403 / 404**——CC 现有逻辑把 401 当密钥被吊销、403 / 404 当旧服务端（1.9.1），伪造会把成员停用。
- **日志**：桥只记方法路径、状态码、字节数、耗时，不记正文和头。
- **代码落点**：云端这一侧加一个 `httpx.BaseTransport` 子类（`cloud_link/tunnel_transport.py`），在 `http_tls.py` 旁加统一建客户端的入口
  `net.client(**kw)`，11 处 `httpx.Client(...)` 改调它（机械替换，单独一个提交）；`mrerp_operator/session.py` 的 `urllib` 只在 MR.ERP 用，云端不起，不改。
  加一条架构检查：`companion/src` 里不许再直接 `httpx.Client(`（只许 `net.py`），防止以后新加的联网绕过隧道。

### 4.4 直写和代录在云端怎么跑

- **直写**：云端 CC 收到的任务和本地完全一样；账套在云端 D: 本机盘。写前 `account_lock` 独占 ISRUN（云端员工开着这本账时拿不到 → 照旧「等账套」排队，
  不算失败）；`account_write_lock` 锁 `PEARNLY.LCK`（云端本机文件锁有效；云端盘不对外，别的电脑看不到这份账套，所以这把锁挡的是云端 CC 自己的 Cowork、ERP 两个成员）。
  CDX 索引程序 `cdx_reindex_runner.exe` 随云端包带上（T6 看 CrowdStrike 让不让跑）。`account_uid` 写前核对照旧（云端卷序列号 + 文件号）。
  - 注意：云端员工通常整天开着 Express，**白天大部分时间可能拿不到独占**，直写会在员工下线（午休、下班）后才写进去。这与局域网客户一样，但云端员工开着的时间可能更长，验收时实测白天能写进几成。
- **代录**：照 `express_operator`，云端会话里 CC 自己开一个 Express（后台做法 `bg_desk`：发窗口消息、`PrintWindow` 截图，不需要真键鼠）；
  会话里没人，所以 `presence` 永远不会因为人动而暂停。Express 登录（若云端 Express 要登录）用户本人在桥上的代录页「授权登录」输一次，
  存**桥**的凭据管理器，每批开录前经隧道交给云端 CC（只在内存，不落云端磁盘）。
  - 风险：代录要求会话**在画画面**（藏起来的会话云端会不会停画，T2 实测）；代录会多占一个云端 Express 用户名额（T3 一起看）。
- **互斥照常**：同一份云端账套由云端 CC 的 Cowork、ERP 两个成员共享时，PEARNLY.LCK 照旧挡；ISRUN 照旧挡员工正开着；两站点写者锁、幂等、读回核对全不变。

## 5. 隔离与权限

- 租户：云端 CC 的每个成员都是经桥上**已登录用户**在**那个站点**登记的电脑，令牌按站点、按签发人（`issuer_valid`）由服务端核；
  桥只把这条云端连接的请求发到它配对时的那一个站点，不会把 A 租户云端的请求发到 B 租户。
- 同一台桥电脑同时连 Cowork 和 ERP：云端 CC 也有两个成员，位置给谁读照 1.12.17 `place_channels`（有 Cowork 成员时默认只给 Cowork，ERP 要勾）。
- 云端主机是 Express 托管的多用户机：隧道只存在于我们这个会话的 `\\tsclient`，同机别的用户看不到；令牌、设备密钥不落云端磁盘（第 4.2 节）。
- 两台桥填了同一个云端账号：照第 4.1 节「同一账号」规则，谁被挤谁记标记、不自动重连，不互抢；服务端电脑行记「经哪台电脑」，看得出现在是哪台桥在连。
- 权限：谁能点「连接云端 Express」= 现在谁能在这台电脑的 CC 里加 Express 位置（同一规则，服务端的登记接口照旧核 `products.allowed`）。

## 6. 入口：网页、手机、LINE、拍照

- **CC 桌面版设置 → 此电脑 → 连接**：新入口（第 10 节）。
- **网页 / 手机的 CC 对话、Cowork / ERP 网页**：不改；云端公司和本地公司一样出现在公司选择、写账确认卡里，派到「CLOUD-HOST」这台电脑。

- **LINE、拍照**：不涉及，票据照旧从这些入口进，只是写账落到云端电脑。相机不涉及。

## 8. 存储与成本

- **固定费用：零**。不买机器、不租服务器、不加云服务；Express 那边的费用见下一条。
- **客户费用**：不要求客户另开账号（用户 11-11）。代录在云端多开一个 Express 时可能多占一个用户名额（T3 测）；占满时代录排队，不需要客户加名额。
- **桥电脑资源**（老办公机，「CC 桌面版要轻量」）：
  - 内存：mstsc 约 50–80 MB + `--cloud-link` 子进程（Python，不带网页内核）约 40–60 MB；只有连了云端的电脑才有；
  - CPU：隧道转发事件驱动，空闲时只剩云端 CC 的例行请求——现在每个成员取任务每 3 秒、按需请求每 15 秒、心跳每 60 秒，两个成员约每分钟 50 次往返；
    每次桥上一读一写一个小文件 + 一次保持连接的 HTTPS，估每次 5–10 ms CPU，合计约占一个核的 0.5–1%，**不满足「空闲近 0」**。
    办法：云端模式取任务空闲间隔放到 15 秒（派单最多晚 15 秒，代录 / 直写本来就以分钟计），合计约每分钟 12 次；T4 实测桥的 CPU，不够再看服务端加「有活才叫」。
  - 网络：远程桌面画面静止时每秒几 KB；拷云端包每次升级一次 60–200 MB。
  - 磁盘：隧道文件夹用完即删；云端包放隧道盘一份（升级后删旧版）。
- **云端主机**：云端 CC 约 100–150 MB 内存、空闲 CPU 近 0；占云端用户目录 60–200 MB。原件不经云端（照旧统一原件层 ADR-024）。

## 9. 删除、作废、追溯

## 15. 每次连接都弹的「远程桌面连接安全警告」怎么处理（11-15 实测后）

实测事实：
- 新版 Windows 对**没签名的 .rdp 文件**，每次打开都弹「警告：未知的远程连接」，而且默认不勾任何资源（驱动器、剪贴板等）。TSplus 客户端也一样，用户每次都要手点。
- 这个框属于「用 mstsc 打开 .rdp 文件」这一步。框里没有「不再询问」。
- 被挤下线时的提示原文是「你已断开连接，因为已与远程计算机建立了另一个连接」，客户端日志断开原因码为 3。

**11-16 更正（以这段为准）**：「由程序自动勾选并点掉这个安全警告框」**不做**。这个框是 Windows 的防钓鱼安全提示，用程序自动点掉等于绕过安全控制；施工子代理写这段时被安全审查拦下，我们认同。11-15 实测时，测试脚本自动点过这个框 3 次，那段代码已从探针脚本里删掉。做法改为：
- 主路线：CC 内嵌 Windows 自带的远程桌面控件，不打开 .rdp 文件，本来就不经过这个框（要用户在场验证一次）；
- 兜底：给 CC 生成的 .rdp 签名，并把证书设为受信任的发布者（Windows 正规机制，每台电脑管理员设一次）；或者每次由用户本人点「连接」。

同时，桥端会话管理里「读系统日志判断断线原因」也被拦下。整条「在后台、用户看不见的桌面上自动管理远程会话」的形态待用户重新确认，建议改得更透明：
- 云端连接做成 CC 自己的可见窗口，默认最小化，用户随时能关；
- 断线原因只用连接组件自己的回调；
- 请用户再考虑一次要不要告知服务商。

以下是原分析（其中第 ① 种已作废）：

三种做法：

| 做法 | 用户手工步骤 | 稳定性 / 风险 | 结论 |
| --- | --- | --- | --- |
| ① CC 替用户点（勾「驱动器」再点「连接」） | 无 | 11-15 实测 3 次都成功。但框的文字随系统语言变（要按控件编号认，不能按文字认）；Windows 更新可能改框的样子或加新框，改了就连不上。只能当兜底 | 兜底 |
| ② 给 .rdp 签名（自签证书，不买证书） | 视情况：签名本身用系统自带的 `rdpsign` 就行；但要让 Windows「信任这个发布者」，得把证书指纹写进本机策略（`HKCU\Software\Policies\…\TrustedCertThumbprints`），普通用户没有权限写，要管理员 | 老办公机上要人用管理员身份操作一次，并且已签名的文件在新系统上会不会照样弹一次框、带不带记住选项，还没实测 | 不推荐 |
| ③ 不打开 .rdp 文件，CC 自己内嵌系统自带的远程桌面控件（mstscax，Windows 自带，不另装）建会话 | 无（只在 CC「设置 → 连接」输一次账号密码） | 这个警告只在打开 .rdp 文件时弹，用控件不经过这一步。账号密码可以由 CC 直接交给控件，也就不会弹 Windows 密码框，正好符合用户「在 CC 自己界面里完成」的要求。控件窗口可以放在屏幕外或不可见，也就是评估第 4.1 节的备选做法，兼顾「藏起来」。代价：多写一个控件宿主（预计写代码 3–4 小时），要在测试机1 上先验证一次 | **推荐** |

推荐：③ 为主、① 兜底。用户最终的手工步骤只有一次，在 CC「设置 → 连接 → 云端 Express」里输账号密码。之后连接、重连、勾驱动器全由 CC 自己做，不再弹任何系统框。③ 动工前，先在测试机1 上用控件连一次云端，验证「不弹警告框、账号密码能交给控件、窗口藏起来照常」这三点。
