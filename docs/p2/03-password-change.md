# P2.03 账号自助改密（三个产品共用）

日期：2026-09-17。用户要求：三个产品里，租户和员工都能自己改密码，入口放在**头像点开的"密码更改"**里，表单是「当前密码 / 新密码 / 确定新密码」，三个产品共用同一套逻辑。

## 实现位置（共用层）

全部落在 `pearnly_core`——这是它能被三个产品共用的原因：

| 文件 | 作用 |
|---|---|
| `pearnly_core/password.py` | 改密接口 `pearnly_core.password.change_password` |
| `pearnly_core/www/pearnly-password.html` | 表单页面（当前密码 / 新密码 / 确定新密码） |
| `pearnly_core/www/pearnly-password.py` | 未登录直接跳登录页，不暴露表单 |
| `pearnly_core/public/js/pearnly_password_menu.js` | 头像下拉里加"密码更改"入口 |

产品页面接入时只需指向同一个路由 `/pearnly-password`，不需要各写一套。

## 校验规则

- 三项必填；新密码两次必须一致；新密码至少 8 位；新密码不能与当前密码相同。
- **当前密码必须真的对**——不是只看会话是否有效。
- 改的是**统一账号**的密码，即身份服务里的那个密码；站点本身不存密码。

## 实测结果（四个场景全过）

脚本 `scripts/sample-password-change.sh`，先走完整 OIDC 登录拿会话，再从页面取 CSRF，然后逐个场景验证：

| 场景 | 结果 |
|---|---|
| 打开 `/pearnly-password`（已登录） | 页面正常渲染，表单字段齐全 |
| 当前密码填错 | **拒绝**：`AuthenticationError: 当前密码不正确` |
| 两次新密码不一致 | **拒绝**：`ValidationError: 两次输入的新密码不一致` |
| 正确改密 | **成功**：`{"message":{"ok":true}}` |
| 用**新密码**重走完整 OIDC 登录 | **成功登入** `tenant-admin@sample.local` |

最后一条是关键：新密码确实写进了身份服务，不是本地假改。脚本可重复执行，已用它把样板密码改回 `KcLocal123!`。

## ⚠️ 与计划的一处偏离，明确记录

计划里写的是「禁止密码授权（Resource Owner Password）grant」。

- **登录没有使用密码授权**，仍然只走授权码 + PKCE，这一点没变。
- 但"输入当前密码"这个要求需要一条校验通道：密码存在身份服务里，站点无法自行比对。
- 因此开了一个**专用客户端** `pearnly-password-check`：它只开密码授权，**不能发起登录跳转、没有服务账号、没有其它权限**。服务端拿用户填的当前密码去换一次令牌，成功即说明正确，令牌立刻丢弃。
- 另有一个服务账号客户端 `pearnly-admin`，只被授予 `realm-management` 的 `manage-users` 与 `view-users`，用于执行改密。

**如果你不接受这条通道**，替代做法是把"当前密码"字段去掉，改成要求用户重新做一次身份服务登录（`prompt=login`）后再改。功能一样能用，只是多一次跳转。这条由你定。

## 未验证 / 未做

- **头像下拉里的入口只用代码交付，没有用真实浏览器点开验证过**。选择器随 Frappe 版本可能变；产品自己做界面时，直接把入口指向同一路由即可，不需要这套注入。
- 密码强度策略（长度之外）没有做；身份服务侧的策略也没配。
- 改密后**强制其它会话下线**没有做——这属于 P2 剩下的会话与撤权部分。
- 管理员代改他人密码、初始密码单次传递 + 强制首登修改，都还没做。
