# DMS 网页端的形态（收窄后）

日期：2026-09-18。这一条是**用户明确要求**的，不是我们自己的取舍。

## 用户怎么说的

> "DMS 身份证录入网页端不要了，业务几乎都在 LINE 完成，网页只负责绑定第三方 DMS
> 和其它不变，**只取消网页前端的录入入口**。"

所以网页端**只剩四件事**：

| 侧栏项 | 是否需要买功能 | 状态 |
|---|---|---|
| 首页（订阅与计费） | 人人都有 | 占位（后端还没有订阅/计费服务） |
| 连接第三方 DMS | 人人都有 | 还没做（后端不存在） |
| LINE 绑定码 | 人人都有 | **已做**（真功能） |
| 推送记录 | `push_record` | **已做**（真数据） |
| 操作员 | `roster` | 还没做（后端不存在） |

**没有"身份证录入"这一项**，这是要点。

## "取消录入入口"落成了什么

三处一起改，缺一处都等于没取消：

1. **新前端**：`frontend/src/lib/nav.ts` 的 dms 侧栏里根本没有录入项（一开始就是这么定的）。
2. **Desk 工作台**：入口标题从「身份证录入」改成「推送记录」
   （`pearnly_control/features.py` 的 `WORKSPACE_LABEL`）—— 名字本身在告诉租户
   "这里不是录入的地方"。
3. **后端权限**：那张表对业务角色**只读**（`READ_ONLY_ON_WEB`），网页端连"新增"
   按钮都不出现。这是 Frappe 的原生做法（按钮就是按 `create` 权限显示的），
   比"前端把按钮藏起来"可靠 —— 直接调接口也会被拒（实测 HTTP 403）。

⚠️ **不影响 LINE**：webhook 是 `allow_guest` 的独立通道，不走这个业务角色；
而且今天 LINE 侧只做绑定，还没有录入分支。将来 LINE 录入要写这张表时，
记得它是**网页端只读**、不是全局只读。

## 为什么"目录改了"要专门有个脚本

开通步骤的 payload 是**建单时**就存进库的字符串（`Pearnly Provisioning Step.payload`），
目录后来改了它不会跟着动。实测：老单子的 `set_oidc` payload 里就没有后来新增的凭据字段。

所以"目录改了、已经开出来的站点也要跟上"用：

```bash
scripts/sample-reapply-workspace.sh DEP-2026-0043
```

它按**当前**目录重算 `roles_payload` / `workspace_payload` 再打到站点上（幂等），
最后重启 web —— 功能清单写在 `site_config.json` 里，而 gunicorn 是 `--preload`，
不重启菜单不变。

## 验证

`node scripts/sample-verify-dms-web.mjs`（20 项，真浏览器登录真租户站 qd65956）：
侧栏五项齐、**没有**录入项、推送记录读到后端真数据、绑定码后端认、直接调录入接口被拒
（HTTP 403）、列表仍可读、Desk 工作台入口是「推送记录」。

顺带改掉两条被这次收窄弄过期的断言：`sample-verify-tenant-landing.mjs` 里 dms 那条
期望值从「身份证录入」改成「推送记录」。

## 已知的两处不足（不掩饰）

- 「连接第三方 DMS」和「操作员」两页**还是占位**：后端没有对应服务，不做假界面。
- 网页端没有"解绑"按钮：解绑目前只能在 LINE 里发「解绑」。
