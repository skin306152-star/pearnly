# 共享 OCR 容量与恢复

适用本轮 DMS 候选及 Core 共享底座。服务器现为 6 vCPU / 11960 MiB；当前生产只有 DMS 和私有计费，ERP/Cowork 的真实 OCR 业务入口尚未迁入。这里定义三产品必须共用的执行边界，不把底座准备误称成三产品端到端验收。

## 容量怎样控制

| 层 | 初始设置 | 目的 |
| --- | --- | --- |
| HTTP | 产品 Web 与识别进程分开 | 接收消息、查看页面不等待模型完成 |
| 原生后台 | DMS 普通队列 2 worker，OCR 独立 2 worker | 避免识别占满普通业务队列 |
| 三产品共享出口 | 全局 4 个在途请求，单租户 2 个 | 同一租户使用多个产品仍共用额度 |
| 供应商速率 | 每项目/区域/模型初始 30 请求/分钟 | 这是应用起步预算，不是供应商承诺的额度 |
| 429 / 503 | 尊重 Retry-After，加抖动、全桶冷却，间隔最多增为 8 倍；连续成功逐步恢复 | 防止三个产品同时重试放大拥塞 |
| 排队 | 全局 300、单租户 50，最长 30 分钟 | 超额明确拒绝，已接单持久保存；不无限占磁盘/内存 |
| 公平性 | 同桶租户轮转，满额租户跳过，过时等待者过期 | 一个公司的批量上传不长期堵住别人 |
| 时间/内存 | RQ 单任务 600 秒；网络空闲和总经过时间检查；图片 15 MiB、响应 8 MiB 上限 | 对异常输入与慢接口保持边界 |

`common_site_config.json` 的 `pearnly_ocr_budget_redis` 必须在所有产品指向同一 Redis DB6。`pearnly_ocr_budget` 可配置上述值，但所有产品必须一致；不一致会拒绝新外呼。修改共享策略须先暂停准入、排空在途工作，再统一改配置与策略记录，不能单独给某 App 加大并发。

原生队列 Redis 使用 AOF、everysec 和 noeviction，独立持久卷。HTTP/cache 不与该容量存储混用淘汰策略。每个产品保留独立 native queue DB，防止其他产品 worker 接到不属于自己的 Site。

## 失败与恢复

- 明确 429/503：工作单记录下次运行时间，归还 worker；调度进程到时投递，不用 sleep 占住执行槽。
- 模型已成功：保存结果及 usageMetadata，重启后续跑后处理与幂等记账，不再次付费识别。
- 连接/响应中断且不知道供应商是否已完成：保留 started 证据，转 uncertain，不自动重复调用。并发租约保留到原生任务硬时限之后。
- RQ 丢投递或 worker 中断：SQL 扫描按 Site 轮转、游标有界恢复。通用 Frappe scheduler 停用时 OCR 的专用投递修复仍有效；维护模式或 OCR 暂停必须遵守。
- 外部订单：永远不放进 OCR 自动重试；已有订单按单号和字段只读核查，附件/LINE 回执单独补齐，不能再建一单。
- 计费不可用：已有识别检查点保留；恢复后沿稳定 reference 记账。同一用量不会再扣一次。

只读查看某 Site 当前排队数量、最老年龄和预算：在它的原生 bench 使用 `bench --site <目标> execute pearnly_core.execution.work.metrics`。指标不输出证件内容、访问令牌或客户身份。

## 服务器与供应商的边界

开户及激活前按候选 Compose **硬限额总和**核算，至少留给宿主 1536 MiB 或物理内存 10%。当前三产品全部开启时容器预算约 12800 MiB，还未加宿主预留，因此 **现有 12 GB 主机不能按这套预算同时全开三产品**。16 GB 能放下预算，但这不等于吞吐验收或自动批准扩容。

如果排队持续增长，先看供应商拒绝率与资源峰值。内存/CPU 已高时增加 worker 会更慢；供应商限流时增加服务器不会增加 OCR 额度。先逐级压测再调预算：要求无 OOM、无重复调用/扣费、无串租户、网页响应稳定，最后评估增配服务器或供应商吞吐方案。不得根据单次空闲内存承诺百人即时完成。

当前 Gemini 使用动态共享配额，没有一个可以从现有配额列表直接认定的保底最大 QPS。Document AI 另一条基础 OCR 的实际区域配额读到 10 请求/分钟；将来接入时必须按该处理器/区域登记独立速率，不能照抄 Gemini 30。供应商官方说明：[动态共享配额](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/resources/throughput-quota)、[429 处理](https://cloud.google.com/vertex-ai/generative-ai/docs/error-code-429)、[Document AI 配额](https://docs.cloud.google.com/document-ai/quotas)。

## 本轮证据和限制

- 真 MariaDB/Redis：100 个请求、20 同时执行、两 Site/五租户，峰值严格为全局 4、单租户不超过 2；所有请求完成。35 项包含配额冷却、Redis 不可用、进程中断、已完成检查点复用、容量拒绝、磁盘/内存保护、慢响应和有界清理游标。
- 真签名 LINE webhook → 原生队列 → 两 Site → HTTP 模型替身 → 真本地计费：连续 50/80/50 共 180 次全部完成，成功外呼恰为 180，无重复；首批包含一次 429 和一次 503。各批完成 330.20 / 211.37 / 122.43 秒，提交最慢 0.944 / 0.909 / 0.527 秒。
- 首轮首页探针 327 次成功，P95 27 ms，另有 3 次 HTTP 错误；因初版只保存异常类别，不能反推这三次的精确原因。第二轮同样连续 50/80/50 共180次完成，耗时335.43/200.20/120.59秒；326次已登录首页读取全部成功，P95 28ms。
- 进一步200次HTTP账务压测复现了MariaDB11.8.9默认快照隔离下的冲突：请求校验先建立快照，等到钱包锁后读到别人刚提交的版本，报1020。首页移除写锁；数据库专用服务入口最多12次抖动重试完整未提交事务，原生提交回调禁止提交后重放。修复后100次首页读取+100笔扣费、20并发、三产品身份全部通过，P95 186ms，余额/页数/100笔流水准确；97项价格与事务检查通过。没有关闭快照隔离或财务锁。机制参考[MariaDB快照隔离](https://mariadb.com/docs/server/server-usage/storage-engines/innodb/innodb-system-variables#innodb_snapshot_isolation)。
- 两张各15MiB合成JPEG在生产同款512MiB OCR容器限制下同时处理，2/2完成，内存峰值380.85MiB，OOM/oom_kill均为0；图片填充仅验证有界传输与内存，不计作大尺寸图片识别质量。
- 真实 Gemini 单笔新链路：合成证件识别成功、记录 usageMetadata、只记一笔 1.50 THB，重放完成任务没有第二次识别或扣费。大量负载使用明确的成本免费替身，不是供应商真实吞吐测试。
- 实验机与生产 CPU 架构、网络及同时在场业务不同；测试数字不等于生产 SLA。最终发布/LINE 真机与非空销售排行仍单列验收。

脚本：`dms-line-lab-capacity.py`、`dms-line-lab-queue-load.py`、`dms-line-lab-dispatch-recovery.py`、`dms-line-lab-scheduler.py`；均须先看脚本副作用和专属实验环境限制。
