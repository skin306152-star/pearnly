**分层是老产品的设计，照搬**（这一点很关键）：`dms_client.py` **一句话都不提 Playwright**，
它只认注入的 `transport`。所以：

· 生产：`MrerpDmsAdapter.client()` 把"已登录的浏览器"包成管道塞进去；
· 单测：塞个假管道，几百行表单逻辑不用起浏览器就能验。

这让"业务对不对"和"浏览器起不起得来"能分开排查 —— 这一轮正好用上了。

## 二、那些"看着像小问题、其实是钱"的规则

老代码里有几条注释是一字千金，这里原样保留并写明为什么：

| 规则 | 不这么做会怎样 |
|---|---|
| **钉了 id 的主档不许回落首行** | id 在第 2 页会被当成"不存在"然后悄悄填了第一行 → 建单填错车型/分店 |
| **顾问栏只认钉死的 id，缺了就报错** | 顾问 = 销售提成归属，落错人**只有月底对账才看得出来** |
| **主档必须翻页取全** | 只取第一页 → "这个人不在名册"变成一句瞎话 |
| **取数失败（None）≠ 主档为空（[]）** | 把"拿不到名册"当成"查无此人"，就会建重复客户 |
| **单号撞重复要顺号重试** | DMS 的 autonum 按分店分段，跟全局唯一约束会失步 |
| **PHP 返回 200 不算写库成功** | 建完要 search 复核、改完要重读姓名复核 |
| **同渠道订金不许合并** | DMS 每渠道只有一组字段，拼起来会伪装成一笔 → 金额错 |
| **附件要回读校验** | HTTP 200 不代表真挂上；而且只发文件字段会把单据既有字段冲空 |

## 四、踩到的两个"看着像 bug、其实是测试写错"

第一轮 A 部分 39 项里有 3 项红，逐个查下来**都是测试自己写错**，但第一个暴露了
老代码一个值得记下来的行为：

**下拉"没选"会以空串回到 data 里。** `_selected_value` 在没有 `selected` 时取
**第一个 option 的值**，而真实表单第一项通常是 `<option value="">-- เลือก --</option>`
占位 → 得到空串。（"取第一项"这个解析行为仍是照抄老产品的。）

> **2026-09-18 更正：** 上面这段的结论当时说对了、收尾说错了。靠
> `_guard_required_selects` **补第一项**恰恰是线上 `b78697f3` 禁掉的做法 ——
> 补出来的是客户从没选过的称谓/地址。现已按线上改成
> `dms_customer_geo.validate_customer_selects`：显式给值 + 与实时父级链核对，
> 对不上就拦。新建客户前还会先 `clear_customer_select_defaults` 清掉新表单自带的
> 默认地址（不清 = 客户凭空多一个没人选过的地址）。见
> [27-customer-geo-parity.md](27-customer-geo-parity.md)。

另外两个是我把假 HTML 写错了（少了 `onclick="ctllistdata"`）、以及断言写在了错误字段上
（拿"报错信息"去比"错误码"）。两个都在测试侧修掉，没动业务代码。
