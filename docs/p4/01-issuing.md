# P4.01 控制面发号

日期：2026-09-17。按用户要求：**不搬现在的 `/admin`**，控制面自己做；先做**发号**，保持简单。逻辑由我设计，记录如下。

## 发号是什么

一次发号 = 给一家公司开一批产品，产出**开通清单**。要填的东西：

| 项 | 说明 |
|---|---|
| 租户名称 | 公司/店铺名。**改名不换身份**，这里只是显示名 |
| 登录账号 | 必须是邮箱。**已存在会被拒绝**，不会合并到别人的账号 |
| 使用人姓名 | 顺带写进身份服务，省掉“补全资料”那一步 |
| 产品（可多选） | Cowork / ERP / DMS |
| 每个产品的域名 | 逐行填，**全局唯一** |
| OCR 能力 | A 档 / B 档，可多选（见下节） |

产出：发号单号、租户编号、账号、身份主体、**一次性初始密码**、每个产品的待开通行。

## 数据模型（三个 DocType）

| DocType | 作用 |
|---|---|
| `Pearnly Tenant` | 租户。一家公司一条，与域名、账号都解耦 |
| `Pearnly Issue` | 发号单。记录这次要开什么、开给谁、结果如何 |
| `Pearnly Issue App` | 子表。一个产品一行：产品 + 域名 + 界面标题 |

## 我设计的四条硬规则

1. **域名全局唯一，且当场校验**。同一张单里重复、或与别的发号单撞车，都直接拒绝，不允许“先建了再说”。
2. **账号已存在就拒绝**：提示走“邀请已有账号”流程。**绝不按邮箱把新租户挂到别人的账号上**——这是旧系统最容易出事的地方。
3. **初始密码不落库**，只在返回值里出现一次；库里只记“什么时候交付过”。
4. **一个产品一行域名**，不允许两个产品共用同一个域名。

## OCR 两档：是两种业务，不是好坏两档

用户特别提醒过这一点。核过旧系统后确认：

| 档 | 旧系统叫法 | 用途 | 单价量级 |
|---|---|---|---|
| **B 档** | economy / 3.8 LOW 一类 | **日常发票识别**：采购票、销售票、收据 | 基准 |
| **A 档** | enterprise / Document AI 财务适配器 | **财务扫描件**：银行流水、总账、VAT 报表 | 约 B 档的 3–5 倍 |

所以在发号单上是**两个独立勾选项**，不是“选高选低”。只选 B 的租户不因为“没用 A”而少拿功能；选 A 的租户也不意味着日常发票会走贵的那条路。

## 新系统不做影子双跑（用户确认）

旧系统有个机制：B 档正常出结果后，后台再异步用 A 档只读复核金额字段，结果落 `shadow_money_log`，用于统计真实错误率（不改结果、不计费、异常吞掉）。

**用户明确：新系统不要影子双跑。** 已相应调整：

- `shadow_money_log` 从“保留”改为**待退役**；
- `services/ocr/shadow_money*.py` 不迁移；
- A 档与 B 档各自独立生效，不存在“用 B 出结果、A 在背后偷偷复核”的行为；
- 同一份文件不会因为双跑被收两次费。

## 实测结果（六个场景）

脚本 `scripts/sample-issue.sh`：

| 步骤 | 结果 |
|---|---|
| 控制面登录（**平台 realm**） | 成功 |
| 平台身份访问业务站点 | **被拒**（跨 realm 隔离仍然成立） |
| 发号：一次开三个产品，各自域名，OCR 选 A+B | `ISS-2026-0005` / 租户 `T-2026-0006` / 账号与身份主体已生成 / 一次性密码返回 / 三条待开通行 |
| 用该账号到业务站点登录 | 身份服务**认证通过**并回跳本站 → 本站**拒绝**：“该身份未在本站点登记” → **未建立会话** |
| 同一域名再发一次 | **被拒**：`域名已被占用（发号单 ISS-2026-0005）` |
| 同一账号再发一次 | **被拒**：`账号已存在。请走邀请已有账号流程` |

第四行是这条流程的重点，也是设计意图：**发号只负责“把账号建出来”，账号还不能进任何站点**。真正能进，要等对应的部署建好、身份在目标站点登记绑定之后。这两件事分开，避免“发了号就等于开通了”。

## 过程中修掉的两个问题

1. **控制面要同时接两个 realm**：它自己用**平台 realm** 登录，但要往**业务 realm** 建租户账号。原来的身份管理模块只会读一套配置，已改为按配置前缀指定 realm（`pearnly_oidc` / `pearnly_business_oidc`）。
2. **新建账号被 Keycloak 的“补全资料”必填动作拦住**（只有名没有姓）。已从 realm 侧关闭 `VERIFY_PROFILE` 默认必填动作——我们的账号是操作员建的，不需要用户再补资料。
