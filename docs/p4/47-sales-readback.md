# 销售数据读取层：查询那一族的底座

日期：2026-09-19。承接 [46-entry-e2e.md](46-entry-e2e.md)。线上基准 `501589f0`。

菜单第 5 项"搜索资料"已经在卡上留好位置了，落地它需要三层：**读取层**（本批）、
卡片层（`query_cards`）、流程层（`query_flow`）。本批先落读取层 —— 它是另外两层的底座，
而且是**唯一能脱开 DMS 验实**的一层（用真实形状的 HTML 夹具）。

## 一、搬了什么

| 新平台 | 线上 | 说明 |
|---|---|---|
| `dms_sales_readback.py`（新增，290 行） | `services/erp/mrerp_dms_sales_readback.py` | 现读 DMS 的销售列表与"卖得最好"看板 |

20 个名字与参数个数与线上**逐一对齐**（脚本校验过）。这是**纯逻辑**：零泰文、零会话，
所以整层可以只靠夹具验。

## 二、两处新平台映射（不是逻辑改动）

1. **端点解算**：线上自己遍历老平台的端点表（`core.db.list_erp_endpoints`），
   新平台走 `dms_ocr_service.resolve_dms_endpoint`（花名册里那个启用中的 `mrerp_dms`）。
2. **首页那份 HTML** 用 `adapter.transport().get(...)`（新适配器的 `transport()` 是公开方法）。

## 三、两条要紧的性质（都在验证里钉住）

· **每次调用都重新登录、读完就丢**：查询是只读的一次性动作，留住会话只会让两个销售
  互相踢下线（这条由 `run_logged_in` 的既有契约保证）。
· **解析 fail closed**：`err::` 开头的响应、列数不足的行、看板返回值不是合法 JSON、
  首页读不到筛选条件 —— 一律**明确失败**，绝不回半份数据让人以为"就这么多"。

## 四、验证：`sample-verify-dms-sales-readback.py`（26 项）

用真实形状的 HTML 夹具驱动（不连 DMS、不需要授权）：

· 常量与 DMS 表头顺序对齐（11 个搜索列、15 个状态筛选、3 分组 / 2 指标、两个原生路径）；
· 单元格归一：去标签、解实体、压空白、`-` 占位归一成空串；
· 列表解析：**字段逐列对位**（错一列就会把客户名显示成车型）、列数不足或单号为空的行跳过；
· 取一页：列/状态/关键词翻成 DMS 编码、页大小夹在 1~30、页码至少 1、拿满一页才算有下一页；
· 失败关闭：`err::` → 明确失败（`ERR_DMS_TECHNICAL`）、无端点 → `ERR_NO_CREDS`、
  端点解算自己炸 → `ERR_UNEXPECTED`（不把异常抛给用户）；
· 看板：从首页读回用户 id / 分店 / team（占位 `0` 去掉、**编号串去重**）、
  打两次 POST（总数 + 本页）、总数与"还有下一页"的算法、默认期间用**佛历**、
  首页读不到筛选条件 → 明确失败。

## 五、抓到的三类错（都值得记）

1. **一个真 port bug**：老产品的异常类叫 `DMSClientError`，新平台叫 `DmsClientError`
   （只有 `ms` 大小写不同）。我导入的是新名字、抛的却还是老拼写 → 四处 `raise` 全是
   **运行时 `NameError`**。静态看代码看不出来（大小写只差一处），是这条验证跑起来才露的。
2. **夹具写错**：看板的本页响应是 `[labels, ids, values]` 三层数组，我一开始写成了
   三个并列数组（少了外层括号）→ 解析按预期失败。代码对、夹具错。
3. **断言写错**：分店**名字列表不去重**（线上同款，去重只发生在编号串上）。我按"应该去重"
   去断言了。

另外记一个**环境坑**：`bench console` 里用 `exec(open(...).read())` 跑文件时，
**文件顶层定义之间互相引用会 `NameError`**（顶层函数看不到同文件里别的顶层名字）。
所以验收脚本的写法必须是"一切都在 `main()` 里面" —— 现有 19 个脚本都是这个形状，
这次踩了一次才发现原因。
