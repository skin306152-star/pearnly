## 二、这条链的价值在"凭据"两个字

销售改不动老客户资料时提审；**执行用的是批准人自己的 DMS 账号**（不是销售的、也不是平台账号）
—— DMS 侧的审计因此显示**真实批准人**。所以执行那一步先解析**批准人**的 DMS 连接，
批准人没配就明说、并把申请**退回待批**（不吞掉）。

三处分工别在这里重复实现：

· **一次性**由 `dms_approval_store.claim` 的原子认领保证 —— 流程只处理"抢不到"的回话；
· **状态话术**来自卡片层（`_status_text_for_sales` 按状态挑一句）；
· **执行失败要回炉**（`finish(..., "pending")`），不是判失败。

## 三、审批策略（泰方 2026-07-19 拍板）与"链路是待开的，不是断的"

`APPROVAL_POLICY = {"customer_profile": False, "credit_auth": True}`：

· **客户档案改写不审** —— 销售直写，写路径借老板管理员凭据落地；
· **未登记的改动类型默认要审**（fail-closed：新高危动作忘登记 = 默认要审）；
· 所以按当前策略，`exact_diff_card` 里"提审"那条分支**走不到** —— 与线上一致。

验证里专门把策略临时打开跑了一遍（"信用授权上线时在此登记 True"），
**证明这条链是接好的、待开的**：销售 + 要审 → 出提审卡并标记走审批。

## 四、验证：`sample-verify-dms-approval-flow.py`（46 项）

外部依赖（花名册 / 存储 / DMS 写入 / 推送）全换假的；**状态话术与卡片结构用真的**。

· 卡片：选人卡首项固定"发给全部"、最多 6 个管理员键；审批卡批/拒两键**只带申请号、
  不带 nonce**（一次性靠存储认领）；等待卡带"改派"；
· 策略与主按钮：fail-closed、管理人直写、没写权只提示、**策略一开就出提审卡**；
· 名录：能收卡的管理员要同时满足"管理员 + 启用 + 已绑 LINE"；老板（无档案但本身管理员）也能批；
· 提审：草稿不对 → 过期；没有能收卡的管理员 → 明说指路；成功 → 建申请（带差异/草稿快照）
  → 清会话 → 发选人卡；nonce 被消费；
· 选人/改派：不是自己的单 → 过期；已处理 → 按状态回话；选的人解绑 → 让重选；
  指定人 → 申请卡**推给他**、等待卡回销售；发给全部 → 推给所有能收卡的人；
· 批/拒：非审批人 → 明确拒；抢不到认领 → 分"已被处理"与"已过期"两句；拒绝 → 落 rejected +
  通知销售；批准 → 先回"正在处理"再丢后台；
· 执行：认领后权限被收回 → 回炉；批准人没配连接 → 回炉 + 明说；
  **用批准人的连接**（审计口径）；写入字段 = 必填两项 + 逐条新值、覆盖写；
  成功 → 台账 + 已批 + 通知双方；失败 → **回炉** + 如实带 DMS 的原因；两种都落台账；
· 小工具：展示差异的兜底、申请人没绑 LINE 时不推送；
· 接线：提审/批/拒三个动作归审批层，**写档动作仍归 `dms_flow`**（审批层不抢）。
