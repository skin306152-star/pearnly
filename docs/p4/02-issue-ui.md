# P4.02 发号界面

日期：2026-09-17。控制面在 `control.localhost`，只在开发机运行（ADR-004）。

## 页面

`/pearnly-issue`，一个页面完成发号：

| 区域 | 内容 |
|---|---|
| 公司与账号 | 租户名称、登录账号、使用人姓名、联系电话 |
| 开通哪些产品 | Cowork / ERP / DMS 三行，勾选后自动带出该产品的域名输入框并预填一个建议域名 |
| OCR 能力 | B 档（经济·日常发票）与 A 档（高精·财务扫描件）两个独立勾选，各带用途说明 |
| 备注 | 自由文本 |
| 结果区 | 发号单号、租户、账号、身份主体、**一次性初始密码**、OCR 能力、待开通清单 |

提交时前端先做基本校验（租户名、账号、至少一个产品），服务端再做完整校验。

## 一次性密码的提示

结果区把初始密码单独框出来，并明确写：**只显示这一次，本系统不保存明文，请立刻交给客户并提醒首次登录后改密**。
库里只记"什么时候交付过"（`password_delivered_at`）。

结果区还写明：**账号已建好，但还不能登录任何站点**——要等对应的部署建好、身份在目标站点登记之后。
这句话是给操作员看的，避免误以为"发了号就等于开通了"。

## 页面不承载数据

页面本身是纯静态表单（没有模板变量），身份与 CSRF 令牌通过一个**要求登录**的接口取：
`pearnly_control.issues.api_context`。未登录时该接口直接报错，前端据此把浏览器送去登录页。

也就是说：**页面能被谁看到无所谓，所有数据动作都在登录之后**。

## 实测结果

脚本 `scripts/sample-issue-ui.sh`：

| 步骤 | 结果 |
|---|---|
| 未登录打开发号页 | 200，表单齐全，页面里**没有未渲染的模板变量** |
| 未登录调 `api_context` | **PermissionError**（前端据此跳登录） |
| 平台 realm 登录 | 成功 |
| 取上下文 | 操作人与 56 字符的 CSRF 令牌 |
| 用页面同一条接口发号 | `ISS-2026-0007` / 租户 `T-2026-0008` / 一次性密码已生成 / 两条待开通行（cowork、dms） |
| 发号单列表 | 能查到自己发的号，含 OCR 摘要（"仅 B 档（经济·日常发票）"） |

## 一个我判断错、后来查清的问题（必须记）

第一次打开发号页，页面里残留着 `{{ operator }}`、`{{ csrf_token }}` 这样的原文，看着像
"模板变量没被渲染"。我据此判断 Jinja 出了问题，改用接口取上下文绕开它。

**这个判断是错的。** 真正原因是 **Frappe 的网页缓存**：在控制器还没被识别的那一小段时间里，
Frappe 缓存了一份"没有上下文的渲染结果"，之后一直拿缓存回给我。清掉站点网页缓存后，
页面里未渲染变量归零，内容也对上了。

**留下的教训**：改过 www 页面之后要清站点网页缓存，否则会拿到旧结果，而且会误导排查方向
（我差点就去怀疑框架的模板引擎了）。测试脚本里已经加上这一步。

接口取上下文这个做法我保留了——它能用、已测过，而且顺带把"未登录就跳登录页"这件事写明白了；
但**不能把它当成"模板不能用"的证据**，那是缓存造成的假象。
