# 计费底座：余额、充值审核、扣费规则（三套产品共用一份）

日期：2026-09-18。状态：**已实现并实测**（`scripts/sample-verify-billing.sh` 全过，可重复跑）。

## 放在哪，为什么

老产品所有租户住同一个库，钱表（`tenant_credits` / `credit_transactions` /
`topup_requests`）就在库里。新平台**每个租户是一个独立站点**，钱不能跟着某个产品走 ——
同一家公司在 Cowork、ERP、DMS 三个站点上必须是**同一本账**。

只有**控制面**同时认识所有租户和所有产品，所以钱记在控制面
（表归属本来就这么定的：`docs/p0/05-table-ownership.md`）。

三条规矩：

1. 产品站点**不许自己算钱、不许直接改余额**，只能调 `billing_client`；
2. 改余额必须**同时落台账**（同一事务）—— 只改余额不落台账，钱账就对不上；
3. 余额可以扣成负数（用量已经发生了），欠账靠后续充值补 —— 这是老产品的口径，不是 bug。

## 规则（老产品原值，一条没改）

| 单位 | 价格 |
|---|---|
| PDF / 图片 | 每月前 **200 页 ฿1.50/页**，超出 **฿0.75/页**（跨界自动拆段）|
| Excel / Word / CSV | **50 字符 = ฿0.01**，向上取整 |
| 文档折成"张"（套餐额度用）| 按量成本 ÷ ฿1.50，向上取整 |
| 银行对账单的计费页数 | `max(物理页数, ⌈行数/40⌉)` —— 防"一页塞很多笔"被低估 |

**失败不收钱**：解析失败、或解析出 0 行的件不算钱。

**月度锚按 Asia/Bangkok（UTC+7）**：用 UTC 算会让月初 7 小时的用量落进上个月，
阶梯价跟着错（老产品踩过）。

## A/B 两档

档位**按任务**分，不是按租户卖的：银行流水 / 总账 / VAT 报表 / 身份证走 **A 档（高精）**，
发票走 **B 档（经济）**。两档是两种业务，不是同一功能的好坏两档。

不做影子双跑（用户 2026-09-17 确认）：同一份文件只收一次费。

### 顺带修掉的一个缺陷

老产品 A 档成本约为 B 档的 3–5 倍，**扣费却走同一套页价** —— 等于高精档白送。
这里加 `TIER_A_MULTIPLIER`（默认 3 倍，取用户给区间的低端）。
这是个生意决定，要改就改 `pearnly_control/billing.py` 里那一个常量。

实测：身份证识别走 A 档，估价 ฿4.50 = ฿1.50 × 3。

## 余额闸：三条出路必须分清楚

```
钱够            → 放行
insufficient_balance → 402，界面引导去充值
lookup_error         → 503，是**我们**查不出来，让用户稍后重试
```

**绝不能把系统故障报成"余额不足"** —— 那会让会计去充一笔本来就够的钱
（老产品为这条专门写过注释，代价是有人被误导过）。

闸门位置：`recognize_id_card` 里排在"端点存在"之后、
**调模型之前** —— 拦晚了就是白花钱。实测余额 0 时被 402 拦下，
识别根本没发出去。

## 充值闭环

```
租户在站点上点「充值」  → service_topup_request  →  落一条 pending 申请（不动余额）
平台管理员在控制面点「同意并到账」（可改实收金额，以银行到账为准）
                       → 余额立即增加 + 落台账（同一事务）
```

审核台：控制面 Desk → 租户开通 → **充值审核**（另有「余额」「余额流水」两个入口）。

## 开通时怎么接上

开通流程多了一个 `set_billing` 步骤，把三样写给站点：

```
pearnly_tenant              本站是哪家租户（T-2026-0001）
pearnly_billing_api         控制面地址（容器内网 http://control-web:8000）
pearnly_billing_host_header 控制面的站点名（Frappe 靠 Host 认站点）
pearnly_billing_token       服务令牌
```

**这个步骤对已经开过的租户也能补**：重跑一次 `plan` 就会把新步骤补进请求里，
执行器自动跑（实测：11 步 → 12 步，补完站点就拿到了计费配置）。

## 卡里的 LINE 是"先开通、后配"

`set_line` 那一步在这家租户还没配 LINE 渠道时记 **skipped**（不是失败、也不是完成）。

之后配好渠道要**补跑那一步**：之前 `skipped` 的步骤永远不会被重跑，
所以加了 `--all`：

```bash
scripts/sample-provision.sh retry ISS-2026-00XX --all   # 连 skipped 一起补跑
```

（默认不带 `--all`：skipped 有两种含义 —— "本单不需要"和"现在还没到配的时候"，
只有后者需要补跑。）

## 还没做的（如实说）

- **租户侧没有充值界面**：申请只能从产品站点用服务令牌发（控制面侧审核台是齐的）。
  产品上那个「套餐与余额」页（显示余额 / 发起充值 / 看流水）是下一步。
- **订阅套餐（S/M/L）** 没搬：老产品有"套餐额度 + 超额单价 + 到期自动从余额续订"，
  这轮只搬了按量计费的底座。
- **扣费目前只有 DMS 的身份证识别这一处**接上了；Cowork 的对账/发票、ERP 侧还没接。
- 真实转账截图核验（SlipOK 自动验金额）没搬。
