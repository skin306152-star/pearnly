# 入口链端到端：从 LINE webhook 入口走一遍

日期：2026-09-19。承接 [45-menu-entry-wiring.md](45-menu-entry-wiring.md)。线上基准 `501589f0`。

前面那些脚本验的是"**每一层自己对不对**"；这一条验的是"**它们接起来以后还对不对**"。
入口是全链路唯一没有单层归属的地方：webhook 事件 → 绑定判定 → 文本/图片/postback 三条路
→ 路由分支。这里出的错长相都一样 —— **用户发了消息，什么也没发生** —— 所以值得单跑一遍。

## 一、怎么跑的

`sample-verify-dms-entry-e2e.py`（12 项）从这个真实入口进：

```python
line_handlers.handle({"type": "message", "source": {"userId": ...}, "message": {...}})
```

LINE 出口（`reply` / `push` / `start_loading`）与后台入队（`dms_flow._enqueue`、
`dms_booking_flow._enqueue`）换成记录器，绑定查询换成假的（不建真绑定行），
**会话用真的** —— 所以状态流转是真的。

走的是这条线：未绑定提示 → `เมนู` 弹菜单卡 → 点"2 订车" → 拍卡丢后台识别 →
输手机号丢后台查重 → 逐问态输金额走状态机 → 待确认态打字只提醒 → 点确认消费 nonce 并丢后台
→ 再发 `เมนู` 覆写会话 → `เริ่มใหม่` 清会话 → 位置消息有明确回应。

## 二、两条**这一层独有**的规矩被钉住了

· **逐问态的文本先归状态机**：金额 `5000` 没被"含数字→手机号"这条通用规则吃掉，
  真的进了 `pay_amount` 步（进错分支就废掉一次会话）。
· **待确认态的文本不算确认**：打字「ยืนยัน」只回"请点上面的按钮"，
  **不消费 nonce、不建单** —— 确认只能来自带 nonce 的按钮。

## 三、写这条用例时踩的三个坑（都是"用例错、代码对"）

1. **金额步的前置**是"已经选好渠道"（`pending_channel` 由 `pick_channel` 先写）；
   我直接造了个 `pay_amount` 态的会话，于是一进状态机就 `KeyError`。
2. **引错命名空间不会报错**：`cards.TXT_CONFIRM_ABOVE` 取不到会**静默返回裸 key**，
   比较自然不相等（正确的位置是 `dms.card.qa.*`，要用 `qa_cards.`）。
   这类"取词回退成 key"的设计方便排查，但**写断言时要看清是哪个命名空间**。
3. **换出口要换全**：建单执行体有**自己的一份入队**（`dms_booking_flow._enqueue`），
   只换 `dms_flow` 那份的话，点"确认"会往真队列丢一个真后台任务。
   第一次跑就真发生了一次：那个任务**卡在"本站点没配 LINE token、发不出消息"**
   （所以**没有碰到 DMS**、没有副作用），留下的那条错误日志已按本次产物清掉。
   现在两份入队都在测试里换掉了。
