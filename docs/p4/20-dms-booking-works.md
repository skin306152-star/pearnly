## 一、先纠正一件事：建单默认值不是必填

上一轮我结尾问了用户"建单默认值要填什么、顾问怎么定" —— **这问题本身就是多余的**，
用户直接指出："老项目怎么做你怎么做，老项目都是跑通的，你现在来问我，是要重新设计规则吗？"

去读代码，老项目的规则本来就很清楚（`mrerp_dms_client_ops.resolve_booking_payload`）：

| 项 | 规则 |
|---|---|
| 车型 / 颜色 / 分店 / 团队 / 付款条件 / 登记代办 | **钉了 id 就用钉的；没钉就取实时主档第一行** |
| 顾问 | **必须按操作员的 DMS 账号匹配出来**（或端点上钉死）；匹配不上就报错拦下 |

而 `dmstest` **本来就在顾问名册里**（`[264, 'dmstest', 'dmstest']`）——
所以顾问会自动归属，不需要任何人工配置。结论：**照老项目跑就行，什么都不用问。**

## 二、这一步补了哪四块

建单这条链缺的部件（都在老项目的 `services/line_dms/booking_flow.py` 和它依赖里）：

| 我们这边 | 老产品 | 干什么 |
|---|---|---|
| `dms_booking.py` | `booking_flow._book_in_session` | 建单执行体：复核主档 → 建单 → 挂附件 → 刷主档缓存 |
| `dms_master_contract.py` | `line_dms/master_contract.py` | 主档会话快照 + **提交前复核** |
| `dms_booking_customer.py` | `mrerp_dms_booking_customer.py` | 建单前按证号重查客户，拿**主档权威值**并核对客户号 |
| `dms_qa_util.py` | `line_dms/qa_util.py` | 逐问的纯函数工具（归一/金额/主档行标签） |

四条必须保留的设计：

1. **先复核再建单**：操作员选车是几分钟前的事，确认那一刻 DMS 主档可能已经改了
   （车型下架、颜色停用、银行换号）。拿旧选择直接建单，轻则填错、重则把钱指向不存在的账户。
2. **账套级互斥只护「取号 → 提交」**：同账套不同销售账号并发取号会撞单号；
   但客户写入/挂附件/刷主档这些慢步骤**不进共享锁**，否则一个慢附件卡住全店。
3. **附件在同一会话挂**（少一次登录），**建单成功但附件没挂全要如实说**，不谎报。
4. **顾问匹配不上宁可报错**，绝不落到名册第一行 —— 落错人只有月底对账才看得出来。

## 四、复核机制被"误报"验了一次（值得记）

第一次跑建单失败在复核那一步：`ERR_DMS_MASTER_CHANGED`（"主档刚刚变化，请重新核对"）。

查下来是**我的测试载荷写错了**：只给了 `id` 没给标签，于是复核层把"标签从空补成真值"
当成了一次主档变化。真逐问在选中时就同时存了标签，所以正常路径不会有这个差异。

两条结论：

· **复核真的在工作** —— 差异确实被它算出来了，不是摆设；
· 载荷修好（补上标签）之后 `status=ok`，建单一次过。

顺带说明为什么"标签变了"也要拦：标签是操作员在预览卡上看到并确认的东西。
如果 DMS 那边把车型名改了，操作员确认时看到的是旧名 —— 那就是"他确认的不是这个东西"，
必须让他再核一遍。
